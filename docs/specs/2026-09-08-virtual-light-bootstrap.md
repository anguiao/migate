# MiGate 起步：本机虚拟灯 Matter Bridge

## 目标与背景

在本机 macOS 上运行 MiGate，将一盏虚拟开关灯通过 Matter Bridge 接入真实 Apple Home，验证配对、双向控制与状态同步、配对信息恢复，以及稳定的设备身份。

MiGate 的长期目标是将米家（Xiaomi/MIoT）设备接入 Apple Home 等 Matter 生态。技术路线为 Rust、`rs-matter` 和 Matter Bridge，优先覆盖灯、开关、插座、传感器、窗帘和空调，仅暴露可自然映射为标准 Matter 能力的设备功能。Apple Home 是首个验证目标。

MiGate 按个人自用项目推进，不以获得正式 Matter 产品认证为前提。Apple Home 的实际配对与控制结果是本轮兼容性验收依据。

当前仓库尚无实现。本里程碑先用虚拟灯验证桥接、命令和状态边界，后续再接入真实米家设备；README 中米家灯到 Apple Home 的完整链路仍是后续目标。

## 范围与方案选择

本文定义的实现里程碑交付一个使用 Rust `std` 的本机前台程序，以及复现运行和验收步骤的项目文档。首轮验收平台为 macOS / Apple Silicon；当前开发机为 macOS 27.0、arm64。

功能范围包括固定的一盏虚拟开关灯、真实 Matter 网桥、终端控制、状态变化上报、本地配对存储和正常退出。虚拟设备从第一天起经过 MiGate 的设备边界和 Matter 适配层。

起步阶段以跑通首次配对、双向控制和同目录重启恢复为中心，优先采用协议栈已有能力和简单的人工操作。验收时在 Mac 保持唤醒、局域网连通的条件下运行单个 MiGate 进程；切换数据目录前先停止现有进程。

| 起步方案 | 取舍与结论 |
| --- | --- |
| MiGate 内置虚拟设备 | 选用。能验证 MiGate 自身的命令、状态和 Matter 映射边界，后续可据真机反馈调整。 |
| 直接运行上游 Matter 示例 | 可作为实现参考，但单独运行示例不足以完成本轮的 MiGate 验收。 |
| 模拟完整米家协议 | 需要先确定真实协议行为，留到米家接入阶段按实际需要评估。 |

本轮范围之外：真实米家通信与账号认证、设备发现、其他设备类型、亮度与色温、动态增删设备、管理前端、HTTP API、插件系统、Linux 部署和常驻服务安装。

## 运行与交互

- 直接运行 `migate` 启动前台进程；开发时可用 `cargo run`。
- 数据目录依次取 `--data-dir <PATH>` 参数、运行时环境变量 `MIGATE_DATA_DIR`、当前用户的 `~/.migate/` 默认目录。参数或环境变量提供的相对路径按进程启动时的工作目录解析。
- 启动后输出实际数据目录、设备信息和运行日志；未配对时输出 Matter 配对二维码和手动配对码。
- 日志写入标准错误；配对指引和终端命令结果写入标准输出。
- 终端按行接收下表中的小写命令，忽略首尾空白和空行。收到输入结束只停止终端读取，桥接服务继续运行；`Ctrl-C` 用于正常停止程序。

| 终端命令 | 行为 |
| --- | --- |
| `on` | 将虚拟灯设为开启，成功后显示当前状态。 |
| `off` | 将虚拟灯设为关闭，成功后显示当前状态。 |
| `status` | 显示固定设备标识与当前 `on` / `off` 状态，不改变状态。 |

未知命令或多余参数显示可用命令提示，保持设备状态并继续接收输入。MiGate 的启动配置由命令行参数和环境变量提供，终端仅支持上表命令。

开发环境通过项目级 `.cargo/config.toml` 设置数据目录：

```toml
[env]
MIGATE_DATA_DIR = { value = ".migate", relative = true }
```

Cargo 将该值解析为项目根目录下 `.migate/` 的绝对路径并注入进程；已有同名环境变量优先于这项项目默认值。该配置对 `cargo run` 和 `cargo run --release` 均生效。[Cargo 环境变量配置](https://doc.rust-lang.org/cargo/reference/config.html#env)

MiGate 在启动时读取进程环境。直接运行二进制时按同一优先级选择目录，不读取 Cargo 配置。项目根目录下的 `.migate/` 用于开发运行数据，并加入 Git 忽略规则。

Apple Home 验收使用同一局域网中的 iPhone/iPad「家庭」App，网络应允许 Matter 通信与 mDNS 发现。Apple 当前说明支持通过家庭 App 添加 Matter 网桥，并说明 iOS 18 及以上的 iPhone 可在没有家庭中枢时进行 Matter 配对和本地控制；本轮不将额外购买家庭中枢作为前提。[Apple 配对说明](https://support.apple.com/en-euro/102135)

## 模块与边界

采用单个 Cargo 包，主要职责如下。进程入口负责组装这些模块。

| 单元 | 职责和对外操作 | 依赖边界 |
| --- | --- | --- |
| `device` | 定义稳定设备标识、开关命令和状态快照。开关命令表达开启、关闭和切换状态。 | 保持协议无关，不引入 Matter cluster、endpoint 或米家属性编号。 |
| `virtual_device` | 保存虚拟灯的当前状态，执行设备命令，提供快照读取和变化通知。 | 使用 `device` 定义，是本轮灯状态的唯一来源。 |
| `matter` | 构建网桥和子设备，处理配对与协议交互，将协议命令转为设备命令，将设备快照映射成 Matter 属性。 | 使用 `rs-matter` 和设备操作边界；将协议库类型限制在适配层内。 |
| 进程入口与存储接入 | 解析启动参数和运行时环境变量，定位数据目录，启动 Matter 与终端任务，处理退出，接入身份和协议栈的持久化。 | 负责基础设施组装，不另建灯状态副本。 |

边界先用普通结构体、枚举和直接调用表达。具体并发组织留在运行与适配代码内部，不建立通用驱动框架或多层 trait 体系。

未来真实米家适配可以沿用设备命令、快照和变化通知的语义。届时再根据设备响应、延迟和离线行为调整边界；本轮不预设 MIoT 协议模型，也不创建空的米家实现模块。

## 状态与数据流

虚拟灯的运行状态只有 `power`，初始值为关闭。身份属于持久化元数据，独立于开关状态。

设备操作具有以下语义：

1. 执行开启、关闭或切换命令时，串行完成状态读取与修改，避免两个入口同时操作时丢失更新。
2. 返回成功表示虚拟设备已达到目标状态；状态已经符合命令时同样成功。
3. 状态实际发生变化后发出变化通知。重复设置同一状态不制造额外的状态变化。
4. 快照始终来自虚拟设备。Matter 侧的协议元数据、属性版本和订阅机制可以由协议栈维护，业务开关值保持单一来源。

家庭 App 控制时，Matter 适配层将命令交给虚拟设备，待设备确认后完成对应协议响应，并使属性读取和报告反映新状态。终端的 `on` / `off` 调用相同的设备操作，随后通过同一条变化通知路径触发 Matter 属性报告。

`status` 与 Matter 属性读取均读取当前设备快照。通知可以合并连续变化，但最新快照必须能够被读取和报告；设备确认失败时返回对应错误，不将请求的目标值当作已完成状态。

## Matter 拓扑与依赖

本轮采用固定拓扑：

| Endpoint | 用途 |
| --- | --- |
| `0` | 根端点，承载节点级系统能力。 |
| `1` | Aggregator，描述其桥接的子设备。 |
| `2` | 虚拟灯，同时具备 On/Off Light 与 Bridged Node 的设备语义。 |

本地设备标识固定为 `virtual-light-1`，用于程序内部寻址。网桥与子设备对外暴露的稳定实例标识在首次初始化时生成并持久化，随后随数据目录复用；固定的本地标识不代替这些对外标识。网桥默认名称为 `MiGate`，虚拟灯默认名称为 `MiGate 虚拟灯`。每次启动保持 endpoint 与设备身份的对应关系。

使用 `rs-matter` 的标准设备定义和簇处理能力，保留此拓扑和 On/Off Light 所需的属性与命令，包括 Matter 侧的 On、Off、Toggle。桥接基本信息提供稳定身份；进程运行期间虚拟灯为可达状态。本轮不模拟设备离线。

上游桥接示例使用根端点、Aggregator 和虚构开关灯，作为本设计的实现参考；示例本身不构成 MiGate 的 Apple Home 验收证据。[官方桥接示例](https://github.com/project-chip/rs-matter/blob/main/examples/src/bin/bridge.rs)

`rs-matter` API 尚未稳定。实现须固定该依赖的具体 Git revision，并提交 Cargo.lock，避免开发期间随上游分支漂移。macOS mDNS 使用上游文档给出的 `astro-dnssd` 路径，并以本机发现与配对结果验证。[rs-matter 文档](https://github.com/project-chip/rs-matter)

本轮使用 `rs-matter` 提供的测试设备认证材料及其匹配的厂商、产品编号（VID/PID），不自行申请正式产品认证。测试认证材料不代表每个 MiGate 实例的唯一身份；网桥与子设备的稳定标识仍按数据目录分别生成和恢复，配对后形成的运行凭据由协议栈管理。[上游测试设备定义](https://github.com/project-chip/rs-matter/blob/main/rs-matter/src/dm/devices/test.rs)

配对参数沿用所固定 revision 的上游公开测试默认值，二维码与手动配对码从同一组参数生成。本轮不增加配对码配置或生成机制；运行文档说明这些参数用于本轮个人局域网验证。未配对启动时开放 15 分钟配对窗口，与上游桥接示例采用的窗口时长一致。[配对窗口定义](https://github.com/project-chip/rs-matter/blob/main/rs-matter/src/sc/pase.rs)

## 启动、存储与退出

数据目录保存两类内容：MiGate 网桥及虚拟设备的身份元数据，以及 `rs-matter` 要求保存的配对和必要协议元数据。Matter 数据使用协议栈的存储接口读写，保持其格式和生命周期；虚拟灯的 `power` 不写入这些存储，也不从中恢复。

| 情况 | 行为 |
| --- | --- |
| 指定目录不存在或为空 | 创建所需目录，初始化并保存稳定身份，创建固定虚拟灯，进入未配对状态并打开配对窗口。 |
| 已有有效配对数据 | 恢复已有身份和协议栈状态，继续提供同一网桥与虚拟灯。 |
| 已有身份、尚未配对 | 复用身份并打开配对窗口。 |
| 配对窗口超时 | 保持未配对状态并提示重启程序可重新打开窗口；重启仍复用身份。 |
| 数据损坏或初始化数据不完整 | 明确报错并退出，保留原始数据供检查。 |

虚拟灯开关状态只存在于内存。每次启动创建关闭状态，包括此前在家庭 App 中开启过的情况；恢复通信后，属性读取与订阅报告应反映关闭状态。

已配对启动时，不因虚拟灯状态重置而重新创建身份、清除配对或自动打开新的配对窗口。配对相关变更按协议栈要求及时落盘，持久化不以正常退出为唯一时机。

运行中收到合法的解除配对请求时，沿用协议栈的配对关系（Fabric）删除与持久化行为。最后一个 Fabric 被移除后，保留 MiGate 身份元数据和当前灯状态，MiGate 不额外触发新的配对窗口；用户以同一数据目录重启后即可重新开放配对。此操作方式写入运行文档，本轮不增加专门的解绑管理交互。

收到 `Ctrl-C` 后停止接收新操作，结束服务并完成正在进行的必要持久化操作。正常停止返回成功；停止期间持久化失败时明确报错并返回失败。

开发中需要全新配对时，可由用户显式选择一个新的数据目录。新目录代表一个新的桥接实例，需要重新添加到家庭 App；原目录的数据不受影响。清理旧实例通过家庭 App 与本地数据目录的显式维护完成，本轮不增加自动重置逻辑。

若用户在 MiGate 离线时从家庭 App 移除配件，而本地配对关系仍然存在，则使用新的数据目录重新开始；MiGate 不根据控制端暂时不可达推断配对已被移除。

## 错误处理

| 边界 | 处理方式 |
| --- | --- |
| 无效启动参数或最终选中的数据目录值为空 | 输出错误和使用提示，以非零状态退出。 |
| 数据目录不可访问、身份或配对数据无法恢复 | 输出问题及相关路径，以非零状态退出。 |
| Matter 端口绑定或 mDNS 初始化失败 | 输出可定位的错误，以非零状态退出。 |
| 终端无效命令 | 显示命令提示，保留状态并继续运行。 |
| 不支持或格式无效的 Matter 请求 | 通过协议栈返回对应状态，不改变设备状态。 |
| 运行中的致命存储或服务任务错误 | 将错误传至进程边界，记录后停止并返回失败。 |

日志包含操作与错误上下文，配对码仅出现在明确的配对指引中，密钥和完整配对存储不写入日志。

## 验收标准

自动化测试覆盖以下项目行为：

- 验证数据目录选择的优先级：参数覆盖环境变量，环境变量覆盖程序默认值。读写使用最终选中的目录；默认用户目录的解析测试不写入该目录，存储测试使用隔离的临时目录。
- 通过 Matter 命令适配入口修改设备后，终端状态读取能得到一致结果；通过终端入口修改后，Matter 属性读取也能得到一致结果。
- 状态改变能够触发变化通知；连续命令后读取到最新值，重复设置同一值不会制造额外变化。
- 无效命令不影响已有状态，合法命令随后仍可执行。
- 使用隔离的临时数据目录验证身份恢复、启动时灯状态归零，以及损坏存储导致明确失败而不被覆盖。

测试重点是共享状态、适配和恢复行为，Matter 协议栈内部能力沿用上游验证。真实 Apple Home 的显示和订阅行为通过以下人工验收完成：

| 用例 | 操作与通过条件 |
| --- | --- |
| 首次配对 | 使用全新数据目录启动；通过家庭 App 添加 MiGate 后，出现且仅出现一盏桥接虚拟灯，初始状态为关闭。 |
| 家庭 App 控制 | 在家庭 App 中分别开启、关闭虚拟灯；终端 `status` 与最终操作一致。 |
| 设备侧变化同步 | 在终端分别执行 `on`、`off`；已连接的家庭 App 显示对应状态，操作期间保持原配对关系。 |
| 重启恢复 | 将灯开启后用 `Ctrl-C` 停止，以同一数据目录启动；无需再次配对且没有重复配件，先确认已有配件状态同步为关闭，再验证它仍可从两个入口控制。 |
| 输入错误恢复 | 输入未知终端命令；程序继续运行，原状态保持，随后能从两个入口继续控制。 |

状态同步用例在家庭 App 保持前台、控制端与 Mac 网络连通的条件下进行。每次操作使用 30 秒观察上限；超时应记录为未通过并定位原因。这是功能验收的观察窗口，不作为性能承诺。

验收允许家庭 App 提示配件未认证，并在其提供继续入口时由用户确认添加。若家庭 App 拒绝添加，则记录为兼容性验收阻塞；自动化测试或上游示例运行成功不能替代真实 Apple Home 验收。

验收记录包括 macOS 与 iOS/iPadOS 版本、所用 `rs-matter` revision、是否使用家庭中枢、是否出现未认证提示，以及各用例结果。
