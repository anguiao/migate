# MiGate 米家真实设备接入与 Matter 桥接

## 目标与范围

在现有米家认证和 Matter 网桥基础上，将当前局域网内选定类型的米家设备接入 Apple Home，提供日常使用所需的核心控制、传感器读数和状态同步，覆盖多设备、多通道及多种设备类型。

控制优先使用中枢，其次使用设备局域网直连，本地路径不可用时允许使用小米云。网桥固定服务于绑定的米家家庭，云端路径只能操作已经通过本地确认并接入该家庭的目标设备，不能因此接入账号中的其他家庭。允许设备固件自身依赖外网；完全断网控制及完全断网重启不作为硬性验收条件。

本轮交付包括完整设备目录、家庭与局域网归属判断、中枢连接、必要的设备直连、云端控制与通知、核心能力适配、真实设备的 Matter 映射、稳定身份和终端诊断。沿用中国大陆服务区、每个数据目录一个账号、Rust 单包和本机前台运行方式。macOS / Apple Silicon 是本轮开发与验证环境，不据此增加携带主机跨家庭移动的运行场景。

本轮移除起步阶段的虚拟灯、专属运行路径和终端控制入口。项目仍处于开发阶段，采用新的存储结构，不提供旧虚拟灯版本的数据迁移或配对兼容；切换到新实现时使用新数据目录，重新登录米家并配对 Apple Home。

照度功能也可以来自本轮已接入的复合传感器，不要求独立的照度计。数值、单位和读写能力必须与设备实际开放的接口一致。

控制类设备须开放对应主要功能的可写属性或可执行动作；仅有状态、电量、配置项或指示灯控制，不足以创建该类桥接设备。用户指定的传感器凭有效读数或事件接入，不要求具有写入能力；电量仅作为已接入设备的附属能力。复合设备逐功能检查，不能借用另一个功能的控制或状态来补齐当前功能的能力。

本轮明确不接入推窗器、无线按钮、旋钮和 `yeelink.light.nl1` 感应夜灯。该夜灯只开放运动、照度和电量，没有照明控制接口，其附带传感器也不导入。[夜灯物模型](https://miot-spec.org/miot-spec-v2/instance?type=urn%3Amiot-spec-v2%3Adevice%3Anight-light%3A0000A0AB%3Ayeelink-nl1%3A1)

门锁、水暖毯、驱蚊器、摄像机、门铃、电视、音箱、路由器及其他厨房、健康或办公设备留到后续。中枢仅作为通信基础设施使用，不创建额外的 Apple Home 设备。排除规则先于服务识别，不能借助附带的灯、温度、门状态或按钮服务绕过设备范围。

设备预设场景、渐变设置、断电记忆、指示灯、提示音、童锁、校准、雷达区域配置、灵敏度、扫地地图、房间清扫、耗材重置等配置功能不导入。存在传感器本轮使用整体状态，不自动创建物模型预置的分区实体。能耗统计、历史数据、自动化规则引擎、管理网页、公开 HTTP API、插件系统和服务安装不在本轮范围。

Apple Home 是兼容性验收目标；所选能力以标准 Matter 类型和属性表达。平台支持的设备类别不等于某个米家型号已完成桥接。[Apple Matter 类型说明](https://developer.apple.com/apple-home/works-with-apple-home/)

## 方案选择与模块边界

采用统一核心能力模型，并为真实协议差异补充少量明确的型号适配。

| 方案 | 取舍 |
| --- | --- |
| 标准能力识别与必要型号适配 | 选用。多种设备共享身份、状态和控制入口；旧 miIO 型号及确有差异的属性转换单独处理。 |
| 全部按型号实现 | 重复定义共同能力，当前型号数量下维护成本较高。 |
| 仅中枢与云端 | 通信实现较少，但会放弃部分已有设备的局域网直连能力。 |

数据流为：账号目录与本地发现确定归属，物模型和型号适配生成核心能力，设备服务负责命令及状态，Matter 与终端使用同一份设备服务。通信路径不创建独立的设备副本。

| 单元 | 职责与依赖 |
| --- | --- |
| `device/` | 从现有 `device.rs` 扩展，定义设备／功能身份、能力、类型化命令、状态和变化通知。保持协议无关，不暴露 MIoT 属性编号或 Matter 类型。 |
| `xiaomi/catalog/` | 整理完整家庭、房间和设备目录，读取并缓存 MIoT-Spec，合并拆分通道，执行类型范围与能力规则。依赖云端边界及存储。 |
| `xiaomi/discovery/` | 发现中枢和局域网设备，报告接口、家庭及身份核对结果。收到设备发现信息不等于身份验证成功。 |
| `xiaomi/gateway/` | 维护中枢 MQTT/TLS、请求关联、属性与事件订阅、设备列表及连接状态。 |
| `xiaomi/lan/` | 处理设备 token 认证的局域网通信，提供原生 MIoT 操作及 `mcn02` 的传统 miIO 适配。 |
| `xiaomi/cloud/` | 扩展现有 HTTP 边界，提供属性读写、动作和完整目录；云端 MQTT 只负责所选设备的通知。 |
| `xiaomi/runtime/` | 编排发现、目录更新、路径选择、命令队列、状态归一化和重连；调用现有认证服务维护凭据。 |
| `matter/` | 管理稳定 endpoint、设备类型与簇，转换命令、读取统一快照并报告变化。 |
| `storage/` | 管理认证、归属、物模型、身份分配及最后确认状态的初始化、事务和格式检查；SQL 不进入业务模块。 |
| `terminal/` 与入口 | 提供交互和诊断，组装依赖，管理任务与退出；不保留另一套设备状态。 |

使用普通结构体、枚举和必要的窄接口，不建立空的通用驱动框架。网络等待不得阻塞现有执行器，不在数据库事务中等待网络。MQTT 断连、单个设备异常或一次刷新结束都不能让主运行任务正常返回并结束网桥。

MQTT 的报文编号、心跳、QoS 握手和通用会话处理使用成熟客户端依赖；项目只维护小米主题、消息格式和请求关联。账号状态、设备准入与连接状态各有明确的唯一维护者，其它模块读取结果，不重复维护控制资格。持久化使用明确的序列化类型，短暂数据库锁竞争在存储边界集中处理；不预建没有实际调用者的缓存或框架。

## 家庭识别与局域网边界

### 完整目录与自动绑定

云端目录继续使用现有 OAuth 应用与中国区入口，关闭共享家庭和共享设备扩展。完整读取家庭／房间分页和设备分页，处理重复游标、拆分条目及协议允许为空的集合；分页中断不把剩余设备认定为已删除。启动、手动刷新、设备目录变更通知时请求更新，并在云端可用时每 10 分钟校对一次，合并重叠请求。目录数据只在边界解析和校验。[上游目录接口](https://github.com/XiaoMi/ha_xiaomi_home/blob/main/custom_components/xiaomi_home/miot/miot_cloud.py)

通过 `_miot-central._tcp` 发现中枢，读取其在局域网发布的发现信息，并将其中的家庭分组标识与账号自有家庭匹配。相同中枢在多个接口出现时去重；同一家庭可以有多台实体中枢，按该家庭当前发现的主中枢建立会话，支持主中枢变更。目标固件包括 `xiaomi.gateway.hub1` 的 `3.5.0_0011`，不将固件号写成唯一允许版本。[上游中枢发现](https://github.com/XiaoMi/ha_xiaomi_home/blob/main/custom_components/xiaomi_home/miot/miot_mdns.py)

本轮以当前局域网的中枢所属家庭为唯一目标家庭。首次运行时，通过本地中枢匹配账号自有家庭，完成本地身份验证后自动绑定并保存账号 UID 和家庭 ID，名称仅用于显示。同一家庭的多台中枢归并处理，家庭识别不需要用户选择或指定启动参数。若已认证的本地自有中枢报告相互冲突的家庭归属，暂停真实设备控制并报告归属冲突；本轮不为该情况增加家庭选择流程。

同一账号已有绑定时只恢复该家庭，本地中枢短暂无法发现不撤销已准入设备；尚未准入的新设备继续等待本地确认。无登录或首次尚未确定目标家庭时，真实设备保持未接入或不可用，Matter 网桥服务继续运行。尚无已发布真实设备时只提供根节点和 Aggregator，不创建占位设备；已发布设备的保留与移除按后述拓扑规则处理。认证子命令保持原有语义。

### 设备准入

目标家庭的云端目录只是候选名单。设备须同时通过类型范围检查，并取得本地归属依据：

- 中枢路径以成功认证的本地主中枢所报告的设备及可本地访问／通知能力为依据；仅在云端在线不足以准入。
- IP 设备直连须在本地物理网络接口上发现，核对 DID，并用该设备 token 校验通信响应；不能仅相信缓存 IP 或未认证广播。
- BLE、Mesh 和其他中枢子设备通过其本地中枢关系确认，不因它们没有自己的 IP 而排除。
- 灯组以灯组自身的 DID 独立判断准入：目标家庭中的灯组须由当前已认证的本地主中枢报告，并具备本地访问能力；不查询或逐一核对其成员。仅云端存在、无法由本地中枢确认并访问的虚拟灯组暂不接入。已准入灯组的后续选路和断连恢复遵循统一规则。[物理灯组与虚拟灯组](https://github.com/XiaoMi/ha_xiaomi_home/wiki/Physical-light-group-and-virtual-light-group)
- 无法确认本地归属的设备保留为未接入候选，不能仅因为云端能够控制就自动桥接；灯组未准入不影响符合条件的单灯独立接入。

局域网直连限制在当前本地接口的连接网段，不通过 VPN 或远端地址扫描账号设备。中枢会话保留发现接口信息，不能只根据一个私有 IP 地址认定属于当前网络。

### 连接恢复与云端路径

设备通过首次本地确认后，准入记录归属于绑定的账号和家庭。已准入设备失去本地控制路径时，可以继续使用云端；普通断网、休眠恢复、接口或路由变化不撤销其准入。云端目录明确显示设备移出所选家庭后，立即停止派发新命令并取消状态订阅。

网络变化按连接故障处理：更新发现地址、重建失效连接、恢复订阅并同步状态。连接变化与设备归属分开，不为休眠时钟、默认路由变化或发送过程建立额外的权限失效机制。启动或重新登录同一账号后，校对完整家庭目录，恢复仍属绑定家庭的历史已准入设备，不要求逐设备重新取得本地证明；首次接入的新设备仍遵守前述准入条件。

账号和家庭归属、凭据有效性以及通信能力仍在派发前检查；目录校对尚未完成的冷启动不承诺控制可用。其它家庭始终不获得命令、动作或通知订阅；只读账号目录不会将它们加入控制名单。

## 能力、身份与 Matter 映射

### 识别与归一化

先检查设备类型，再按服务语义、属性或动作语义及访问权限识别能力。`on` 不能脱离所属服务解释，指示灯和保护设置也可能具有同名属性。读写、事件参数、数值范围、步长和枚举都在协议边界归一化；内部代码处理类型化值。

属性的 `access` 为空时不声明其可读写；属性若被动作或事件引用，仅按对应参数规则使用，不因此变成可单独读写的属性。缺少 MIoT-Spec 且没有已核对的型号适配时保留为未识别候选，不生成没有核心能力的桥接设备，也不直接断言设备本身无法控制。

| 差异 | 处理规则 |
| --- | --- |
| 不同亮度量程 | 使用设备的实际范围映射亮度；`yeelink.light.light3` 的物模型范围为 `1..65535`，不能固定按 `1..100` 发送。零亮度作为关闭处理，不向最小值为 1 的属性发送 0。 |
| 色温、颜色与风速 | 采用各设备实际上下限和步长，检查单位；颜色格式须有明确含义，缺少色彩能力时不声明。档位风速按离散档处理，不宣称支持任意百分比。 |
| 窗帘位置 | 内部统一为 0% 关闭、100% 打开；MIoT 与 Matter 两侧各自转换方向和量程。停止命令不能被替换为猜测位置。 |
| 数值照度与亮暗枚举 | 仅真实照度数值映射为 lux。`isa.magnet.dw2hl` 的 Weak／Strong 枚举不生成虚构照度，其门窗状态正常接入。 |
| 存在检测的中间状态 | 快检、未知或无效枚举保持未知，不折算为有人或无人。 |
| 人体运动事件 | 处理 `motion-detected` 和设备的有效无动作报告；核对秒／分钟单位。断线、安静一段时间或重启本身不构成无人报告。 |
| 空调数值与枚举 | `mcn02` 与 `mcn04` 分别映射服务及协议；整型目标温度按整型编码，不发送同值浮点数。外部切换到无法表示的模式时，不伪报成另一个模式。 |

参考：[亮度量程物模型](https://miot-spec.org/miot-spec-v2/instance?type=urn%3Amiot-spec-v2%3Adevice%3Alight%3A0000A001%3Ayeelink-light3%3A1%3A0000C802)、[门窗传感器物模型](https://miot-spec.org/miot-spec-v2/instance?type=urn%3Amiot-spec-v2%3Adevice%3Amagnet-sensor%3A0000A016%3Aisa-dw2hl%3A1)、[空调伴侣目标温度问题](https://github.com/XiaoMi/ha_xiaomi_home/pull/1111)。

### 身份与拓扑

物理设备以账号、家庭与父 DID 标识；桥接功能以父设备、服务实例和能力角色标识。角色指灯、某路负载或温控等功能，同一盏灯的亮度与色温属于同一功能，不分别分配设备身份。云端 `.s<siid>` 拆分条目合并回父 DID 的对应通道，不能与父设备服务重复创建 endpoint。名字、房间、IP、在线状态和当前控制路径均不参与身份计算。

多路开关按实际负载通道分别接入，每一路独立控制并保持稳定的功能身份。浴霸的照明、送风、换气、取暖分别具有稳定功能身份。一个功能在中枢、直连和云端之间切换时，身份和 endpoint 不变。只因网关主从变化或设备改名，不能重复创建 Apple Home 设备。

灯组和单灯分别按各自的 DID 与能力创建功能身份，满足准入条件后全部发布到 Apple Home。本轮不查询或推断灯组成员关系，也不隐藏、合并成员灯；灯组的存在、离线或移除均不改变单灯的展示与身份。

根 endpoint 为 0，Aggregator endpoint 为 1，真实功能从 endpoint 2 起递增分配，不为旧虚拟灯保留编号或标识。网桥和真实功能的对外唯一标识在新数据目录中生成并持久化；此后的重启和目录更新复用这些身份。已分配给真实功能的 endpoint 和对外标识不得用于另一个功能。

目录增量更新按一次完整、有效的变更发布到 Matter 拓扑；新增 endpoint 前先提交身份分配。设备短暂离线或用户注销米家账号时保留 endpoint，通过可达状态反映不可用；注销后重启仍恢复这些不可用的 endpoint。设备确实移出目标家庭，或成功登录另一账号后不再符合准入范围时，旧 endpoint 不再执行命令，并从有效拓扑移除，身份分配记录保留。重新接入同一身份时复用原分配。

| 核心能力 | Matter 表达 |
| --- | --- |
| 灯 | 根据能力选择 On/Off Light、Dimmable Light、Color Temperature Light 或 Extended Color Light，按实际功能声明特性。 |
| 负载通断 | 使用 On/Off Plug-in Unit 的执行端语义承载插座和继电器通道，保留通道名称；不使用只发送控制命令或按钮事件的设备类型。 |
| 窗帘 | Window Covering，提供升降位置及打开、关闭、停止。 |
| 空调／空调伴侣 | Thermostat 与所需 Fan Control；模式和设定范围取实际能力与标准表达的交集。没有当前室温来源时保留未知，不把设定温度作为室温。 |
| 风扇 | Fan 与 Fan Control，声明实际支持的风速和摇头能力。 |
| 传感器 | Temperature、Humidity、Light、Occupancy、Contact 等标准传感器语义；电量作为对应设备的附属能力。 |
| 扫地机器人 | Robotic Vacuum Cleaner，适配运行模式、清扫模式、运行状态和回充等核心命令，不伪装成电源开关。 |
| 浴霸 | 照明映射为灯，送风与换气映射为对应风机功能，取暖映射为仅供暖的温控功能。缺少当前温度时保持未知。关闭某个功能不主动关闭其它功能，设备自身的联动按回报同步。 |

对所声明的标准设备类型，必须实现其必需属性、命令、枚举和订阅行为。灯的 Move／Step／Stop 等协议操作与“导入厂商渐变配置”分别处理，不能以排除配置为由省略已声明类型的必需行为。Matter 侧的连续调整合并为有界的设备目标更新，停止后取消未下发的调整。

沿用固定的 `rs-matter` revision 和锁文件，补充相应业务处理器；生成的簇声明不能替代设备控制与状态实现。所有功能使用统一快照，协议版本号与订阅元数据留在 Matter 边界。[项目使用的 rs-matter](https://github.com/project-chip/rs-matter/tree/ca16b0ca3c3776272d5fa7aa3693501882ec41a3)

## 通信路径与命令语义

### 可用路径

中枢连接使用现有客户端身份、私钥、证书和小米 CA，校验服务端证书链并完成账号授权。按本地中枢协议使用发现的地址，不做 DNS 主机名匹配，但必须保留小米 CA 链验证；此例外不适用于云端 HTTP 或 MQTT。将中枢返回的设备在线、属性访问和推送能力分别保存，不把 MQTT 已连接等同于所有设备都可控。

中枢适配支持设备列表、属性读取、属性写入、动作及属性／事件通知。不同请求独立关联回复、超时和取消，重连后恢复订阅并刷新目录。[中枢接口与通知](https://github.com/XiaoMi/ha_xiaomi_home/blob/main/custom_components/xiaomi_home/miot/miot_mips.py)

设备直连支持目标 IP 设备的原生 MIoT 属性与动作，并对 `lumi.acpartner.mcn02` 提供传统 miIO 映射。使用已有账号目录提供的设备 token，校验其格式、数据包及身份，地址随发现更新。中枢存在时仍允许对它无法控制的设备使用直连；BLE／Mesh 设备不使用这条 IP 直连路径。[原生 MIoT 局域网协议](https://github.com/XiaoMi/ha_xiaomi_home/blob/main/custom_components/xiaomi_home/miot/miot_lan.py)

`mcn02` 的传统命令包括 `get_prop`、`set_power`、温度、模式和风速设置，以型号适配转换到统一能力。它与 `mcn04` 不能共用未经区分的原始命令映射。中枢是否能控制该型号以实际访问能力为准，不直接根据协议年代排除中枢路径。[python-miio 驱动](https://github.com/rytilahti/python-miio/blob/master/miio/integrations/lumi/acpartner/airconditioningcompanionMCN.py)、[miIO 与 MIoT 转换](https://github.com/al-one/hass-xiaomi-miot/blob/master/custom_components/xiaomi_miot/core/miio2miot_specs.py)

社区对 `mcn02` 固件 `2.1.8_0016` 有设备自身断网后回复成功而空调未动作的报告。因此验收区分接口回复与实际空调响应；本轮不要求伴侣自身断网仍工作。[相关问题](https://github.com/al-one/hass-xiaomi-miot/issues/2615)

云端复用已授权的 HTTP 入口执行属性与动作，使用云端 MQTT 订阅所选设备的属性和必要事件。云端控制与推送分别记录可用性；没有本地推送时可以使用云端通知，无需把该设备的控制也改为云端。

### 路由与执行结果

对已准入设备的具体操作，采用以下规则：

1. 发送前选路：按中枢、设备直连、小米云的顺序，选择已知可用、支持该操作且凭据有效的路径；没有可用路径时返回设备／功能不可用。
2. 调用后返回结果：每次设备写入或动作只调用选定路径一次，明确回复按已接受或具体错误处理。控制层不自动重试或换路补发，后续新命令根据最新连接和能力信息重新选路。
3. 超时后同步状态：命令已发送但因超时或断线未收到明确回复时，报告结果不明确，通过后续有效报告或受限回读同步状态；不以回读未达目标为由补发命令。

派发边界是应用将一次操作交给网络客户端：在此之前统一检查准入、账号和路径；交付之后不再反复检查业务授权，也不尝试撤回操作。注销、设备移除或新目标值只影响尚未派发的操作。取消已交付请求可以停止调用方等待，不保证阻止设备执行；网络客户端仍按正常协议处理回复、断连和超时。控制请求不进入断线后的重放队列。

路径选择与控制不自动补发的做法参考小米官方集成的[属性写入与动作路由](https://github.com/XiaoMi/ha_xiaomi_home/blob/1a5f890cbe08d14ec7252196bd925a57090e8774/custom_components/xiaomi_home/miot/miot_client.py#L638-L831)。连接恢复和状态读取的重试另由同步流程处理，不重新执行控制命令。

同一物理设备的操作串行，避免多个通道或空调组合设置互相覆盖；不同设备可独立推进。待发送的同属性目标值可以合并，动作不能被合并成状态值，也不持久化到重启后的执行队列。

网络接受、设备报告的状态和物理动作完成是不同结果。协议确认可以表示请求已被接受，但不能直接把所有目标值当成已实现状态。单条控制命令的总时限为 10 秒，包含排队、选路和等待回复；本地单次控制最多 3 秒，云端单次控制最多 5 秒，均服从剩余总时限。认证和目录 HTTP 保持已有 30 秒超时。请求支持取消，后续状态同步不延长本次请求。用户已有更新命令时，取消旧命令尚未发送且已被替代的设置或转换步骤。

## 状态同步、离线与恢复

状态须区分当前确认值、最后已知值和未知，来源与更新时间用于诊断。重启前的缓存须经有效读取或报告重新确认，晚到的旧查询不能覆盖新报告。未知或失效状态不能伪装为零、关闭、无人或门已关；Matter 侧使用标准未知或不可用表达。

按本地推送、云端推送的顺序为设备选择一个推送来源，切换时取消旧订阅并建立新订阅。[上游订阅切换](https://github.com/XiaoMi/ha_xiaomi_home/blob/1a5f890cbe08d14ec7252196bd925a57090e8774/custom_components/xiaomi_home/miot/miot_client.py#L990-L1027) 连接建立后补齐初始状态；有正常推送的属性不叠加周期性读取，缺少推送时有限轮询，命令后按需补读。只读取已识别的核心属性，限制并发和频率，并遵守设备的上报周期与调用限制。

根据中枢或设备的在线信息、有效报告和读取结果判断可用性，不能仅凭传感器长时间无变化或缺少云端在线字段判定离线。本地故障但获准使用的云端路径仍可用时，保留相应控制能力；无可用路径或关键状态无法确认时，在对应功能上体现不可用。单个可选读数失败不影响其它已确认功能。

连接或读取失败后逐步延长重试间隔，成功后恢复正常调度。重连或切换来源时恢复订阅，按需补齐缺失或失效的状态；已确认的有效状态不因来源切换而统一失效。订阅目标变化合并为最新设备集合，顺序应用差异，不因调用者停止等待或重叠更新而关闭健康连接。启动和重连不重放历史动作事件；退出时取消排队工作、网络等待和重连任务。

## 持久化与凭据维护

继续使用 `state.db` 保存小米认证信息、Matter 配对数据和下列运行数据，沿用现有事务、文件权限和敏感信息保护约定。使用新数据目录按当前结构初始化；不兼容或损坏的已有数据库明确报错，不自动迁移或覆盖。

| 数据 | 保存内容与生命周期 |
| --- | --- |
| 目标家庭 | 绑定的账号与家庭；与本次网络会话的验证结果分开。 |
| 设备及本地归属 | 设备目录、连接所需信息和历史归属依据。 |
| 物模型 | 已获取且供目录恢复和能力识别使用的 MIoT-Spec；固定型号适配保留在代码中。 |
| 功能身份 | 网桥与真实功能的稳定标识及 endpoint 分配。 |
| 状态 | 最后确认状态及其来源、更新时间。 |

新分配的身份先持久化再发布到 Matter，频繁状态变化按设备属性合并写入，不另外建立状态缓存溢出后的全量扫描机制。取消设备准入时立即停止派发新命令，不以历史归属记录写入成功为前提。

长期运行沿用现有令牌刷新和证书续期策略，更新成功后及时持久化并用于后续通信；新证书用于重建中枢会话并恢复订阅。临时失败保留仍有效的旧凭据，不影响其它有效路径。

并发认证操作不能让过时的结果覆盖新凭据或恢复已注销的凭据。运行中的网桥观察到注销或换账号后，停止派发旧账号的新操作、取消状态订阅并关闭对应会话；已交付操作可能完成，不提供跨进程注销与网络发送之间的原子保证。注销时清除账号凭据和关联设备 token，保留 Matter 配对、已发布设备的拓扑与身份分配，以及不含凭据的家庭绑定和设备记录；Apple Home 中已有设备继续显示并标记为不可用。重新登录同一账号后，校对家庭目录并同步设备状态，再按原身份恢复；成功登录另一账号时按前述拓扑规则移除旧账号设备。

## 终端与诊断

维持现有数据目录、Matter 端口、配对窗口和认证命令用法。`on`、`off`、`status` 均要求指定设备／功能 ID；缺少 ID 时显示用法，不默认选择任何设备。

| 交互命令 | 行为 |
| --- | --- |
| `help` | 显示命令用法和米家认证状态。 |
| `devices` | 显示本轮目录中的设备／功能标识、名称、类型、接入状态和可用路径。 |
| `status <id>` | 读取该功能的当前快照、未知／最后已知状态及来源。 |
| `on <id>`、`off <id>` | 对具备电源能力的指定功能执行明确目标操作。 |
| `set <id> <property> <value>` | 设置统一核心属性，例如亮度、色温、目标温度、位置和模式；名称、单位及合法值由帮助列出。 |
| `action <id> <action>` | 执行该功能支持的动作，例如窗帘停止、开始清扫或回充。 |
| `refresh` | 请求重新发现并同步目录和核心状态，仍遵守同一准入、队列和限速规则。 |

命令不暴露任意 DID／SIID／PIID 写入入口，也不允许引用未准入设备绕过范围检查。参数、属性和能力不匹配时在入口报错，不产生网络操作。

状态与命令结果继续使用英文普通文本写标准输出，后台诊断使用现有日志系统写标准错误。日志记录设备／功能标识、操作、实际路径、失败阶段和安全的协议状态码，区分未发现、身份未验证、能力不支持、路径不可用及结果不明确。相同状态不连续刷屏。

## 验收标准

自动化验证使用隔离的数据目录和可控的协议边界，覆盖以下实际行为，不依赖真实家庭设备执行写入：

- 完整分页、重复游标及部分失败；多接口和同家庭多个中枢去重；家庭自动绑定、归属冲突和不同家庭排除；新设备不能通过云端绕过首次本地确认，历史已准入设备不因普通网络变化而被撤销。
- 已选类型的核心能力、明确排除的型号／类别、父设备与拆分通道去重、复合功能身份；只有附带状态或配置的设备不生成控制类桥接设备，有效的只读传感器与事件仍可接入，权限为空的属性不被当作可读写属性。
- 灯组须由已认证的本地主中枢报告且具备本地访问能力，仅云端存在的虚拟灯组不准入；灯组与单灯满足各自准入条件后同时发布，不查询或推断成员关系；灯组的存在、离线或移除不隐藏单灯，也不改变单灯身份。
- 亮度量程、色温与位置方向、枚举与整数温度、数值照度与亮暗枚举区分、运动事件和检测中间状态；无数据不生成有效零值。
- 中枢、直连与云端的派发前检查、路径选择及无路径报错；已交付命令不因后续业务授权变化被改判为未发送；控制调用报错或超时后不自动重试或换路补发，后续状态读取不触发控制重放；旧命令或慢查询不覆盖新状态。
- 初始查询与推送并发、不同来源切换、按需补读和有限轮询；缓存须重新确认，传感器无变化不被误判离线，可选读数失败不影响其它功能；断连后恢复订阅和必要状态且不重放历史动作，所有网络任务能被退出取消。
- 对应 Matter 类型的命令、属性、特性和通知；终端与 Matter 共享状态；新增、移出、重启后 endpoint 与唯一标识保持正确；取消准入立即停止新命令派发，不等待历史归属记录保存。
- 虚拟灯不再注册为设备或 endpoint；零设备时网桥继续运行；终端设备命令缺少 ID 时不执行操作。
- 新数据目录按当前结构初始化，真实功能从 endpoint 2 起分配，重启后复用配对和身份；旧版、未知版本或损坏的数据库被明确拒绝且不被覆盖；并发认证更新不覆盖新凭据或恢复已注销凭据，注销或换账号后停止旧账号操作；凭据不出现在输出中。
- 注销清除凭据和设备 token、停止控制与订阅，同时保留已发布设备并标记不可用，注销后重启仍保留；同账号重新登录并核对归属与状态后复用原设备，成功登录另一账号后移除旧账号设备。
- 保留认证及网桥进程的回归覆盖，将原虚拟灯相关验证改为设备服务及 Matter 映射验证，完成仓库现有的 `cargo test --locked` 和 `cargo clippy --locked --all-targets -- -D warnings` 检查。

真实环境以每种所选类型的代表设备覆盖下表，不将接口声明或模拟响应当作物理执行证据。同类型所有符合准入条件的目标设备都应被目录处理；不同能力或协议变体分别记录支持或失败原因，不能用一个代表型号的结果宣称所有型号已通过。

| 场景 | 通过条件 |
| --- | --- |
| Apple Home 接入 | 已选真实设备功能按适当类型出现，可读取状态；虚拟灯、推窗器、按钮、旋钮及其它延后设备不出现，其他家庭没有控制或订阅请求。 |
| 灯、开关和插座 | 验证实际负载通断、灯亮度和支持的色温／颜色、多路独立控制；米家或实体操作后的状态能同步。 |
| 空调与风扇 | 两种空调伴侣分别验证实际空调响应、模式、目标温度和风速；风扇验证开关、风速及摇头。 |
| 窗帘 | 验证打开、关闭、中间位置与停止，方向正确，实体或米家操作后位置反馈一致。 |
| 传感器 | 验证温湿度、真实照度、运动、有人／无人和门窗状态变化；不生成虚构读数，不把断连解释为无人或关门。 |
| 扫地机器人 | 验证开始、停止、回充、清扫类型和运行状态；超时恢复不重复启动动作。 |
| 浴霸 | 验证照明、送风、换气和取暖功能，状态反映设备自身联动，不因一个功能关闭而主动关闭其它功能。 |
| 路径与网络 | 健康本地路径优先；受控制造本地不可用后可按规则走云端。网络变化后重建连接并恢复状态，已准入设备保留绑定家庭资格，新设备仍须首次本地确认。 |
| 重启与恢复 | 不重复添加设备，复用配对与身份；重新确认状态后继续同步。注销后重启仍保留不可用设备，重新登录同一账号并核对归属后恢复。单个设备或云端暂时失败不终止其它可用链路。 |

状态同步和恢复需验证 Apple Home 的实际显示与订阅行为；设备固件仍需联网不构成失败。选用可观察的代表设备完成物理动作验证，验收不对全屋插座、空调或设备批量执行写入。

更新 `docs/running.md` 和 README，替换虚拟灯演示和旧终端命令说明，说明切换新版本时使用新数据目录、重新登录和配对的步骤，以及家庭自动识别与绑定、设备范围、各类核心功能、路径与状态诊断、重启及恢复方式；明确灯组与单灯同时显示，以及注销、重新登录和换账号时已有设备的处理规则。
