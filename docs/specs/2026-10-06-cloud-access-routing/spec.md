# 云端接入与统一选路

## 目标与范围

为已有插座补齐米家云端属性读取、写入和主动通知。在保持本地优先的同时，当本地中枢接口不可用而云端仍能服务设备时，继续提供控制与状态同步；云端故障不能阻断有效的本地路径。

直接动机是[已知限制](../../known-limitations.md)中的主中枢轮换问题：米家 App 已恢复使用时，中枢本地接口仍可能持续无响应。MQTT 已连接不代表业务接口正常，米家 App 正常也不证明 MiGate 使用的云端接口正常。云端可能仍依赖物理网关，不能预设网关断电后所有设备都能通过云端工作。

本轮范围：

- 沿用当前中国大陆服务区、单账号绑定一个米家自有家庭的边界。
- 为已加入网桥的受支持插座提供云端读写和主动通知，保留多通道独立状态与命令顺序。
- 中枢统一管理本地路径的降级与恢复；控制与通知共用本地、云端优先级，按各自就绪条件完成切换。
- 支持本地故障期间使用原数据目录重启，由云端恢复已有设备。
- 保留动态加入、删除、重新加入、稳定身份、端点、名称与 Apple Home 配对。
- 运行与验收范围继续为 macOS / Apple Silicon，保持 Rust 单包结构。

不增加新设备品类、IP 局域网直连、云端独立发现并接入新设备、远程家庭或多家庭管理、管理界面、常驻服务安装及 Linux 适配。既有 Matter 插座符合性限制保持原有说明，不扩大认证或兼容性声明。

本设计延续[多设备与多路插座桥接](../2026-10-04-multi-device-channel-bridge/spec.md)的设备模型与拓扑，调整其中仅依赖本地访问条件的可用性判断，并补充跨路径的状态处理规则。

## 现有逻辑的复用与简化

“新设备加入”和“已有设备恢复”使用两个明确分支，不新增设备准入机制。

| 情况 | 行为 |
| --- | --- |
| 新设备加入 | 沿用家庭成员过滤、能力解析、本地型号与实例描述匹配、属性与推送访问能力检查，再事务保存设备描述、身份、通道和名称。无需新增测试写入，也不把全部通道首读成功作为加入条件。 |
| 已有设备恢复 | 复用已保存的有效描述、身份和通道，按当前可用路径恢复服务；本地信息暂不可用不再阻止云端恢复。 |
| 已删除设备重新出现 | 已保存身份只用于复用编号与名称；仍经现有加入流程重新发布，不能凭云端目录自动恢复已删除设备。 |
| 描述发生变化 | 沿用功能兼容检查；不能把原有端点悄悄变为其他功能。本地失联本身不触发重新加载描述或重新分配身份。 |

现有 published 记录、账号与家庭范围、已保存描述足以表达恢复依据，不新增“曾经本地确认”的字段、证明记录或独立存储表。已确认删除的设备保持未发布；正常离线、路径变化和凭据更新不改变发布状态。

当前实现把本地信息缺失直接用于已有设备的不可用判断。本轮将设备创建与当前路径可用性分开，使已有设备无需再次满足首次加入时的本地条件。必要调整集中于接入协调与可用性计算，不重建身份管理或能力解析体系。

## 模块边界与数据流

| 单元 | 职责 |
| --- | --- |
| device | 保留物理设备、通道、状态快照、可用性、命令队列和变化通知。不了解本地、云端、MQTT、家庭或选路。 |
| xiaomi/adapter | 米家适配层，管理共享中枢优先级、各设备现有访问条件、控制选路、通知来源、消息有效期、补读与凭据协调；将有效观察应用到统一设备状态。 |
| xiaomi/central | 沿用本地 MIPS 请求、订阅与连接管理，提供请求结果、发送阶段和设备观察。 |
| xiaomi/cloud | 扩展既有 HTTP 客户端完成属性读写，增加云端 MQTT 通知传输；保留目录、OAuth 与响应解析职责。 |
| storage | 复用设备描述、家庭范围、发布状态、身份、名称、凭据及 Matter 存储。 |
| matter、终端、runtime | 继续通过通用设备接口读状态和发命令，组装并管理任务；终端额外呈现米家适配层的选路诊断。 |

### 适配层内部职责

本轮将现有 src/xiaomi/source、XiaomiSource 分别重命名为 src/xiaomi/adapter、XiaomiAdapter，模块导出与调用处同步更新，本文统一称米家适配层。XiaomiAdapter 负责组装和驱动；适配层负责米家协议与通用设备模型之间的双向适配，路径和状态协调由其内部完成。扩展集中于三个职责边界：

| 职责 | 管理内容与输出 |
| --- | --- |
| 设备成员与生命周期 | 维护当前家庭成员、已发布设备及描述，执行已有加入、兼容更新和删除流程，管理设备任务的创建与结束。已有设备的运行时可用性交给路径判断，不重复执行首次加入条件。 |
| 路径选择与恢复 | 维护共享本地降级状态、恢复时间和各设备访问条件；按共同优先级选择请求路径与通知来源，协调必要订阅的交接，计算总体可用性。云端同步、凭据刷新及传输重连仍复用对应任务。 |
| 观察结果处理 | 统一处理属性通知、读取结果和写入受理，检查设备、绑定、来源有效期及观察顺序，再决定状态更新和命令完成；补读需求在此统一合并后交由路径选择执行。 |

各职责通过明确入口更新自己管理的状态。Context 保留共享资源及状态的持有关系，不继续集中设备发布、路径恢复和属性时序处理的全部逻辑。按职责整理现有实现即可，不要求为每项职责建立新架构层、通用后端接口或消息总线。协议编解码、TLS、HTTP 请求和 MQTT 连接管理继续留在 central、cloud 等对应模块。

Matter 或终端提交命令后，进入原有通道队列；xiaomi/adapter 在实际发送前选择路径，由相应传输执行。响应与通知回到适配层，完成有效性与时序处理后，再更新同一份设备状态。传输层不绕过适配层直接修改设备状态。

每台设备的路径条件和订阅关系只存在于米家适配层。它们不构成每台设备独立的故障恢复状态机，也不进入持久化的通用设备描述。多个通道继续共享物理设备可用性，同时保留独立状态和命令队列。

### 任务生命周期与调度

- 设备记录与每通道命令消费者继续随设备生命周期存在；补读需求和观察顺序也按设备生命周期管理，路径切换时保留，不再随本地 Session 销毁。每个设备保持一份统一状态，每通道保留一个命令消费者及一份合并的补读管理，不按本地、云端复制。
- 请求与订阅仍属于相应连接或操作的有效期。本地断开只清理该连接的工作、撤销本地候选并重新计算设备可用性，不直接把全部设备标为不可用，也不结束仍有效的云端任务。在途写入按原操作的结果结束，不随切换重新提交。设备删除或整个适配层停止时，统一结束该范围内的所有路径任务。
- 补读统一去重、合并和选路，各路径按自身协议节奏执行。本地保留现有批次调度，云端慢读取不加入本地批次的共同等待，也不设置等待所有路径完成的全局轮次屏障。一个路径的慢请求不阻止其他路径已就绪的补读和其他通道的命令；同一通道的命令仍遵守 FIFO。

复用现有队列、订阅确认、有界重试、补读合并与任务取消机制。新增协调状态限定于路径选择与恢复所需状态、通知来源及有效期、每通道的观察计数和生效补读标识，不保存消息历史。观察计数独立于设备状态修订号，因为同值通知也会影响迟到结果的有效性。

若本地与云端确有可复用的 MQTT/TLS 代码，只抽取共同协议部分；不建立通用路由插件框架。

## 云端链路与可用性依据

云端连接在网络和凭据允许时提前建立，不等本地故障才启动。属性读写使用 HTTP，主动通知使用 MQTT；两者沿用各自的请求、连接和订阅机制，由适配层按共同优先级使用，不额外维护混合组合的运行模式或恢复策略。

| 能力 | 协议与边界 |
| --- | --- |
| 属性读取 | 使用官方属性读取接口，按 DID、SIID、PIID 关联各项结果。读取结果是云端可提供的缓存观察，不视为设备实时响应的证明。 |
| 属性写入 | 使用官方属性写入接口，仅写入当前设备描述中已支持的布尔开关属性；同时检查响应封装、目标关联及单项业务码。业务成功码 0 或 1 表示受理。 |
| 属性通知 | 使用云端 MQTT 属性通知，校验主题、DID、属性绑定及布尔类型；只分发给当前仍加入网桥的设备。 |
| 在线状态 | 使用完整云端设备信息与适用的在线状态通知。部分设备没有对应在线推送时，沿用设备信息更新，不能把推送缺失当作离线。 |

云端身份沿用现有 OAuth 应用与规范化客户端标识；访问令牌用于云端 HTTP 与 MQTT，本地客户端证书只负责本地中枢认证。云端通知连接使用服务端 TLS 验证。

同一账号、绑定家庭和已发布设备集合始终限制访问范围。首次云端恢复须取得当前绑定家庭的完整成员关系和相应设备信息；静态缓存不能单独证明当前在线或云端访问有效。运行中云端暂时故障、分页失败或部分响应不能用于删除设备，也不能推翻仍有效的本地路径。

路径可用性是发起请求的依据，不是物理动作已经完成的证明。沿用设备在线与访问条件，再结合凭据、连接和实际请求结果选择路径；不能仅凭 MQTT 在线、目录读取成功或缓存属性读取成功，声称设备真实控制与通知已通过验证。

设备总体可用性由可用控制路径决定。通知暂不可用时单独呈现“状态同步受限”，不阻止仍有路径的明确 On、Off 命令。状态未知时 Toggle 仍失败；暂不可用时可显示最近内存状态，但不能宣称它代表设备当前实际值。没有可用控制路径时，有效通知仍可更新内存状态，但不恢复设备可用性，Matter Reachable 仍为 false。

## 路径优先级与失败处理

### 正常选择

控制与通知共用同一优先级：正常时本地优先，本地故障后云端优先，本地恢复后返回本地优先。各设备沿用自己的在线与访问条件，控制检查请求路径是否可用，通知检查必要订阅是否就绪；一方无需等待另一方就绪。

共享中枢的业务降级仅降低本地优先级，不宣告全部物理设备离线，也不完全禁用仍可能有效的本地路径。优先路径不可用时使用另一条满足条件的路径；例如云端不可用而本地仍连接、设备访问条件满足时，允许新的命令尝试本地。云端失败也须更新候选条件，恢复复用既有同步与凭据维护，不新增独立的 HTTP 健康检查或每设备探测循环。

云端失败按现有错误分类处理：

- HTTP 网络错误、超时、408、429 或 5xx 结束当前请求，将该账号的云端 HTTP 控制与读取暂时移出候选，并合并到既有云端同步退避。后续控制与读取使用仍有效的本地路径；没有可用控制路径时，新命令报告不可用，不反复尝试尚未恢复的云端 HTTP。此类失败不撤销正常云端 MQTT 的通知资格，通知仍按共同优先级及自身连接、订阅、认证和设备访问条件选择来源。暂停期间继续接纳生效来源的有效通知；属性通知或在线通知到达均不解除账号的 HTTP 暂停。
- 认证拒绝交给统一凭据维护；拒绝的令牌不再用于新操作，刷新失败或明确需要登录时保持暂停。
- 明确的设备离线或设备访问权限错误只更新该设备的云端访问条件；其他设备不受影响。属性参数错误、其他业务拒绝或单次内容解析失败仅结束当前请求，不推断整个云端服务或设备离线。
- HTTP 临时失败后，同一账号、绑定家庭的完整目录与设备信息同步成功，即可按更新的信息恢复云端 HTTP 候选资格，并重新按共同优先级选择；不额外读取属性或测试写入作为恢复门槛。
- 设备离线或访问条件失效由后续完整设备信息、适用的在线通知及访问条件更新解除，不能由缓存属性值覆盖。认证暂停由成功更新且未再次遭拒的凭据解除。

同步成功只恢复尝试云端 HTTP 路径的资格，不证明属性接口或设备实时控制已经恢复；后续实际请求仍按结果处理。通知连接与订阅继续沿用各自的重连和有界重试，保留通知不新增运行模式或恢复任务。

### 触发范围

| 观察 | 对选路的影响 |
| --- | --- |
| 本地共享连接断开、TLS/MQTT 传输失效 | 相关设备立即失去该本地候选路径，使用各自仍可用的云端路径；传输层继续恢复连接。 |
| 已发送的本地业务请求等待有效应答超时 | 触发共享本地优先级降级，后续尚未发送的命令与通知来源均优先云端。 |
| 中枢明确返回设备离线或其他业务拒绝 | 当前请求失败；按明确的设备信息更新其访问条件，不据此降级整个中枢。业务拒绝本身也不一概等同设备离线。 |
| 请求未发送便排队超时、队列满、调用取消或设备删除 | 当前请求结束，不作为中枢业务无响应的证据。 |
| 完整收到但内容不合法的业务消息 | 沿用协议边界处理，仅丢弃消息或使关联请求失败；不因单条坏消息重建共享连接。无法关联的损坏应答仍可能使原请求等到超时。 |

保留“本地等待超时”与“收到中枢返回的超时错误码”的区别。请求层应能说明写入是否尚未发送、已得到明确业务结果，或可能已经发送但结果不明；不能从一个合并后的 Timeout 或 SendFailed 值推断安全重试。

本轮接受单台设备静默无应答也可能导致共享本地优先级下降。其代价是其他设备暂时优先云端；不增加跨设备故障确认流程，也不将这一策略表述为已经定位到共享中枢故障。

### 命令生命周期

- 保留每通道单消费者与 FIFO，在实际执行时将 Toggle 解析为绝对目标；不同通道可并发。
- 路径切换时，只要仍有可用控制路径，就不产生中间不可用状态，队列与消费者继续工作。全部控制路径不可用时，沿用现有规则结束尚未执行的排队命令，不积压到恢复后执行；保留队列生命周期不等于保留其中已经失败的命令。
- 一次命令只向选定路径提交一次写入。已发送请求不因选路改变、认证刷新、连接恢复或调用者停止等待而重新发送。
- 明确受理返回成功，拒绝、超时及结果不明如实返回失败。成功表示服务受理，不增加动作确认、自动回滚或写后定时核验。
- 当前在途命令仍由原路径的结果完成，后续命令等待它完成后再按新的选择发送；超时结束后的迟到应答不能复活命令。
- 超时不能撤回远端可能已经执行的写入。MiGate 保证提交顺序和不自动重放，不承诺不同服务之间的物理执行严格有序；后续有效状态观察仍用于修正显示。
- 删除设备、变更为不兼容的属性绑定或结束所属任务后，旧命令结果不得恢复设备或改写新的绑定。

## 本地恢复检查

健康且空闲时不新增探测。现有请求或连接事件暴露故障后，才进入恢复处理。

| 情况 | 调度与行为 |
| --- | --- |
| MQTT 仍连接，但本地业务已降级 | 首次降级后等待 1 分钟开始只读恢复检查；检查未恢复时，从该轮结束再等待 5 分钟。 |
| 多个设备或请求连续失败 | 合并为同一个共享恢复任务；同一时间最多一轮，重复失败既不额外启动检查，也不重置已安排的时间。 |
| 共享连接断开 | 结束该连接上的业务恢复检查，由现有传输重连负责。 |
| 新主中枢出现或重新连接成功 | 复用正常的设备列表刷新，成功后即可提前恢复本地优先，无需等慢速检查时间。 |

每次恢复检查只读取当前中枢的设备列表。当前有效请求返回合法的成功结果后，更新设备访问条件并恢复共享本地优先级，无需额外选择设备或读取属性作为恢复门槛。正常重连后的列表刷新也使用同一规则；MQTT 重连本身、旧连接或已结束请求的迟到结果不能触发恢复。

列表成功作为共享本地接口恢复的信号，各设备仍按列表中的在线与访问条件选路。通知来源仍须满足自己的订阅条件；正常属性补读继续负责更新状态。后续实际读写再次无应答时，按既有规则重新降级。静默恢复可能等待最多 5 分钟才开始下一次检查，另加列表请求耗时。

恢复调度接管降级期间的本地业务恢复工作，合并尚未发送的列表、属性重试和重复触发，避免旧的短周期重试在旁边继续探测。新主中枢、重连及明确设备变化带来的必要刷新仍按事件处理；设备事件不为每台设备创建新的共享恢复循环。业务降级本身不强制断开仍在工作的 MQTT 连接。

## 通知来源与统一状态

### 来源选择与切换

每个物理设备在适配层只有一个生效的属性通知来源，按与控制相同的优先级准备和选择来源。新来源尚未就绪时保留仍有效的旧来源，已经可用的控制不等待通知切换。访问能力或订阅就绪时间不同可以自然产生混合状态，不为维持这种状态增加独立选路模式、恢复任务或持续探测。

切换遵守以下规则：

1. 准备新来源的全部必要属性订阅。多路设备包括各路开关与用于触发读取的总控属性；部分订阅成功不能视为整个设备准备完成。
2. MQTT SUBACK 成功才表示订阅建立，提交订阅请求或 MQTT 已连接都不够。新来源未准备完成前，保留仍有效的旧来源；准备失败按有界订阅重试处理。
3. 新来源准备完成后，统一变更该设备的生效来源，撤销旧来源的状态更新资格，并释放不再需要的旧属性订阅。新旧订阅短暂并存时也只有一个来源可以更新状态。
4. 为每次来源生效、连接重建与设备生命周期保留可区分的有效期。即使经历本地→云端→本地，旧连接及接收时已关联旧有效期的消息或回调也不能重新获得资格；不只比较来源名字。有效期用于隔离能够辨认的旧工作，不能推断服务端消息的实际生成时间。
5. 切换后通过统一入口刷新设备状态。两个来源都不可用时保留最近状态并报告同步受限，等待连接、订阅或设备访问条件恢复。

云端在线状态通知与属性来源不同：即使当前属性由本地提供，云端仍可维护自己的设备在线信息。来自不同路径的在线信息只更新各自访问条件，云端离线不能直接使仍可本地控制的设备不可用。

订阅建立不能证明真实外部变化已能推送。健康设备长时间没有属性变化是正常情况，不能仅因静默判定通知失败，也不使用持续属性轮询代替主动通知。

### 统一状态刷新

设备加入、恢复、通知来源切换和设备描述中声明的刷新事件，共用一个状态刷新入口，按设备的通道集合请求读取。普通通道通知直接更新该通道，写入受理沿用既定状态处理，不因此刷新整台设备。

- 按通道合并读取需求。未发送的请求不重复排队；在途读取再次收到刷新触发时，该旧读取失去更新资格，并最多保留一次后续读取。重复触发沿用现有合并与退避规则，不增加独立任务或队列。
- 实际发送前按共同路径优先级选择可用路径，不等待通知切换。失败结束本次请求，后续沿用现有有界重试，在下次发送前重新选路，不叠加另一套重试流程。本地降级期间不绕过共享恢复检查的慢速节奏。
- 读取结果按通道独立应用，无需等待整台设备全部读完；是否仍有效由下述统一观察规则判断。

cuco.plug.cp7pd 继续仅暴露 outlet_1、outlet_2 和 usb 三路。生效来源的总控通知只触发上述设备刷新，读取三个通道各自的开关属性；不把总控值复制给各通道，也不把总控暴露为第四个控制端点。

刷新用于弥补状态缺口，允许云端读取更新未知或已有状态。云端缓存即使没有与并发通知冲突，也可能比设备实际状态或此前观察更旧。本轮接受由此带来的旧值或回跳，随后由有效通知或读取纠正；不把补读成功称为已确认物理状态，不承诺无新观察时的固定纠正期限。

不确定写入失败后不安排自动补写或专门的写后确认；已经需要的来源切换刷新可以正常执行。设备列表与云端目录同步只更新访问条件，开关状态仍通过属性读取和有效通知更新。

### 观察顺序与迟到结果

适配层按通道管理当前观察顺序，规则如下：

- 仅接纳当前生效来源、当前设备与属性绑定的有效通知；旧连接、已失效来源、已删除设备的观察不进入状态。
- 同值通知不重复递增设备状态修订或向 Matter 报告，但仍算一次有效观察，用于防止在途读取和成功应答覆盖它。
- 读取发起后，若该通道已有有效通知或成功写入，则该读取的迟到结果不再覆盖状态。来源切换、绑定更新或设备删除也使旧读取失效。
- 写入发送后若已经收到该通道的有效通知，迟到成功应答仍完成命令、推进 FIFO，但不再把目标值写回快照。没有这类通知时，继续沿用受理后的乐观更新。
- 当前生效来源内的合法通知按接收顺序应用。不假定本地与云端拥有共同事件序号或可信的全局时间，也不声称可以识别所有同一来源内部的迟到报告。同一 MQTT 连接取消并重新订阅后才首次抵达、且没有可验证旧有效期信息的服务端报告，也受此限制。

上述观察顺序与有效期属于 xiaomi/adapter；通用设备模型仅接收已决定应用的状态和命令完成结果，不因此增加来源或路径字段。命令完成接口需支持成功受理并保留当前快照，是否应用目标值由适配层决定；接口不接收米家协议或选路信息。未收到写入后的有效通知时，仍保留现有受理后的乐观更新。

## 启动、成员同步与凭据维护

启动时先恢复同一账号、绑定家庭中仍已发布的拓扑、身份与名称，各通道值从未知开始。设备的访问条件满足后即可恢复控制，状态读取异步进行；不要求所有通道先读成功。未发布或已经删除的记录不能因为重启重新出现。

已有设备可以在本地中枢尚未发现、认证失败或接口不可用期间，由云端恢复。新设备仍复用原有本地支持确认与发布流程。中枢换主、路径变化、令牌刷新及证书续期均不改变设备 DID、功能键、endpoint、UniqueID、名称或 Matter 配对。

当前家庭成员关系仍按既有触发与每 5 分钟的完整同步更新。只有同一账号和绑定家庭的完整成功结果能确认删除；部分页、网络错误、认证拒绝和其他家庭响应不能被解释为空家庭。删除统一结束本地与云端订阅、补读和命令任务，迟到回调不能重新发布设备。

凭据维护复用现有 AuthService、持久化与刷新规则，将目录同步中的刷新协调供云端读写和通知共用：

- 在现有令牌刷新时间到达时维护凭据；并发的认证拒绝合并为同一次刷新，迟到旧令牌错误不能覆盖已更新凭据。
- 安全读取可以在受控的刷新成功后重新尝试；写入遇到认证错误仍结束本次命令，更新后的凭据服务后续命令。
- 凭据成功保存后，HTTP 使用新令牌，云端 MQTT 更新认证并重新建立必要订阅。正在执行的写入不因换令牌重新创建。
- 云端临时网络故障按现有恢复机制重试。明确需要重新登录时暂停依赖该凭据的云端操作，并保留提示；刷新不能陷入无限认证重试。
- 云端认证失败不阻断同一账号缓存、有效证书和有效访问条件支持的本地控制。证书维护失败也不阻断仍有效的云端路径；本地认证仍按真实证书有效性执行。
- 慢目录请求、证书请求或云端订阅恢复不占用本地命令通道，不以认证检查的整体结论统一关闭所有路径。

独立 auth login、auth check、auth logout 沿用现有入口与数据目录互斥；需要重新登录时停止网桥，完成登录后使用原目录重启，不增加跨进程或运行中的交互登录流程。账号发生变化时不能用新账号访问原账号的设备缓存。

不持久化当前开关值、在线状态、选中路径、恢复计时器或未完成写入。存储失败沿用保留数据并停止服务的规则，不以创建新实例、重置身份或清空配对作为恢复手段。

## 时限与可观察性

不增加用户可调的超时或选路配置。时限采用已有实现及官方请求边界；恢复检查频率使用本设计确认的慢速调度。

| 项目 | 时限或调度 |
| --- | --- |
| 本地直接属性读写、中枢设备列表 | 单次请求 10 秒，沿用现有请求层行为。 |
| 本地批次属性刷新 | 单次 6 秒；正常刷新沿用每轮每设备一个属性、跨设备并发与 200 毫秒轮间隔。降级期间的重试由共享恢复调度合并。 |
| 云端属性读取 | 单次 HTTP 请求 30 秒；失败不能伪造属性值。 |
| 云端属性写入 | 单次 HTTP 请求 15 秒；不自动重发。 |
| 通知订阅建立 | 单次确认等待上限 10 秒；首次失败后最多追加 3 次。保留成功项，本地重试间隔沿用 0.1 秒，云端使用 1 秒；耗尽后等待连接、设备信息或来源选择条件更新再尝试。 |
| 本地业务恢复检查 | 首次降级后 1 分钟；后续从前轮结束起间隔 5 分钟。每次只读取设备列表，使用其 10 秒请求时限。 |
| 本地传输重连 | 沿用 6、12、24、48、60 秒退避，成功连接后重置；同一家庭新主中枢候选可提前唤醒。 |
| 云端 MQTT 重连 | 参考官方云端 10 秒起、逐次翻倍、上限 600 秒的退避，成功连接后重置；不影响有效本地路径。 |
| 云端目录和凭据的临时失败 | 沿用现有 1 至 30 秒退避及成功后的正常同步节奏。 |
| 家庭成员同步 | 沿用每 5 分钟及已有事件触发。 |

故障确认后立即更新后续选路，不额外设置 30 秒或 60 秒切换等待。上述网络请求时限不等于端到端接管时限，也不恢复旧的“通道排队与应答合计固定期限”。尚未发送便在请求层超时的工作不能继续发送。

终端保留 list、status、on、off 等操作。status 由米家适配层提供：当前本地连接与业务降级状态、共同路径优先级、各设备当前可用控制路径与生效通知来源、不可用或同步受限原因、最近切换原因和下一次已安排的恢复检查。控制路径显示反映当前选择；在途命令的结果仍注明其实际路径。

终端与日志继续使用英文，设备名称原样显示。成功仍使用 accepted，避免将受理描述为真实动作已经确认。日志可以记录 DID、操作、属性绑定、请求关联、路径、错误码和恢复阶段，不记录令牌、认证头、私钥及完整账号响应。

运行说明同步反映云端恢复、路径诊断及重新登录方式；已知限制记录仍未解决的产品限制，不在仓库记录具体账号或真机验收结果。

## 验证要求

### 自动化验证

测试代码遵循仓库统一的目录约定：模块测试及其辅助实现放在所属模块的 `tests/` 目录，按行为主题组织；根目录 `tests/` 保留公开接口与进程集成测试。测试移动不扩大生产代码的可见性，也不改变现有验证行为。

复用当前可控协议对端、可推进时钟、临时数据库、Matter 组装和进程回归，扩展云端 HTTP 与 MQTT 替身。普通测试不访问个人账号、中枢或真实插座。

- 云端读写的目标关联、逐项成功与失败、合法布尔值、错误封装、缺失或重复结果，以及订阅确认、拒绝、断连、重复消息与坏消息隔离。
- MQTT 仍连接但已发送本地业务无应答时，后续命令改选云端；排队超时、取消、明确设备错误不触发共享降级。
- 原写入可能已经执行但应答丢失时，只返回失败；超时、切源、认证刷新、重连和重启都不增加该写入的发送次数。
- 控制与通知共用本地优先、故障后云端优先、恢复后返回本地的选择顺序；云端不可用时仍可使用有效本地路径，单台设备离线不误伤其他设备。
- 云端 HTTP 临时请求失败合并到既有同步恢复，恢复前的新命令和读取不使用云端 HTTP 候选；完整同步成功后恢复候选资格，不增加属性恢复探测，也不把同步成功等同于实际控制成功。
- 云端 HTTP 暂停而 MQTT 仍正常时，生效来源的通知继续更新状态，属性与在线通知均不解除 HTTP 暂停；所有控制路径不可用时设备仍不可用、Matter Reachable 仍为 false。认证和设备访问条件失效仍按对应范围处理。
- 本地连接结束后保留设备身份、原通道队列与命令消费者，后续命令和补读可转向云端；仍有控制路径时不短暂标记不可用，全部控制路径失效时结束待执行命令，恢复后不执行这些已失败命令。旧连接结果失效，设备删除及适配层停止则统一结束所属任务。
- 云端读取挂起至超时时，其他设备的本地补读仍按原有节奏执行，其他通道命令继续工作，不受跨路径共同等待阻塞。
- 首次 1 分钟、随后轮末 5 分钟的恢复调度，重复失败合并、无并发检查、无健康空闲探测、无遗留快速重试绕过慢速节奏。
- 当前有效的本地设备列表请求成功即可恢复本地优先级，无需额外属性探测；设备仍按各自在线与访问条件选路，后续读写无应答时重新降级。旧连接或已结束请求的迟到结果无效，新主中枢及重连后的列表刷新可提前恢复。
- 新来源部分订阅成功时保留旧来源；来源切换和同源重连使旧工作失效；控制可用而通知受限时仍能执行明确开关命令。
- 单路与多路共用刷新入口，重复触发合并，在途读取被新刷新触发失效后最多保留一次后续读取；总控通知读取三路各自属性并独立更新，不推断通道值或等待三路全部完成。
- 同值去重、同值通知阻止迟到读取覆盖。写入后的有效通知不被迟到成功回复覆盖，命令仍成功完成并推进 FIFO；未收到这类通知时维持原有乐观更新，包括切换来源后的补读已返回、原在途写入随后成功的交错情况。
- 云缓存补读的既定应用规则；测试不把缓存成功等同实时设备健康，也不要求实现协议无法提供的跨来源全局事件排序。
- 多设备状态隔离、通道 FIFO、跨通道并发、执行时 Toggle、动态增删、重加及不兼容绑定隔离。
- 本地缺失时恢复已发布设备；云目录中新设备与已删除记录不自动发布；账号、家庭及不完整分页隔离。
- 令牌定时维护、并发及迟到认证拒绝、刷新后通知重建、写入不重试、证书失败不阻断云端、云认证失败不阻断本地。
- 现有身份、名称、端点、配对、订阅和存储迁移，以及正常退出、同目录重启、认证命令与 macOS 进程回归。

执行现有检查：cargo fmt --check、cargo test --locked、cargo clippy --locked --all-targets -- -D warnings。

| 外部变化 | 每个代表通道在两种生效通知来源下分别完成 1 轮外部关闭与开启，使用实体按键或米家 App。Apple Home 保持打开且不手动刷新，正常网络下 3 秒内反映变化。多路总控需检查各路实际状态，不要求不存在的独立实体按键。 |
| 本地故障、云端有效 | 3 轮。保持设备及必要网关的互联网链路有效，使 MiGate 本地路径不可用，检查后续控制和主动通知实际通过云端恢复，不重新配对。 |
| 云端故障、本地有效 | 3 轮。检查有效本地控制与通知持续工作。 |
| 主中枢轮换 | 3 轮。保留其他中枢工作，断开当前主中枢；检查新的实际控制与通知路径，随后恢复原中枢并观察稳定性，不要求切回原中枢。 |
| 本地故障期间重启 | 原数据目录重启 3 轮。已有设备由云端恢复控制与状态，无需再次登录或配对，身份、端点和名称不变。 |
| 切换后的持续同步 | 每类故障切换的最后一轮成功后持续观察 10 分钟，期间再次操作各代表通道，检查通知持续有效和通道隔离。 |
| 动态加入、删除与重新加入 | 选一台方便操作的设备完成 1 轮，确认原有加入条件、完整成员关系删除、身份复用和其他设备继续工作的行为保持。 |
| 无重复执行 | 结合请求计数与日志核对故障前后没有跨路径补发或重启重放；不能只凭插座最终仍为同一状态证明没有重复发送。 |

对“本地 MQTT 保持连接但业务无应答”，自动化可控对端必须覆盖；若真机无法稳定制造，明确该项仅有自动化证据，不能用普通断网替代后声称完成同一真机场景。

网关断电时分别记录各代表设备的云端读写和主动通知是否还能工作。若云端依赖的物理网关也不可用，应如实报告设备不可达；不把这种依赖认定为路由实现必须绕过的故障。

故障切换记录实际耗时，并分别检查各网络步骤的时限。故障确认后的下一条新命令应按新优先级选择；云端真正恢复可服务后再检查其正常控制与通知标准，不能用延长单次请求超时掩盖错误选路。3 秒是正常网络下的真机同步标准，不是所有故障恢复场景的总期限。

Apple Home 的重启、断线及拓扑恢复保留最长 20 分钟观察窗口。重启从 MiGate 重新提供 Matter 服务起计，断线恢复从相应路径实际恢复服务起计，拓扑变化从 MiGate 提交更新起计。这个窗口不取代 MiGate 的网络步骤超时或正常同步标准；未恢复时如实记录，不用重置配对掩盖问题。
