# 灯具能力自由组合与灯组接入

## 目标与范围

灯具按真实具备的开关、亮度、色温和 RGB 能力自由组合接入，独立灯与灯组成员使用同一套模型、持久化和控制链，不虚构缺失能力。

米家灯组提供身份、名称和成员关系。MiGate 根据成员能力交集发布一个普通的 Matter 灯端点，复用成员完整的读取、订阅和控制路径，负责组控及状态汇总，不使用组 DID 自身的 MIoT 灯光接口。Apple Home 每组只显示一个灯入口，成员单控保留在米家。

物理灯的能力及量程在接纳后作为静态描述；灯组的能力和共同量程由确认关系派生，随成员变化在原身份和端点上更新。成员关系、物理实例、对外发布集合或固定描述变化统一通过重建 Matter 实例应用，允许整桥短时中断。

灯光操作、连接选路和桥接基础分别依据[单灯照明控制](../2026-10-08-single-light-control/spec.md)、[云端接入与统一选路](../2026-10-06-cloud-access-routing/spec.md)及[多设备多通道桥接](../2026-10-04-multi-device-channel-bridge/spec.md)。能力组合、灯组控制与汇总、成员变化及发布生命周期以本文为准。运行范围为 macOS / Apple Silicon，采用 Rust 单包结构。

范围限于独立灯具及其米家灯组，不包含墙壁开关负载映射、浴霸内置灯、厂商场景、Apple 自适应照明、由 MiGate 编辑米家灯组，以及新的协议栈或通用设备编组框架。无代表设备的能力组合按自动化验证边界完成，不要求取得新硬件。

## 灯具能力与解析

开关、亮度、色温和 RGB 独立描述，通用模型及持久化允许任意非空组合。能力必须来自真实可控属性及其绑定，固定参数不等于可调能力；灯具类别不依赖某项可选能力是否存在。Matter 设备类型要求在发布映射处处理。

MIoT 解析在协议边界检查属性类型、访问方式、量程和编码，只生成实际能力的绑定。缺少可选属性不拒绝整盏灯，解析失败明确报错，不以默认属性或量程代替。厂商私有颜色编码及模式由适配层处理，不把代表型号或型号专有模式设为通用准入条件。

同一描述贯穿解析、模型、控制、状态和恢复，各层不另设能力组合白名单。缺失能力不生成对应状态、属性访问或控制器；支持但未读到有效值时保持未知。模式及模式切换也只按实际能力提供，不补造缺失模式。

## 成员目录与关系

通过米家云端设备目录接口 `/app/v2/home/device_list_page` 读取组设备的 `extra.member_list`。组 DID 取 `group_did`，成员 DID 取 `member_ship` 的键，不根据名称或排列推断关系。`member_ship` 是接口实际字段名；`display_member_switch` 不决定 Home 展示，`is_physical` 只区分米家组类别，两类组使用同一规则。

关系在云端协议边界解析，组及成员状态按接口的 `"1"` 处理；未知状态或无法解析的响应视为读取失败，不转换成有效空组。`group.*` DID 或已知 `mijia.light.group3` 进入组关系解析，不作为普通单灯接入；代表型号不构成组白名单。

支持当前家庭内非空、扁平，且全部成员均可作为单灯发布的灯组，不要求成员能力相同。同一物理灯可以属于多个组；单组内成员不得重复，组不得包含自身或其他组。成员暂时离线或首读失败不影响关系成立。超出此范围的组不发布灯组入口；支持且未属于其他已发布组的成员按独立灯处理，并说明原因。

目录读取沿用统一认证、分页及同步机制，完整同步同时刷新组元数据，关系按约 5 分钟的目录周期收敛，不设独立组连接。各组独立确认：关系读取成功且必要成员描述齐备时更新，读取失败或信息未齐时保留该组最后确认的关系，其他组继续推进。跨组共享成员不构成冲突，不等待其他组释放成员；新旧确认关系暂时重叠时，各组仍按自身已应用关系控制和汇总。删除须由完整家庭目录确认，详情缺记录不等于删除。已确认的设备删除撤销对应控制路径并清理活动来源引用，不因相关关系尚未刷新而延后。

## 组能力与共同量程

灯组能力取当前已应用关系中全部成员能力的交集，不随在线或灯光状态临时改变。每项组操作适用于全部成员，暂时无法执行的成员按失败规则处理，不按能力筛选部分成员执行。

亮度统一以百分比表达，再按成员真实量程及步进换算，不承诺相同物理亮度。色温取成员可调区间的共同部分；没有共同可调区间时仅省略灯组色温能力。共同区间不要求设备离散取值完全重合，写入仍遵守成员量化规则。

色温发布量程与目标限幅使用同一描述，在 Matter mired 与成员单位之间换算。新请求的目标限制在当前共同范围内，不依赖 Home 收窄滑块，也不把限幅后的目标作为实际状态。

确认成员变化后重新计算交集和共同量程，按发布更新规则与成员关系一并应用于原灯组的虚拟灯端点，保持身份、端点和配对。

## 组状态与可用性

灯组状态只汇总当前成员的有效实际快照，沿用单灯成功受理后的快照更新及通知、回读校正规则，不取组 DID，也不直接把组命令目标写成组状态。共享成员只有一份实际状态，其变化参与所有所属组各自的汇总。

成员失去全部可用路径后，离线前的缓存按未知参与组聚合；路径恢复本身不使旧值重新有效，相应字段取得新的有效状态后才重新纳入。此规则只约束组聚合，不改变能力、关系或独立单灯的缓存展示，也不增加定时过期机制。

| 属性 | 汇总规则 |
| --- | --- |
| 开关 | 任一成员已知为开，则组为开；全部成员确认关闭，组才为关；其余情况为未知。 |
| 亮度 | 成员开关状态足以确定亮灯集合，且所有亮灯成员的亮度均有效时，取这些成员的百分比平均值。信息不足则未知，不只对已读到的部分取平均。 |
| 全部关闭时的亮度 | 保留本进程内最后一次有效组亮度；没有有效历史则未知。 |
| 颜色与模式 | 从稳定代表成员读取，颜色、色温和模式保持同源，不按通知先后切换代表。 |
| Reachable | 至少一个当前成员具有可用控制路径即为 true；全部不可用时为 false。 |

代表成员优先从亮着且可读到有效活动颜色及模式的成员中选择，其次考虑其他可读成员；同一优先级按稳定成员键排序。目录重排及通知到达顺序不改变选择。必要字段不足时保持未知，不用不同成员的字段拼成一组颜色；非活动颜色缓存也只取该代表成员。

代表成员的活动模式不在组已发布能力内时，不伪造另一种模式或对应值。代表色温超出当前共同范围时，组色温为未知，不把观察值夹到范围内，也不因此反向控制成员。

成员通知省略的字段表示未更新，不清除已有观察。组状态按当前有效观察生成完整快照；字段变为未知时替换此前已知值，不保留已经失效的聚合结果。

Matter 允许空值的属性以空值表达未知；不能表达空值的属性按未知读取失败处理，不用默认开关、颜色或模式补齐。状态未知不直接等同于整组不可达，也不承诺 Home 为每种未知状态显示专门提示。部分离线通过成员当前状态展示，操作错误沿用单灯既有诊断，不用 Reachable 表示“全部成功”。

## 控制与结果

### 操作分发

独立灯与灯组成员使用同一控制链，每项操作只依赖其实际需要的能力。开关联动和模式切换按真实能力处理，色度换算不依赖虚构亮度；来源所需的模式由成员适配层处理。

`Options`（含 `ExecuteIfOff`）、`OnLevel` 等端点设置在灯组入口形成统一意图，分发后不再套用隐藏成员原 Matter 端点的设置。协议规定的无动作成功按协议返回，并与实际成员写入结果区分。

组命令确定统一操作意图，再按触发时的成员集合分发：

- 绝对目标采用同一有效目标，各成员从自身实际状态按请求时长执行。
- Step／Move 按实际命令逐成员计算起点和进度。色温执行边界取触发时共同范围与命令有效边界的交集，再按成员量化，不假定 Home 或 Siri 一定发送相对命令。
- Toggle 根据组开关状态生成统一开关目标；状态未知则返回错误，不逐成员翻转。
- Stop 使用自身触发时的成员集合，停止范围沿用单灯语义；共享成员当前对应维度的动作也会停止，不区分动作由哪个组或单灯入口发起。

成员独立选路和排队，慢速或离线成员不阻塞其余成员。各组及单灯入口共享同一成员控制链，不设置组优先级或动作归属；后来的有效操作按单灯规则接管对应成员及控制维度，不影响其他成员。

### 部分成功与失败

至少一个目标成员完整受理即返回组成功；全部失败才返回整体失败。成员受理标准沿用单灯语义，部分必需属性写入成功不算完整受理，但实际生效值仍参与状态同步。

成功响应不表示所有成员成功或动作完成，也不截断其余成员的正常分发。成员错误沿用已有控制链的诊断，失败不引发回滚、不确定写入跨路径重发或离线恢复补发。

命令响应与状态报告独立：无论受理结果如何，灯组均按实际成员状态汇总，不将请求目标当作当前值。

## 动作与成员生命周期

组命令按触发时已应用的成员关系确定分发对象与操作意图。已经交给成员控制链的操作沿用单灯的执行、接管、停止和失败规则，普通状态同步不额外取消操作。成员关系变更或物理实例更换统一触发 Matter 重建，未完成操作按重建中断规则处理，不向新增成员补发或在新实例续跑。目标、有效范围和时长等执行所需参数由成员控制链按需持有。

灯组只保留完成命令分发和受理应答所需的临时状态，不另行保留组级完整动作快照或历史，也不持续追踪成员执行完成。正常执行所需的活动状态复用单灯控制链。

有限时长动作的 RemainingTime 从当前成员控制链的活动状态中取对应控制维度的最大剩余时间，包含其他入口在共享成员上发起的当前动作，全部结束后归零；连续 Move 沿用协议语义。已移出成员不参与该组汇总，已撤销能力停止报告。

新的有效命令、识别到的米家或实体操作以及 Stop 仍按单灯规则接管或终止对应动作。实际设备的控制路径撤销或进程退出按真实生命周期终止执行；进程重启不恢复或重放未完成动作。

## 模块边界与数据流

| 单元 | 职责 |
| --- | --- |
| `xiaomi/cloud` 与 `xiaomi/catalog` | 解析组身份、名称、成员及完整家庭目录，提供已确认关系。 |
| `xiaomi/capability` | 独立解析真实灯具能力和可选 MIoT 绑定，区分组目录与普通灯具。 |
| `xiaomi/adapter` | 执行成员读取、订阅和写入，复用实例、选路、队列及实际状态；不为组 DID 建立灯光接口。 |
| `device` | 表达单灯与灯组的统一能力、状态和命令接口；派生组能力、共同量程和状态，确定组命令的分发成员并汇总受理结果，不携带 MIoT 属性或 Matter 端点类型。 |
| 灯光控制链 | 复用单灯的目标操作、渐变、Move／Step／Stop 和接管逻辑，维护实际执行所需的当前活动状态。 |
| `storage` | 保存真实能力、可选绑定、身份、名称、端点预留及已确认关系，按一致版本恢复。 |
| `matter` | 将单灯或灯组映射为普通灯端点，转换命令并报告实际状态、动作进度；成员关系、物理实例、发布集合或固定描述变化时，通过实例重建统一应用配置及版本。 |
| `runtime` 与终端 | 分别管理源连接与 Matter 生命周期，展示关系、能力、当前状态、路径、已有请求错误和未发布原因。 |

数据流为：米家目录与能力描述 → 物理成员及确认关系 → 通用组能力和状态 → Matter 灯端点。控制沿相反方向经组命令分发到各物理成员，状态经同一成员快照返回聚合。

每盏实际灯只有一个活动物理实例、源连接及状态来源，多个组引用同一实例。组记录引用稳定成员键，不复制成员设备或维护另一套成员控制器。成员在 Home 中隐藏，仍保留其物理实例、内部订阅、控制路径和身份预留。

Matter 接口不包含 Xiaomi 请求或成员 MIoT 细节，源适配不决定 Home 端点结构。

配置在统一的同步应用边界取得最新确认结果，完成准备、差异计算、事务提交和已应用视图更新，各层复用已解析的成员与派生描述，准备结果不作为可独立提交的候选跨阶段传递。外部目录、持久化恢复和协议映射在各自边界校验；启动恢复与运行期变更共用固定描述差异和配置版本的计算规则。已应用视图统一持有独立设备和组成员的物理实例引用；来源撤权立即关闭控制路径，旧引用仅用于维持最后完整发布视图，成功提交后统一替换。

## Matter 能力与发布结构

Matter 设备类型规定最低要求，允许端点增加类型定义未列出的标准 cluster。通用能力模型不受固定灯型限制，映射必须满足所选设备类型。

四种现有标准灯类型均要求真实 OnOff。没有开关的能力组合仍可解析和保存，但不能补造 OnOff 并发布为这些灯型，应说明无法映射的原因。具备 OnOff 时，独立灯与灯组按同一规则选择类型：

| 实际能力 | Matter 设备类型 |
| --- | --- |
| 亮度、色温和 RGB 均具备 | Extended Color Light（`0x010D`），提供 CT + XY + HS。 |
| 具备亮度和色温，无 RGB | Color Temperature Light（`0x010C`），提供 CT。 |
| 具备亮度，其他情况 | Dimmable Light（`0x0101`）；有 RGB 时增加对应 ColorControl 能力。 |
| 不具备亮度 | On/Off Light（`0x0100`）；有色温或 RGB 时增加对应 ColorControl 能力。 |

有亮度才发布 LevelControl；有色温或 RGB 才发布 ColorControl。CT 仅随真实色温能力启用，XY／HS 由 RGB 映射。没有对应能力的命令返回不支持，不转换为其他能力操作。

类型、cluster、feature、量程、属性、命令列表和处理器从同一描述生成，不能只改 ServerList 而留下不匹配的处理器。CT、XY 和 HS 按所选 feature 的标准依赖发布，不额外要求亮度或其他颜色能力。范围不包含 Enhanced Hue、Color Loop 及完整 Matter 符合性认证，灯光协议实现的既有差异见[已知限制](../../known-limitations.md)。

控制器可以忽略设备类型之外的额外标准 cluster。允许发布某种组合不保证 Home 一定提供相应控件，没有代表设备的组合按自动化边界验证。

根端点 `0`、Aggregator 端点 `1` 及插座结构保持既有职责。独立灯与灯组都在自己的桥接端点上提供 Bridged Device Basic Information、Descriptor、Identify、Groups 及真实灯光控制能力，Bridged Device Basic Information 提供 ConfigurationVersion。灯组以组 DID 对应的稳定身份发布，使用单一控制端点，不设用于展开成员的子端点或成员 TagList。

属于至少一个已发布组的成员不发布为独立 Matter 灯端点，其端点编号和身份保留在存储中。退出最后一个已发布组且仍属于当前家庭的支持成员恢复原独立端点。Descriptor 的 PartsList 只列出实际发布结构，不包含隐藏成员；多个组可以分别发布虚拟灯入口并控制共同成员。

Matter Groups 的标准行为属于各已发布端点，不将米家 group DID 映射为 Matter group ID，也不依赖 Actions.EndpointLists 或控制器自动编组生成组入口。Home 通过灯组的虚拟灯端点进行控制。

## 身份、持久化与恢复

物理灯由 DID 对应的 DeviceKey 和 `main` 功能键标识，灯组由组 DID 标识。成员关系、描述重排及灯组能力变化不改变 UniqueID、endpoint、保存名称或网桥配对。撤销或隐藏的身份及端点继续预留，不分配给其他对象，重新出现时按既有策略复用。

首次名称采用已有保存名称或米家目录名称，之后遵循持久化命名规则：目录更名不覆盖保存名称，NodeLabel 的有效写入保存，Home 本地显示名由 Home 管理。成员名称独立于灯组保存。

物理灯持久化真实能力及可选绑定，灯组保存身份和确认关系；派生描述从同一版本关系与成员描述计算。当前格式的设备、组身份及端点数据按保存结果恢复，不补造缺失能力、默认绑定或组 DID 的灯光功能。

项目处于开发期，生产代码只维护当前数据库格式的创建、读写和恢复，不保留旧版本迁移路径及迁移测试。已有本地库不兼容时单独做一次性数据修复，不将该修复纳入运行期配置流程。

关系、身份、派生发布描述及配置版本作为同一份配置原子保存并统一应用，网络操作不进入数据库事务；存储失败保留此前已应用的发布配置，已确认删除或撤权仍立即生效，不因恢复旧发布配置重新取得控制权。运行状态与未完成动作不作为持久化恢复值，包含在线状态及全关时保留的历史亮度。原目录重启先恢复最后成功提交的完整配置，再同步目录及实际状态；待应用候选不与旧配置版本混用。属性从未知开始，已撤销组不自动发布，配置版本不倒退。

单灯描述不兼容沿用静态描述规则，保留身份并报告不可用原因；不改变对外能力及量程的描述重排、绑定或换算更新仍按既有规则处理，不建立通用能力迁移框架。

身份恢复不依赖清空运行目录或重置配对。Home 场景、自动化、房间及自定义布局迁移不在范围内。

## 发布更新

发布集合由各组确认关系的合集决定：有效灯组分别发布一个入口，这些组成员的并集从独立发布集合中排除，其余当前家庭中的受支持灯具作为独立灯发布。关系更新后重算集合及派生描述；组解散、变空或不再满足接入范围时撤销该组入口，仅未属于其他已发布组的支持成员恢复原独立端点。目录未确认的变化不提前应用。

成员关系按组键及其成员键集合比较，目录重排和相同关系的重复同步不算变化。固定描述的变化按端点集合、设备类型、cluster、feature、量程、属性与命令列表及 Descriptor 比较，不以成员实例是否相同代替。各组最后确认的关系及派生描述合成为同一份待应用配置；连续变化合并为最新确认结果，原子提交不要求各组关系来自同一轮读取。候选提交前，控制与状态汇总继续使用当前已应用的完整关系和描述；实际设备删除或控制权撤销仍立即终止对应控制路径，旧关系中的相关成员按不可用及未知状态处理。

成员关系、物理实例、发布集合或固定描述变化时，统一结束旧 Matter 实例及其传输、交互模型、响应器、处理器和 socket，再以完整的新配置启动实例。成员关系实际变化或同键物理实例更换，即使没有改变发布集合、能力或量程，也走同一重建流程。同一运行实例内不增删既有端点的 cluster、属性或命令，不改变其固定能力描述。

需要重建时，旧实例完整退出后，在统一同步应用边界重新取得最新确认结果并安装新配置；成员关系、发布集合、派生描述和配置版本须原子保存，新实例对外服务前完成恢复与初始化。旧实例不观察新配置或新版本，不在原交互或分片报告中途切换结构。提交失败不发布部分配置、不将候选标记为已应用；恢复仍以最后成功提交的完整配置为准。

重建允许中断尚未完成的 Matter 交互、分片报告及渐变、Move／Step 等操作，不要求等待全局交互空闲或保留原会话、订阅对象。被中断操作的剩余调度与活动状态须清理；已发出的设备命令可能已经生效，不承诺撤回。源连接和状态同步继续运行，新实例不自动续跑或重放被中断的操作。Fabric、ACL、Groups 等协议持久数据、配对、身份及端点编号保留，会话和订阅按协议重新建立或恢复，无需重新配对。重建期间未变化的灯具及插座也可能短时无响应，服务恢复后须正常控制和同步。

普通状态同步、源连接恢复及相同成员关系的重复同步不触发重建。不改变固定描述的来源绑定或换算更新复用原物理实例，不触发重建。设备控制权撤销后重新接纳等真正更换物理实例的情况，即使设备键相同也统一重建 Matter；运行中的 Matter 实例不原地替换设备处理器和成员观察任务。

固定描述变化时按协议递增根节点及受影响灯端点的 ConfigurationVersion，并向控制器报告配置变化；仅成员关系或物理实例变化而固定描述未变时，重建本身不额外递增 Matter ConfigurationVersion。固定属性及相应版本的变化在同一 Report Data Action 中报告，允许分片，但不能靠后续报告补齐不一致版本。配置应用与 Home 展示刷新分别观察；配置稳定且通信正常后，Home 展示自行收敛，不依赖重新配对或强制刷新。

## 运行观察

终端与日志使用统一关系和状态来源，展示灯组派生描述、汇总依据及成员当前状态、路径，成员查询列出全部所属组，复用既有请求诊断定位失败成员与原因。请求受理不表示动作完成，实际状态仍来自成员快照；不另建组级执行完成记录，正常状态更新不重复输出整组描述。

目录确认、配置待应用、提交完成及 Matter 服务恢复的时点和错误分别可观察，以区分目录同步、配置应用、Matter 重建和 Home 展示收敛的延迟。

## 验证与完成条件

### 自动化验证

模块测试及辅助代码放在所属模块的 `tests/`，跨模块流程放在根目录 `tests/`，不为测试扩大生产代码可见性。测试按以下主题验证正文规则及其边界，不以有限样本组合代替能力覆盖；同一行为优先在负责该行为的边界覆盖，跨模块仅保留必要的集成验证，不为内部阶段拆分重复建立测试流程：

- 能力全链路：覆盖四项能力的全部非空组合，验证解析、绑定、模型、控制和持久化一致，区分固定参数、缺失能力与未知状态。具备 OnOff 的组合覆盖独立灯及灯组的 Matter 映射；其余组合不得补造 OnOff 发布。
- 派生能力与状态：覆盖混合能力、共同范围及量化边界，验证实际状态汇总、稳定代表选择和已知／未知转换；离线缓存不参与有效聚合，恢复后以新状态为准；能力不因暂时离线删减，代表选择不随目录重排或通知顺序改变。
- 操作与结果：覆盖所支持命令及模式切换、部分受理和全部失败、逐成员独立选路及接管；成员开关状态不一致时，端点设置仍按组入口解释，区分协议无动作成功与成员写入结果。共享成员复用物理实例和控制链，跨组操作及 Stop 按成员当前维度生效，各组状态跟随实际观察。确认响应不截断其他成员的正常分发，状态来自实际快照，无组 DID 灯光请求、回滚或旧命令补发。
- 动作生命周期：验证普通状态同步不额外取消已交给成员控制链的操作；新的有效操作及 Stop 按单灯规则接管，设备控制权撤销及时终止。RemainingTime 反映当前成员的必要活动状态；成员关系或物理实例变更触发的 Matter 重建允许中断未完成操作，清理被中断操作的剩余调度与活动状态，不向新增成员补发，恢复后不续跑或重放，进程重启也不重放。
- 目录与发布：验证完整家庭范围、各组独立确认及失败保留、共享成员及新旧关系暂时重叠、单灯静态描述不兼容，以及成员完整生命周期；退出一个组但仍属于其他组时保持隐藏，退出最后一组才恢复独立端点。成员关系、发布集合、能力、身份和端点预留一致应用，存储失败不产生部分视图；配置待应用时重启仍恢复最后成功提交的完整配置和版本，已删除成员不恢复控制权，配置版本不倒退。
- 配置应用与重建：验证成员关系、物理实例、发布集合或固定描述变化触发旧实例完整退出，新实例按原子保存的完整配置启动；覆盖发布集合和固定描述相同但成员键关系变化或同键物理实例更换的重建，确认仅重建不额外递增 Matter ConfigurationVersion。未完成的交互或分片报告可中断，旧实例不读取新配置，新实例的元数据、处理器和版本一致，固定属性及对应版本在同一报告动作中报告。覆盖连续变化合并、提交失败保留完整配置、身份及协议持久数据保留，以及会话和订阅恢复后的控制与同步。普通状态变化、相同关系重复同步、连接恢复及复用原物理实例的来源绑定更新不触发重建，不引入全局空闲判断。
- 回归：当前格式数据恢复及独立灯、单路与多路插座的控制、同步和恢复行为保持。

### 真实设备与 Home 验证

使用二楼 6 盏筒灯组、4 盏过道筒灯组（`yeelink.light.light3`），以及卧室床头左右彩灯组（`devcea.light.ls2307`）验证真实入口、控制和状态。已有组的成员关系与自动化保持不变，关系变更仅使用独立临时组。

| 项目 | 通过条件 |
| --- | --- |
| Home 呈现 | 在已有配对和数据上，每组收敛为一个普通灯入口，成员不另行展示；组身份、端点和保存名称保持，无重复入口。 |
| 控制与状态 | 各组所声明的控制能力及模式切换各验证一轮；米家单控成员不误控其余成员，Home 在成员状态不一致及全部关闭时仍遵循汇总规则。 |
| 渐变与接管 | 验证正常组渐变及单个成员被米家操作接管，其余成员继续，汇总值跟随实际进度。 |
| 临时组生命周期 | 依次创建、加入成员、移出成员和解散，验证入口隐藏与恢复、原身份及名称保持、派生能力与量程更新，以及每步控制和同步；成员关系、物理实例或发布变化触发的自动 Matter 重建允许短时中断，恢复后组入口、未变化灯具及插座均可正常控制和同步，无需重新配对。 |
| 重启与回归 | 原数据目录重启一次后恢复关系、能力和控制，身份与配对保持；抽查未编组灯具、单路及多路插座。 |

临时组至少准备三盏当前家庭内、受支持且未编组的灯，确认米家允许共同编组及编辑，优先选不同能力或量程。先用两盏创建，再加入第三盏、移出一盏，最后解散；增删期间保留至少两盏以适应米家界面。每步等待目录确认、配置应用及 Home 收敛后再继续，不能把解散重建当作原组内增删成员通过。

能力变化后，原入口应提供与当前描述一致的控件和控制。色温量程以发布范围、请求限幅及实际反馈判断，不要求 Home 滑块收窄。

使用经过实际聚合和分发路径的隔离虚拟灯组，补充验证 Home 对部分成功及全部失败的反馈和真实汇总状态，也可验证动态能力与量程。普通测试灯切换能力不能代替组控验证，虚拟成员不能代替米家目录及真实组生命周期。

缺少实物样本的能力或量程组合按自动化边界完成，对应真机行为标记未验证，不要求新硬件，也不以范围外设备替代。真实组生命周期缺少样本的项目保持待验，不为凑样本改动已有组。没有界面入口的协议命令及复杂故障、并发由自动化覆盖。

服务稳定、无配置变更且网络正常时，操作或渐变完成后的实际状态以及米家外部变化按 3 秒同步目标判断，总计持续观察 10 分钟。目录同步、配置应用、Matter 重建中断及 Home 展示收敛分别记录；Home 收敛窗口从配置实际生效且 Matter 服务就绪、通信正常后起算，最长 20 分钟，不包含目录同步、配置应用和服务重建的时间。原目录进程重启也从 Matter 服务就绪且通信正常后起算。

每个样本只验证实际使用的本地或云端路径，不重复完整选路故障矩阵。设备、系统和网关版本及结果记录在任务对话中，不写入仓库。成员关系、物理实例或发布变化触发的自动 Matter 重建属于正常流程；未执行、超时或不符预期的项目如实保留，不能靠额外手动重启、重新配对、清空数据、强制刷新或 Home 手动编组替代通过。
