# 灯具能力自由组合与灯组接入

## 目标与范围

灯具按实际具备的开关、亮度、色温和颜色能力接入，各项能力自由组合。纯开关灯、固定色温调光灯、色温灯、彩灯及其他能力组合使用同一套能力模型、持久化和控制链；独立灯与灯组成员均按真实能力发布和控制，不虚构缺失能力。

能力自由组合用于支持不同灯具的实际能力。单灯接纳后的对外能力及物理量程作为静态描述，本轮不支持运行中增删能力或改变量程；该限制同样适用于灯组成员。灯组动态变化只调整成员关系及发布角色，保留成员原有控制能力。

米家灯组通过 Matter 组合端点呈现为一个配件及多个灯光功能。目标是在 Apple Home 中每组只有一个入口，进入后可以单独控制成员，且彩灯具有颜色控制。

米家灯组只提供成员关系。每个成员使用自己的完整灯光能力、状态和控制路径；组合控制及其界面由 Apple Home 提供。MiGate 不建立可控制的总灯端点，不计算成员能力交集，也不生成整组开关、平均亮度、色温或颜色状态。

灯组支持当前家庭内扁平、互不重叠，且全部成员均可作为单灯发布的关系，包括米家物理灯组和虚拟灯组。成员可以具有不同能力；不另设灯组成员的能力组合限制。成员数量不构成型号白名单或固定容量限制；单成员组可以保留组合关系，空组不发布父端点。成员暂时离线不影响组的成立。

灯光控制语义、连接选路和桥接生命周期分别依据[单灯照明控制](../2026-10-08-single-light-control/spec.md)、[云端接入与统一选路](../2026-10-06-cloud-access-routing/spec.md)及[多设备多通道桥接](../2026-10-04-multi-device-channel-bridge/spec.md)；灯具能力组合、结构发布及其引起的服务重建和操作中断以本文为准。运行范围为 macOS / Apple Silicon，采用 Rust 单包结构。

范围不包含墙壁开关负载映射、浴霸内置灯、嵌套组、重叠组、非灯成员、由 MiGate 创建或修改米家灯组、厂商场景、Apple 自适应照明，以及新的协议栈或驱动框架。不使用试验展示的虚拟设备；没有代表设备的能力组合通过自动化验证，代表灯和灯组按下述真机要求确认。

## 自由组合的灯具能力

统一能力列表分别描述开关、亮度、色温和 RGB，通用模型及持久化允许它们独立存在，不限定灯型组合。Matter 的设备类型要求仅在发布映射处处理。

| 能力 | 来源与行为 |
| --- | --- |
| 开关 | 真实的开关属性及读写绑定。缺少时不补造开关。 |
| 亮度 | 实际可调的亮度属性、量程及换算。纯开关灯不声明亮度；固定色温调光灯只需开关和亮度。 |
| 色温 | 实际可调的色温属性和量程。设备固定的白光色温不等于可调色温能力；没有亮度不妨碍表达色温能力。 |
| RGB | 实际颜色属性及明确的编码、模式语义。颜色能力不要求同时具备亮度或色温，向 Matter 映射为 HS／XY。 |

MIoT 解析只为实际能力生成绑定。缺少可选属性不导致整盏灯被拒绝；只读的固定参数不作为控制能力。属性类型、访问方式、数值范围及编码在协议边界检查，解析错误直接说明原因，不以默认属性或默认量程代替。RGB 按可识别的属性语义与编码解析，厂商私有格式及模式由对应适配处理；`devcea.light.ls2307` 是具有 RGB 与白光模式的代表设备，不是通用模型或存储层的颜色能力白名单。

同一能力描述贯穿解析、通用模型、读取与订阅、命令转换、状态和缓存恢复。各层按能力存在与否处理对应字段，不重复维护组合白名单，也不因当前样本没有某种组合而排除它。灯具类别不依赖亮度或色温绑定是否存在，纯开关灯仍是灯具。

能力缺失与状态未知分别表达：描述决定是否支持，快照决定是否已读到值。缺少的能力不生成状态、读写请求、通知订阅或控制器；支持但尚未读到的值保持未知。色温与彩色之间的切换只适用于同时具备二者的灯；来源要求的其他工作模式由设备适配处理。不为纯开关灯、调光灯或仅支持 RGB 的灯补造色温模式。

## 灯组与协议边界

米家灯组提供成员关系；Matter `Descriptor.PartsList` 表达组合结构；Apple Home 提供组合控件及整体操作。Matter `Groups` cluster 表达组地址与成员配置，不定义总灯状态，也不决定控制器 UI。每盏灯提供自己的 `Groups` 行为，不将米家 group DID 映射为 Matter group ID，不提供 Actions 组控制。

Matter 的组合设备与桥接模型允许多个功能端点共享顶层桥接身份；同一个桥接设备的 Bridged Device Basic Information 位于其层级顶端。灯组采用这一模型组织父子端点，成员的完整控制能力独立于组设备的属性。参见 [Matter Core §9.12.2](https://csa-iot.org/wp-content/uploads/2024/05/matter-1-3-core-specification.pdf#page=533)及[设备数据模型](https://developers.home.google.com/matter/primer/device-data-model)。命令、属性及类型版本由项目采用的 Matter 数据模型决定。

Home 的自动呈现通过真机验收确认。Apple 文档中的手动编组能力不作为此种 Matter 组合设备自动呈现的保证，端点结构正确也不能代替 UI 验收。

## 灯组成员目录

### 成员数据来源

通过米家云端设备目录接口 `/app/v2/home/device_list_page` 获取组设备的 `extra.member_list`。代表设备的目录结构如下，标识为示意值：

```json
{
  "extra": {
    "member_list": {
      "group_did": "group.example",
      "status": "1",
      "display_member_switch": 0,
      "member_ship": { "member-a": "1", "member-b": "1" },
      "is_physical": true
    }
  }
}
```

`member_ship` 是接口实际字段名。以其键取得成员 DID，不按灯名、房间、连续编号或设备列表顺序推断成员。`display_member_switch` 不作为 Home 展示要求；`is_physical` 只描述米家组类别，两种类别采用相同接入规则。组自身 MIoT 描述中的亮度、色温、RGB 缺项和量程均不限制成员能力。

成员关系在云端协议边界解析，读取组及成员状态 `"1"`；未知状态或无法解析的响应按目录读取失败处理，不过滤成有效空组。

目录读取使用统一认证、分页、周期同步、事件触发及重试。完整同步同时刷新组元数据，不因组尚未发布或成员已接入而漏查。成员关系按约 5 分钟的目录周期同步，无独立组连接；拓扑变更的收敛按目录同步节奏，不适用灯光属性同步的 3 秒目标。

### 接入与同步

灯组由米家创建和维护，MiGate 直接采用其成员关系。沿用现有家庭范围及完整目录同步规则，取得成员列表且全部成员可作为单灯发布时，即可组合接入，不要求成员能力相同或包含亮度、色温。成员离线或首读失败不影响接入，能力仍由各自的描述决定。

组与普通单灯分别处理：`group.*` DID 或已知 `mijia.light.group3` 进入组关系解析，不作为普通单灯接入。当前型号是代表样本，不限制具体组 DID 或成员数量。

读取失败时保留最后确认的关系，完整家庭目录确认的删除正常生效；详情缺记录不等于设备已删除。超出扁平、互不重叠及灯具成员范围的组不组合，支持的成员保留独立入口并说明原因。组关系不引入额外的能力兼容性准入或专用恢复流程。

## 模块边界与数据流

| 单元 | 职责 |
| --- | --- |
| `xiaomi/cloud` 与 `xiaomi/catalog` | 在协议边界解析组元数据，提供带账号、家庭及分页完整性约束的目录结果。 |
| `xiaomi/capability` | 独立解析各项真实能力与 MIoT 绑定，保留组与普通单灯的区别。 |
| `xiaomi/adapter` | 按已有绑定执行读取、订阅和命令；协调成员关系及撤销，复用实例、选路、队列和状态快照。 |
| `device` | 用统一能力列表及可选状态表达灯具，按请求需要的能力执行命令；保留独立的组合关系及修订，不携带 MIoT 属性或 Matter endpoint。 |
| `storage` | 保存真实能力、可选绑定、身份、名称、端点预留和已确认关系；按身份恢复，不重复进行能力组合准入，网络操作不进入数据库事务。 |
| `matter` | 从能力描述派生类型、cluster、feature 和处理器；独立灯及成员复用映射，组合关系映射为父子拓扑，在完整服务重建边界应用结构变化。 |
| `runtime` 与终端 | 管理生命周期，展示组及成员关系、未发布原因、成员能力和实际路径，不另建整组灯光状态。 |

数据流为：目录及 MIoT 描述 → 真实能力和绑定 → 持久化设备与组关系 → 发布注册表 → Matter 按已接纳的静态能力及确认关系准备拓扑，在自动重建服务后发布。成员属性通知直接进入原单灯快照，再由当前 Matter 实例的灯光处理器读取、报告及计算状态。

协议栈 fork 只保留项目内无法解决的最小通用接口或正确性修复；灯组发布策略和端点结构组织由 MiGate 的 `matter` 模块负责，能在项目内解决的问题不放入 fork。单个 Matter 实例存续期间保持已发布端点的结构稳定，通过完整服务重建应用新结构，遵守上游 Node 契约。

每盏灯由一个 `PhysicalDeviceDescription` 和一个 `main` 功能表示，组合记录引用成员的稳定设备键。分组变化继续复用外层米家连接、发现任务、设备注册表、成员实例、命令消费者及状态快照；Matter 实例及其灯光处理器按下述规则重建，不额外复制整组控制状态。

Matter 按已接纳的静态能力生成控制功能，并按组合关系确定发布角色。结构变化的判断依据完整发布结构，不能仅凭 `PhysicalDevice.same_instance()` 跳过更新；同一个成员实例也可能从独立端点变为子端点。端点集合、cluster 及属性／命令／事件列表、父子集合或 Descriptor 固定属性发生变化时，自动重建 Matter 服务；普通开关、亮度、颜色、在线状态变化及没有结构变化的目录同步不触发重建。运行中发现不兼容能力仍按静态描述规则处理，不借服务重建接纳能力热更新。

取得完整确认关系并准备新拓扑后，合并同一批待发布的结构变化，完整停止旧 Matter 实例、InteractionModel、Responder 及其在途交互、报告和控制调度，再建立新实例。旧实例的遍历器及分片报告不得继续访问新结构。新实例复用持久化的身份、endpoint 分配、保存名称、Fabric、ACL、Groups 和订阅等协议数据；在开始处理外部请求或恢复订阅报告前，完成新拓扑及 `ConfigurationVersion` 的一致初始化。类型、cluster、feature、处理器、父子集合和 Descriptor 信息须完整一致，不出现重复发布成员或引用不存在端点。固定属性与对应配置版本的报告继续遵守 Matter 协议要求，不通过后续报告补救同一报告内的版本不一致。

服务重建允许整座桥的 Matter 访问短时中断，包括未参与此次编组的灯具和插座；Home 可以暂时保留旧展示或显示不可用。米家连接及设备状态同步继续在外层运行。配置稳定且通信正常后，通过协议启动恢复及控制器重新建立会话、恢复或重新建立订阅，自动收敛到当前结构与状态；不依赖用户手动重启 MiGate、重新配对或手动刷新。Matter 服务恢复与 Home 展示收敛分别验证，不承诺秒级恢复，也不将服务启动完成等同于 Home 已更新。

旧实例中的未完成请求、读取及订阅分片、渐变和 Move／Step 等持续操作允许因重建中断，不要求等待所有交互自然结束。停止时取消剩余调度并清理其动作状态，避免遗留无主的“进行中”状态；新实例不自动续跑或重放这些操作。已发送设备命令可能已经生效，不承诺撤销，也不因重建跨路径重试；恢复后依据实际状态继续接受新操作。服务恢复失败按既有错误处理说明原因，不清空协议数据或伪装成功。

## Matter 能力映射与组合端点

Matter 设备类型规定最低要求，允许端点增加类型定义未列出的标准 cluster。因此，标准灯型用于决定发布类型，不反过来限定通用模型的能力组合。四种现有标准灯类型均要求真实 OnOff；缺少开关能力时仍可识别和保存其他能力，但不能补造 OnOff 发布为这些灯型，应说明无法映射的原因。

对具备 OnOff 的灯，按以下优先顺序选择设备类型，并只附加实际能力对应的 cluster 和 feature：

| 实际能力 | Matter 设备类型 |
| --- | --- |
| 亮度、色温和 RGB 均具备 | Extended Color Light（`0x010D`），提供 CT + XY + HS。 |
| 具备亮度和色温，无 RGB | Color Temperature Light（`0x010C`），提供 CT。 |
| 具备亮度，其他情况 | Dimmable Light（`0x0101`）；有 RGB 时增加对应 ColorControl 能力。 |
| 不具备亮度 | On/Off Light（`0x0100`）；有色温或 RGB 时增加对应 ColorControl 能力。 |

有亮度才发布 LevelControl；有色温或 RGB 才发布 ColorControl。CT 仅随真实色温能力启用，XY／HS 由真实 RGB 能力映射；无色温的彩灯不声明 CT，无亮度的灯不声明 LevelControl。模式、量程、属性、命令列表及处理器随同一描述生成，不能只改 ServerList 而留下缺失能力的处理器。没有对应能力的命令按 Matter 规则返回不支持，不转换成另一种能力操作。

ColorControl 的 CT、XY 和 HS 可独立选择，不要求同时存在亮度或其他颜色 feature。发布遵守所选 feature 的标准依赖，范围不包含 Enhanced Hue、Color Loop 及完整 Matter 符合性认证，协议差异见[已知限制](../../known-limitations.md)。

控制器可以忽略所声明设备类型之外的额外 cluster；因此，协议允许发布某种组合不代表 Apple Home 一定提供相应控件。没有代表设备的组合按自动化边界验证，不以获取新硬件为完成条件。

根端点 `0`、Aggregator 端点 `1` 及既有插座结构保持现有职责。

| 对象 | 类型、身份与功能 |
| --- | --- |
| 灯组父端点 | Bridged Node；仅提供 Descriptor 与 Bridged Device Basic Information，承载组身份、名称和成员 PartsList，不含 OnOff、LevelControl 或 ColorControl。 |
| 灯具成员 | 保留 Descriptor、Identify、Groups 及由自身能力选出的灯类型、控制 cluster 和 feature，不受米家组缺少属性影响。 |
| 未分组或退出组的单灯 | 同一端点同时提供灯类型及 Bridged Node 身份。 |

组合内的成员端点不重复声明 Bridged Node 或 Bridged Device Basic Information，桥接身份位于父端点。独立灯与 Child 路径共用实际灯类型、量程、命令和异步处理器映射，仅按发布角色调整桥接身份与标签；纯开关灯使用灯类型，不套用 On/Off Plug-in Unit。

同组多个同类灯通过 Descriptor 的 TagList 及成员标签区分。标签使用原成员已保存的设备名称，区分键绑定稳定成员身份；重排或移除其他成员不能重编号剩余成员，重名不能导致键碰撞。组首次名称使用已有保存名称或目录名称，之后沿用现有持久化命名规则；成员名称仍属于原设备，不改成统一的“灯”。Home 若未采用成员标签，允许首次逐灯核对后手动命名；这不免除 MiGate 正确发布标签的要求。

新服务对外提供访问前，保持父节点 PartsList、根与 Aggregator 的规范列表、成员角色、DeviceTypeList、ServerList、TagList 及对应数据版本一致，并通过后续读取和恢复后的订阅报告呈现当前结构。规范要求的祖先列表包含后代，不等于额外发布一份独立配件；每盏灯只有一个实际控制端点和一个组合归属。

父节点 Reachable 表示至少一个当前成员有可用控制路径；全部成员不可用时为 false，不用米家组自身的 online 字段代替。它不表示成员灯是否亮起，也不要求读到任何灯光值。子端点不另带 Bridged Device Basic Information，因此不承诺 Home 为每个子灯显示独立离线徽标；内部及终端继续保留逐成员可用性与错误。

## 身份、存储与动态变化

灯具身份由 DID 对应的 `DeviceKey` 和 `main` 功能键决定，组身份由组 DID 决定。能力列表顺序不影响兼容性；加入或退出组只是发布角色变化，使用原 endpoint、保存名称和配对关系，不分配第二个控制端点。

接纳时以完整有效描述确定单灯能力，读取或解析失败不作为能力删减依据。运行中发现能力或物理量程与已接纳描述不兼容时，沿用既有不兼容描述处理：保留身份记录，已有设备保持不可用并报告原因，不替换其已发布控制功能。保持对外能力及物理量程不变的属性绑定或数值转换更新，继续遵循既有单灯规则；本轮不新增能力迁移或热替换流程。

持久化保存真实能力及对应的可选绑定，不要求亮度、色温、颜色或模式同时存在。已保存的色温灯、彩灯和组关系可从原数据目录读取，不清空数据或重建身份；恢复不重复执行型号或能力组合准入。数值范围与绑定按实际能力保存，缺失字段不以默认量程、颜色或模式填充。

组父记录只保存身份及关系，不携带组 DID 的灯光功能。已有组身份预留可以复用，只有已确认成员关系才用于发布，单独的组设备缓存不代表成员关系。成员在独立灯与组合子灯之间切换时，保留原成员身份和控制能力，通过自动重建 Matter 服务调整桥接身份及 Descriptor；未完成操作按服务重建规则取消和清理，已发送命令不重放。

组身份、关系及必要的角色变化以一致事务保存，发布使用同一确认版本；异常不能导致一半成员独立、一半成员已归组。已撤销的组和成员继续保留原有身份预留，重新出现时按现有身份策略复用。

| 变化 | 处理 |
| --- | --- |
| 单灯描述不兼容 | 能力或物理量程变化不触发热更新，按既有规则保持不可用并报告原因，保留身份记录。仅能力列表重排不视为变化，也不打断操作。 |
| 成员加入组 | 确认完整新关系后自动重建 Matter 服务，该成员由独立灯变为原 endpoint 的子灯。 |
| 成员退出组 | 当前家庭中仍存在且受支持的成员恢复独立灯；剩余非空有效组继续发布。 |
| 组明确解散或有效成员列表变空 | 撤销父端点，仍属于当前家庭的支持成员恢复独立灯，不删除米家设备。 |
| 单个成员暂时离线 | 关系、能力和端点不变；其命令按该成员路径返回结果，其他成员仍可用。 |
| 关系明确变为不支持的结构 | 该组不再组合，支持成员按普通单灯处理，并说明原因。 |
| 确认成员从家庭删除 | 清理该成员引用；没有有效组关系时撤销父端点，其余支持成员恢复独立灯。 |
| 目录读取暂时失败或关系未确认 | 保留最后一致关系、延后相关变更；已确认的成员删除正常处理。 |
| 已确认关系引起发布结构变化 | 合并待发布批次，自动完整重建 Matter 服务；允许整桥短时不可用及旧实例的未完成操作中断，恢复后发布一致的新结构。 |
| 原数据目录重启 | 恢复当前账号及家庭保存的真实能力、端点分配及最后确认的有效组关系，再异步同步目录及成员状态。已撤销组不自动发布，不重放命令，属性从未知开始恢复。 |

MiGate 的内部身份、端点分配、名称及网桥配对保持稳定，不通过重置配对或清空运行目录处理灯组变化。Home 场景、自动化、房间配置或自定义显示布局的迁移不在范围内。

## 控制、状态与失败语义

Home 无论通过组入口还是成员入口发出请求，MiGate 都只执行请求所指向成员端点的命令，不再次向整组分发，不读写或订阅组 DID 的灯光属性。一个成员失败或离线不能阻塞其他成员，也不能以一盏灯成功表示其余成员成功。

命令只依赖其实际需要的能力：开关操作不要求亮度，亮度操作不要求色温，色温与 RGB 操作也不要求亮度。可调能力支持对应的目标设置、渐变、Move、Step、Stop 及后来有效操作接管；开关联动和模式切换仅作用于实际具备的能力。色度换算与独立亮度控制分开，不用虚构的亮度状态构造颜色控制器。来源要求的工作模式切换由设备适配执行，不把某个型号的模式属性作为所有彩灯的必需条件。

独立灯与组成员使用同一控制链。组入口没有额外优先级，实际命令按成员命令边界处理，已发送请求不因组变化或失败而跨路径重发。读取、写入、订阅及回读跟踪只涉及实际绑定和所支持的操作。

MiGate 不构造统一整组完成、原子成功或回滚语义；请求按成员返回实际受理或错误，Home 如何汇总 UI 由 Home 决定。未读到成员状态仍为未知，不能用其他成员或米家组的值代替。

通过米家 App 或实体操作改变成员状态时，更新该成员快照及当前 Matter 实例的报告，其他成员不随之伪造变化；服务重建期间仍更新外层快照，恢复后报告实际状态。颜色与色温切换、外部变化校正控制器计算状态及旧通知处理遵循相同的单灯规则。

## 验证与完成条件

### 自动化验证

测试按主题放入所属模块的 `tests/`，跨模块流程放在根目录 `tests/`，不为测试扩大生产代码可见性。覆盖以下行为：

- 能力解析与模型：四项能力的非空组合均可独立表达，不依赖固定灯型列表；缺少可选属性、固定参数与可控能力、未知状态与缺失能力得到正确区分；代表 MIoT 描述及合成描述覆盖绑定、范围和模式语义。
- 持久化：各能力组合及可选绑定往返恢复，已有 CT／RGB 缓存可读；能力列表重排、灯组角色变化及原数据目录重启不改变身份、endpoint、名称及配对。恢复不产生缺失能力的默认状态或绑定。
- Matter 映射：具备 OnOff 的全部八种亮度／色温／RGB 组合，分别覆盖独立灯和组成员；核对类型、ServerList、FeatureMap、属性、命令及实际处理器一致。没有 OnOff 的组合不伪造开关，也不声明要求 OnOff 的灯类型。
- 控制与状态：请求只触达真实属性；纯开关、调光、无亮度色温、无色温彩灯等组合可执行对应操作；不支持的命令返回不支持；未知值、通知、回读、渐变、连续控制、接管及模式切换按实际能力工作。断言缺失能力没有属性访问、处理器或虚构状态。
- 目录与成员：物理组和虚拟组按家庭目录接入，成员可具有不同能力，组缺少 RGB 不影响 RGB 成员；离线和首读失败不阻止有效组接入。读取失败保留关系，详情缺记录不误判删除，超出结构范围的组不组合。
- 拓扑与触发条件：纯父节点和各能力组合的子节点正确发布，同名成员可区分；关系变化即使成员实例不变也触发必要的服务重建，无重复控制端点或无效 PartsList；未确认的相关变更不提前改动无关组结构。普通状态变化、能力列表重排及无结构变化的目录同步不触发重建，同一批待发布结构变化合并处理。
- 重建与协议恢复：覆盖灯组创建、成员增删、解散及成员角色变化与通配读取、写入、命令、首次订阅和增量报告分片交错的情况；确认旧实例及其在途任务完整停止，旧遍历器不访问新结构，新实例在首个外部请求或恢复报告前完成拓扑与 `ConfigurationVersion` 的一致初始化。配置稳定且通信正常后自动恢复读取、控制和状态报告，不依赖用户手动重启 MiGate、重新配对或刷新；固定属性与版本满足报告一致性要求。
- 中断与清理：允许整桥 Matter 短时不可用，外层米家连接、发现和设备状态同步继续；未完成请求及渐变、Move／Step 等操作取消后不遗留动作所有权、剩余调度或长期“进行中”状态，已发送命令不重放，新操作可以正常执行。服务重建失败明确报错，不破坏持久化身份和协议数据。
- 身份及恢复：成员加入及退出、组解散、重加、重新排序、组身份预留复用、自动服务重建及原数据目录重启；组父端点和成员 endpoint 不冲突，名称、标签、Fabric、ACL、Groups 等协议配置保持，订阅恢复或重新建立后自动报告当前状态。
- 生命周期：确认成员删除后清理引用，缺少有效新关系时撤组并恢复其余支持成员为独立灯；存储失败不发布半套关系；单灯描述不兼容时沿用既有处理且不热替换能力，读取或解析失败不删减能力；仅能力列表重排不打断操作，成员角色变化按服务重建规则处理。
- 控制隔离：同组成员使用不同路径时仍各自选路，部分离线或失败不阻塞其他成员；无组 DID 属性操作或第二次命令分发；成员连续控制、接管、外部通知和颜色模式同步保持单灯语义。
- 回归：未分组单灯、单路插座及多路插座保留原控制、状态同步及恢复行为。

### 真机验收

真机验收覆盖代表色温灯、彩灯及其灯组的呈现、控制与恢复，以及临时灯组的创建、成员增删和解散。临时组使用未分组的受支持单灯，现有米家组配置保持不变。

纯开关灯、固定色温调光灯及其他没有独立灯具样本的组合，以能力解析、模型、控制、持久化及 Matter 自动化验证作为完成条件，不要求取得新硬件。它们的真机行为和 Home 控件效果尚未验证，留待有代表设备后确认；不以墙壁开关负载或浴霸内置灯替代独立灯具样本，也不将这些组合的 UI 纳入下表的通过要求。

| 项目 | 范围与通过条件 |
| --- | --- |
| 代表组 | 二楼空间的两个色温灯组：6 盏筒灯组与 4 盏过道筒灯组，成员为 `yeelink.light.light3`；另选包含左右两盏 `devcea.light.ls2307` 彩灯的卧室床头灯组。前两组为米家物理组，后一组为虚拟组。 |
| Home 呈现 | 自动形成每组一个入口，进入后能够单控成员，成员不重复显示为独立配件；允许首次核对并手动命名，使名称足以区分。 |
| 组入口控制 | 各组完成开关、亮度、色温各一轮；床头灯组额外验证整组颜色控制及色温／彩色切换，实际成员按目标变化。 |
| 成员单控 | 每组选至少一盏单独调整，确认其他成员不被误控；床头灯验证成员颜色控制及模式切换。 |
| 外部状态同步 | 每组选一盏通过米家改变状态，Home 自动同步；床头灯包含颜色变化。在无结构变更、服务稳定及正常网络下沿用 3 秒标准，整体持续观察 10 分钟，不能靠手动重启 MiGate 或刷新使值收敛。 |
| 独立灯与恢复 | 使用现有可用的未分组单灯，按实际能力抽查控制、模式及状态同步，不要求另备未分组彩灯；使用原数据目录重启一次，独立灯与组关系、控制恢复，名称、端点分配及配对保持；抽查单路插座及多路插座。 |
| 临时组样本 | 准备至少三盏属于当前家庭、已按受支持单灯接入且未加入任何米家灯组的灯，确认米家 App 允许共同创建灯组及编辑成员。按各灯实际能力验证控制。米家目前不支持单成员灯组，成员增删期间组内至少保留两盏灯。 |
| 临时组创建与成员增删 | 先用两盏灯创建临时组，确认自动形成一个 Home 入口并可单控成员；加入第三盏，确认其转为组内成员且没有重复配件；移除一盏，确认其恢复独立灯、原组及其余两名成员保留。每步允许自动重建 Matter 服务及整桥短时不可用；恢复后核对成员能力、控制及状态同步。成员 endpoint 全程保持，同一组的 DID 和父 endpoint 保持。 |
| 临时组解散 | 在米家解散临时组，确认 Home 撤销组入口，参与验收的灯均恢复独立入口及控制，成员 endpoint 保持；既有组配置不变，允许控制随整桥重建短时中断，恢复后抽查既有组及未参与编组设备的控制和状态同步。 |

临时组每一步均等待完整目录确认、自动重建的 Matter 服务重新可用及 Home 拓扑收敛后再进行下一步，分别观察目录发现、服务恢复与 Home 更新，避免多步操作被一次同步合并；不通过手动重启 MiGate、重新配对或手动刷新促使其通过。样本不足时，未执行的步骤保持待验，不能把解散后重建灯组当作原组内的成员增删通过，也不为满足样本数量而改动既有组。

每个样本只验证当时实际使用的路径，并记录其本地／云端情况，不重复完整的本地／云端故障矩阵。目录发现、服务重建、Home 拓扑恢复与灯光属性传播分开判断；3 秒仅用于服务稳定后的单灯同步，不作为目录发现、服务重建或 Home 重连的期限。单独记录从结构变化确认到 Matter 服务重新可用的耗时。自动重建服务或进程重启后的 Home 拓扑恢复沿用最长 20 分钟观察窗口，从重新提供 Matter 服务起计；该窗口不作为服务重建的耗时预算。未恢复即如实记录，不以重新配对掩盖问题。

真机验收只增删临时组的成员并最终解散临时组，不拆散既有米家灯组或改动其成员，以免影响米家自动化；不引入重叠组。部分离线、目录读取失败或信息未就绪，以及未提供界面入口的协议命令由自动化覆盖，不纳入真机验收，不要求完整灯协议符合性验收。

代表组自动形成总入口、成员单控和床头彩灯组的整组／成员颜色控件均为交付要求。首次手动命名不影响通过判定；其余展示或控制不符合要求时为未通过项，不能以手动编组、独立灯、仅色温组或额外总灯端点替代后宣布通过。
