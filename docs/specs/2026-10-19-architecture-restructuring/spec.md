# MiGate 全面结构整理

## 目标与范围

以 `168544f80c7f81c09cd3d6675651fd86a6465f91` 为设计基线，在同一轮中完成有效模型、配置核心、群组关系、来源所有权、命令仲裁、灯光策略与 MQTT 公共机制的整理。统一运行配置入口、缩小 Rust 接口范围、调整存储与测试边界均属于本轮交付内容。

采用按职责与状态所有权重构的方案：每类状态有明确管理者，模块通过有业务含义的操作协作；共用具体规则和协议机制。继续使用现有 Rust 单包及本地异步执行方式，复用已建立的设备协议与灯光算法。

成功标准是核心使用场景成立，重复表示和跨对象协调关系实际减少，规则能够独立测试。所有方向共同形成一个交付结果。

### 核心功能

- 米家认证、令牌与证书维护，单家庭接入，已准备账号的空桥启动。
- 现有单路与多路插座的独立通道控制和状态同步。
- 开关灯、调光灯、色温灯、扩展彩灯的能力解析与 Matter 映射；支持对应的开关、亮度、CT、XY、HS、渐变、Move、Step、Stop 及既有设置语义。
- 米家原生灯组接入、成员隐藏与恢复、虚拟组成员反馈，以及全员 `devcea.light.ls2307` 灯组缺失 RGB 的来源适配。
- 本地与云端控制和通知路径、连接恢复、运行中接入和移除、配置自动应用。
- 新格式下的账号、身份、端点、名称、配对和必要协议数据恢复。
- 通过终端和 Matter 观察实际服务配置、可用性、状态与命令结果。

本轮围绕这些既有能力整理，不扩展新的设备类别、厂商效果或 Matter 认证范围。[已知限制](../../known-limitations.md)中的产品边界继续作为范围依据。

### 兼容与行为调整

| 项目 | 本轮决策 |
| --- | --- |
| Rust 接口 | 按独立应用组织，可删除或收窄公开接口、兼容包装和测试专用入口。 |
| 终端输出与诊断 | 可随职责调整重组，保留控制与排障所需信息，不要求字符串逐字兼容。 |
| 旧数据 | 采用新数据库格式，不提供旧格式迁移。旧库被识别后明确拒绝加载，不自动删除或覆写。 |
| 新版本恢复 | 正常重启、连接恢复和配置重建保留身份、名称、端点与配对，不依赖重置。 |
| 原生描述生命周期 | 目录发现 MIoT 描述的 URN／版本变化时自动加载新描述，通过统一配置流程应用受支持能力。以新版向后兼容为前提，不增加新旧描述兼容性校验；实例内的原生描述不可变，更新按需整体替换实例，不保留原位绑定热替换和描述不兼容阻断分支。 |
| 协议与算法 | 继续遵守已声明功能的协议约束、发送边界和实际反馈语义；轨迹坐标、颜色转换与舍入沿用基线算法。 |

上述明确调整之外，核心行为按本文约定验证。旧测试对内部组织或历史限制的断言可以调整，不能用删除场景掩盖核心功能缺失。

## 职责与依赖

| 单元 | 状态与职责 | 交互边界 |
| --- | --- | --- |
| `device` | 有效逻辑描述、设备可用性与功能状态、每个 function 的命令协调器 | 提供状态观察、命令提交和写入请求结算；不依赖 Xiaomi 或 Matter。 |
| `configuration` | 配置输入、纯数据计划、身份和端点分配规则、配置比较 | 接收明确输入并产生计划；不读取数据库、访问网络或创建运行设备与任务。 |
| `app` | 应用组装、当前生效配置、提交与激活、来源和 Matter 生命周期 | 组合具体来源、存储、终端和 Matter。收拢当前根层 `publication` 与 `runtime` 的应用协调职责。 |
| `xiaomi/capability` | 原生描述、真实绑定及型号约束 | 将网络或存储边界提供的数据构造成有效原生模型，派生原生能力。 |
| `xiaomi/adapter` | 最新来源事实、成员和访问资格、选路、来源运行对象、群组执行与观测 | 导出不可变事实，接收已提交的来源配置；不分配 Matter 身份和端点。 |
| `lighting` | 轨迹、颜色数学、时间推进与动作进度 | 使用有效目标和设备命令接口，提供轨迹观测；不管理 Matter 报告状态。 |
| `matter` | 发布形状、协议命令规划、属性投影、端点设置、版本和报告 | 接收显式发布条目，调用设备接口；不自行重新读取来源或设备配置表。 |
| `storage` | 新格式编码、数据库事务、协议及认证存储、加载边界检查 | 读出有效数据，原子保存配置；设备能力与发布策略由所属模型和规划模块决定。 |
| `terminal` | 命令解析、配置与诊断呈现 | 每条命令取得一次当前生效视图，包括隐藏成员，通过统一设备接口控制。 |
| `xiaomi/mqtt` | 共用 MQTT 帧、握手、发送进度、保活与入站 QoS2 机制 | 返回协议事实；认证、订阅与业务处理由两个具体驱动负责。 |

`configuration` 使用设备以及来源、发布端导出的纯数据类型。固定发布形状由 Matter 的纯转换函数提供，应用层在收集输入时取得；规划器比较该形状，不另外复制一套 Matter 能力判断。

Matter 的发布输入由 Matter 定义，应用层构造并交付。终端的只读访问不暴露配置提交、来源内部槽位或运行资源。存储编码结构保持私有，消费者使用有效模型而非 SQLite 行或序列化对象。

不引入应用级统一事件总线、设备 actor 系统或通用来源插件框架。文件拆分服务于上述职责，新增包装必须拥有规则、状态或实际边界。

所有模块以已支持的结构稳定、MIoT 新版向后兼容为前提，不为假设性的内部结构变化增加兼容比较、重排映射或兜底分支。外部数据在网络、存储或命令边界构造为有效模型后，内部直接使用其约束；本轮此前已引入的同类处理也一并清理。

## 有效模型

### 逻辑描述

功能描述保留稳定功能键、名称和明确的功能种类。种类使用封闭类型表达插座和四类灯型：

| 功能种类 | 构造后成立的条件 |
| --- | --- |
| 插座 | 具备开关控制。 |
| 开关灯 | 具备开关控制。 |
| 调光灯 | 具备开关和亮度控制。 |
| 色温灯 | 具备开关、亮度和有效色温范围。 |
| 扩展彩灯 | 具备开关、亮度、有效色温范围和 RGB。 |

删除可分别修改的 `category` 与 `Vec<Capability>` 主表示。能力列表仅在诊断或输出需要时派生。类别、灯型及色温范围从同一个有效值读取，消费者不再调用可能失败的 profile 推导或重新验证能力组合。

范围类型通过构造保证非空有效区间、合法步长及必要的编码条件。原生量化网格与群组发布的逻辑色温区间具有不同含义，分别保留；不为了类型统一强求成员步长相同。Matter 单位换算属于表示边界，来源属性量化属于 Xiaomi 边界。

设备描述保证功能键唯一、拓扑非空；Xiaomi 的单灯 `main`、支持的插座通道和型号约束由来源构造边界检查。本轮不借此接纳额外拓扑或任意灯光能力组合。

### 原生描述与绑定

原生模型以真实绑定为依据。插座与灯具分别表达；灯具绑定按四类受支持 profile 携带必要属性，扩展彩灯的模式绑定仍可按实际描述缺省，缺少模式反馈时保持未知。

原生能力由绑定派生，发布能力由原生模型与已提交群组规则生成。两者用途独立：前者用于真实读写，后者用于设备逻辑接口和 Matter。RGB 修复不得向组 DID 补造原生 RGB 属性。

网络解析与数据库加载各自验证输入完整性，然后共用有效对象的构造约束。领域对象的字段和反序列化入口不能绕过构造约束。已有对象在内部传递、比较和使用时不反复验证。

删除只有固定取值且无行为读取的 `BrightnessConversion` 及对应存储字段。`ls2307` 跨服务绑定等型号规则继续集中在来源能力模块。

### 原生描述的加载与更新

原生描述在首次准入时加载，随配置保存。正常重启先从已提交记录恢复；运行期目录发现设备的实例 URN（包含 MIoT 描述版本）变化时，自动加载对应描述，并通过统一配置流程应用 MiGate 已支持的能力与量程。连接恢复、普通属性通知和未变化的目录不重新加载描述。

设计以新版 MIoT 描述向后兼容、保留已有能力为前提，不比较新旧描述的能力包含关系或属性编号来做兼容性准入校验，不增加绑定迁移、描述不兼容阻断或对应的持久禁用机制。仅保留新描述自身在网络边界的解析、支持范围判断和有效模型构造。新描述获取、构造或配置提交失败时继续使用旧配置，并给出诊断。

每个运行实例使用不可变的原生描述。新版本改变 MiGate 实际使用的控制描述时，准备新实例，在配置成功提交后整体切换并重建 Matter，保留身份、适用端点、名称和配对；不在旧实例上逐项改写绑定。只有 URN 等元数据变化而实际控制描述不变时，只提交元数据，不替换实例或重建 Matter。配置比较用于决定复用、替换和版本变化，不承担新旧描述兼容性校验。

群组原生描述遵循同一更新规则；群组的有效逻辑能力、量程、RGB 修复及反馈规则由当前已确认关系和原生描述派生。成员增删、描述首次补齐或新版描述生效时重算受影响组，并与成员配置一并提交。

确认移除后重新准入重新加载描述，暂时离线不构成重新准入。自动更新限于目录可发现的 URN／版本变化，不主动轮询同一 URN 下的静默修改；新增功能仍受 MiGate 已实现的设备类别和能力范围限制。本轮不新增手动刷新入口，不以清库重新配对作为日常更新或恢复手段。

### 命令目标

灯光目标明确区分亮度和颜色；颜色再区分色温与 RGB。目标自身决定维度，亮度与颜色不能同时塞入一个目标，也不能构造空目标。必要的关联电源目标显式携带；单纯调节不隐含开关。

数值有效性在命令构造边界检查，内部轨迹生成有效目标。能力是否支持该命令、动作 token 是否仍属于当前实例和维度，在接收操作及异步执行边界检查。后者是运行权限检查，不能因模型已验证而省略。

## 配置规划、提交与激活

### 四种对象

| 对象 | 内容 | 生命周期 |
| --- | --- | --- |
| 来源事实 | 最新有效原生描述、家庭范围、确认成员关系及准入信息 | 首次准入或目录发现 MIoT 描述版本变化时加载原生描述；以不可变值交给规划。 |
| 配置计划 | 下一份完整配置、身份与端点分配、实例增删或替换、群组变化、版本及重建原因 | 一次规划结果，纯数据，不持有 receiver 或待启动任务。 |
| 激活资源 | 新建实例、一次性 receiver 及明确安装操作 | 由应用流程独占，提交成功后消费；放弃时仅丢弃未安装资源。 |
| 生效配置 | 已提交配置值及对应运行设备引用 | 由应用持有，整体切换；Matter 与终端从同一版本取得视图。 |

最新来源事实与已提交事实表示不同时间点，必须允许同时存在；差异来自设备准入、移除、新版原生描述和群组关系等配置变化。来源保留最新事实与加载状态，已安装实例及生效配置引用其所属版本的不可变描述。减少的是 `native_confirmed`、`candidate`、`admitted` 间重复解释、独立修改完整描述和协调原位绑定热替换的路径，不把待提交的新版本误当成已生效版本。

### 规划输入与结果

规划输入包括来源事实、当前已提交配置、保留身份与端点、撤权记录，以及 Matter 固定形状。规划明确输出每个设备的复用、新增、移除或替换，发布与隐藏集合，群组执行规则，配置版本和 Matter 重建原因，不输出独立的原生绑定热替换操作。

规划使用稳定设备键比较目录集合，目录设备列表重排和等价重复同步不造成实例替换、版本增加或重建。单设备 MIoT 功能结构及顺序以稳定、向后兼容为前提，不为假设性的功能乱序增加排序、规范化或顺序无关比较；测试也不人工制造此类兼容需求。新增身份所需的随机值由应用提供，规划器内部不调用随机源、数据库或时钟；端点分配根据预留集合确定。

实例复用比较功能身份、完整逻辑控制描述及实际使用的原生控制描述。原生控制描述变化时整体替换受影响的来源运行对象和设备实例；只有群组派生逻辑描述变化时替换逻辑实例，复用未变化的原生来源。实例替换时重建 Matter；映射出的固定形状相同时，固定版本保持不变。保存名称或 URN 等纯元数据变化可更新配置并复用原对象，不据此重新建立订阅。

固定形状包括实际发布集合、功能结构、设备类型及对应 cluster/feature、声明能力与量程、影响 Descriptor 的功能信息。固定版本比较使用 Matter 的规范形状，等价 Kelvin 表达映射成相同 mired 区间时按相同发布量程处理。

新身份的 ConfigurationVersion 从 1 开始。已有身份以“是否发布、已发布时的固定形状”作为版本比较项，该项变化时递增设备版本；整体发布集合或固定形状变化递增根版本。隐藏或移除后重新发布属于发布项变化，因此无需额外保存一份历史能力描述来判断旧身份的版本。仅关系或运行实例变化导致的重建不额外增加固定版本。版本溢出或端点耗尽是明确的配置错误，保留当前配置并给出诊断，不分配冲突端点或回绕版本。

### 应用顺序

1. 收集最新输入，生成候选计划。没有变化时结束。
2. 候选计划需要重建时，结束动作并完整释放旧 Matter runner，然后重新取得最新输入和计划；来源连接继续工作。重新规划已无变化时，直接恢复当前生效配置的服务。
3. 按最终计划准备未安装资源。新任务和新来源实例尚不取得控制或通知权限。
4. 需要重建时，清除旧 Matter 持久订阅；清理失败则不提交配置。
5. 在数据库事务中保存完整新配置，并清除本次重新确认准入对应的撤权记录。
6. 提交成功后同步安装来源、设备实例与群组配置，切换生效视图并通知消费者。最终输入收集、资源准备、提交和内存切换之间不出现 `await`。
7. 需要重建时，使用新生效配置启动 Matter。纯元数据变化在同一应用流程内完成，不重建 Matter。

安装操作消费计划明确给出的变化类型，不重新推断一次变化。所有成员和群组配置安装完毕后，再启动所需刷新和群组状态重算。激活阶段不执行可失败的外部 I/O，也不再次进行输入合法性检查。

Matter 取得显式设备引用、身份、端点和版本，不在构造期间将新数据库行与旧 registry 拼装。运行中的固定 Matter 模型只使用构造时的配置。

### 更新与失败规则

- 首次、重新准入及 MIoT 描述更新共用原生描述构造边界，明确拒绝支持范围外或无效的描述；已有实例在新版成功提交前继续使用旧描述。独立设备与群组的有效能力、量程变化均进入统一配置流程，不另做新旧描述兼容性校验。
- 纯连接恢复与普通属性变化不重建 Matter。发布形状、发布集合、被服务实例、有效群组关系或家庭范围变化需要重建。
- 同一设备键和功能键继续使用保留身份、名称与适用端点。隐藏或移除的端点不分配给其他设备。新增功能获得新预留；已有功能退役后，其预留仍保留。
- 配置准备或事务失败时保留最后完整生效配置。若旧 runner 已停止，则用该配置恢复服务并按应用层重试策略重新规划。订阅已清除但配置提交失败时，旧配置恢复后等待控制器重新订阅。
- 启动恢复只采用当前账号及选定家庭范围内的配置。来源启动失败或收到退出信号时停止准备，丢弃未安装资源；范围切换先撤销旧来源权限，再按新范围规划。
- 已确认删除或撤权立即关闭相应控制权限，并写入独立的持久撤权记录；启动恢复先应用该记录。重新准入需要新的有效确认，旧快照、迟到结果和配置提交失败均不能恢复权限。
- 撤权记录无法持久化时，将错误上报为应用失败并停止服务；不宣称已安全保存撤权，也不继续运行一个重启后可能恢复旧权限的配置。
- 数据库已提交后，Matter 启动发生致命错误时明确停止并报告错误；新提交仍是恢复依据，不伪装成提交失败或悄悄回退旧配置。
- 运行状态和未完成动作不持久化。启动时状态重新观测，中断动作不重放。

名称写入经过统一的应用配置入口：保存成功后同步更新当前名称和运行对象；来源目录更名不覆盖已保存名称。单纯设备 NodeLabel 变化不增加固定形状版本。配置在等待旧 runner 退出期间发生名称写入时，最终重新规划须取得已保存的新名称。

## 新存储格式

新格式使用 schema version 8。保留账号认证、桥接身份和 Matter 协议 blobs 的独立存储职责，将当前设备配置相关的分散表示收拢为一个完整配置记录。

完整配置采用存储模块私有的、带明确字段的 JSON 编码结构，保存在单例配置行中。初始配置允许设备集合为空，家庭范围按现有认证与首次绑定规则确定。内容为：

- 当前家庭范围与已提交的原生设备描述、真实绑定。
- 已确认的群组类别、成员关系及其可发布条件所需事实，包括暂时不活跃的确认关系。
- 设备与功能身份、端点预留、保存名称、根及设备配置版本；历史预留可以没有当前来源实体。

发布描述、发布/隐藏集合、群组正反索引和 RGB 修复计划从该记录确定性重建，不再分别保存可相互矛盾的 `category`、能力列表、首功能镜像和逻辑修复描述。原生绑定与派生的发布能力不混写。

撤权记录作为独立的小表保存，满足完整配置事务失败期间的恢复要求；成功重新准入与撤权清除处于同一事务。账户与协议数据不纳入每次设备配置记录的重写。

加载时先验证格式、结构、键、身份及端点一致性，再通过领域构造器恢复有效模型，最后生成逻辑配置。单功能设备与唯一功能共用端点，多功能设备的父端点与各功能端点分离；历史预留也遵守该约束。损坏记录明确报错，不能跳过损坏部分、补造默认能力或偷偷新建桥接身份。

首次启动创建新格式。旧库不迁移，不保留旧版序列化分支及迁移测试。项目处于开发期，运行指南仅说明当前版本的操作与恢复办法，不提供旧用户迁移步骤。

## 来源运行对象与订阅切换

每个设备槽位管理一个当前来源运行对象，引用所属配置的不可变原生控制描述，内部拥有连接附着、本地和云端订阅状态、当前通知来源、刷新调度及观测代次。删除 `Session.devices`；Session 只持有连接、连接级请求与访问恢复调度。新版控制描述通过配置提交整体替换来源运行对象，不为原位绑定热替换建立独立的更新流程。

连接附着记录明确的连接身份。同一连接重复协调不重复启动工作；连接断开只撤销该附着，仍合法的云端工作可以继续。来源实例退休统一撤销其订阅、未发送操作、刷新和投递资格。

本地与云端各自拥有准备状态；当前有效通知来源单独表达。因此旧来源仍有效时，可以同时准备新来源，新来源完整就绪后再切换。过期 SUBACK 或通知不能把旧订阅重新激活。

外部模块使用连接、断开、准备完成、来源失效、请求刷新等操作，不直接修改 `subscribed`、`running`、`exhausted` 和 generation 字段组合。失败与重试状态由对象内部转换。

连接身份、来源实例身份、观测来源代次和访问条件代次有不同失效原因，分别保留；不另设描述热替换专用的绑定代次。刷新需求的 pending、inflight、后续脏读归现有刷新状态对象管理；首次 poll 前丢弃应归还需求，旧读取不能消费新需求。

异步任务可以持有退休对象以完成收尾，但旧引用不再代表当前控制或通知权限。来源实例退休不能直接销毁已发送写入的原始回执。

## 功能命令与按 DID 串行写入

### function 内的命令协调

一个私有协调器管理电源 FIFO、每个灯光维度最新待发送帧、整体出队顺序、在途操作和动作结果。替代当前 `Queue`、`LightCoordinator` 与 `RuntimeState` 取消流程之间由调用者完成的协调。

电源命令继续按既有 FIFO 规则处理；灯光帧按维度合并，保留相对于另一维度与电源命令的顺序。新动作接管同维度旧动作；颜色维度包含 CT、XY、HS 对应控制，亮度独立。Off 结束灯光动作并撤销相应未发送工作，Stop 结束指定维度；取消原因和受理结果可以被观察。

写入请求由协调器交给来源执行。来源只能检查当前资格、在实际提交边界标记发送、结算回执或未发送失败，不直接操作协调器内部队列和完成对象。等待者退出、动作结束和发送回执结束分别处理。

不需要实际写入的已确认同值目标具有明确的无写入结算路径；仍需要模式切换或启动真实过渡的操作不能因此误报受理。首帧受理、最终动作结束和诊断结果的语义各自保留。

### 实际写入的生命周期

| 对象 | 结束条件 |
| --- | --- |
| 逻辑动作 | 完成、失败、Stop 或被接管。 |
| function 在途写入 | 其原始请求结束后释放该 function 的顺序限制；未发送替换可以提前退休该帧。 |
| 灯具 DID 的实际写入 | 原始请求成功、失败、超时或连接终止后，才允许同 DID 下一条实际写入。 |

“按 DID 串行写入”是同一灯具的实际请求排队规则。独立灯控制、组成员 RGB 补写、配置更新或同 DID 重新准入后的来源实例共用同一个 DID 写入管理对象。它与 function 命令协调器分别管理传输竞争和逻辑动作。

请求已发送时，即使动作取消、连接切换、配置更新替换来源实例或同 DID 删除重加，旧回执仍保留所占用的写入位置，直到原始请求结束。只能对明确未发送的请求重新选路；可能已发送或结果不明的操作不跨路径重发。

未发送与已发送以各传输实际提交边界为准。中枢在首字节写出时同步标记，HTTP 沿用其实际提交边界；出队或创建 Future 不代表已发送。

回执只负责结算操作。灯光状态由有效通知或读取更新；插座的受理后状态更新规则集中在来源观测逻辑，保留新通知优先于旧写入结果的规则。命令协调器不推断设备实际状态。

## 已提交的群组规则

来源规划从候选配置事实生成不可变群组关系图，包含组类别、稳定成员键、反向成员关系、反馈规则和 RGB 修复归属。只有该配置成功提交后，图才随生效配置整体替换，没有独立更新入口。组类别或反馈来源改变时，相应订阅和观测权限随配置重新建立。

成员隐藏、独立灯识别、共享成员动作接管、刷新来源和状态重算均查询该图。成员状态变化只按反向关系通知受影响组。实际状态仍取当前有效成员快照，图不保存成员状态或永久绑定句柄。

群组规则集中为可独立调用的规划、聚合与目标选择函数：

- 原生功能写组自身 DID。物理组原生反馈来自本体；虚拟组反馈来自成员。
- 虚拟组任一有效成员开启则为开，全员确认关闭才为关，其他情况为未知；亮度采用既有开启成员或全关设置值汇总规则。
- 色温、RGB 与模式取同一稳定代表成员，优先选择亮着且当前颜色有效的成员，同优先级按 DID 排序。无法表达的反馈为未知，不把实际反馈限幅成另一个值。
- RGB 修复仍限定为原生组缺失 RGB、全员满足 `ls2307` 型号和真实绑定约束的情况。原生开关、亮度、色温不补写成员模式或电源。
- 修复动作首帧根据生效图捕获当时合法的成员实例与绑定；后续帧不追加新成员。发送时只向当前确认亮着且权限有效的成员写 RGB。至少一个受理即满足组受理，其他成员继续结算；没有可执行成员或全部失败则失败。
- 明确新命令通过关系图接管共享成员的相关组动作；Stop 只停止目标组自身。组及成员通知用于状态同步，独立灯保留外部通知接管和自身回声识别。
- 关系变更导致的配置重建结束旧动作，已发送结果继续结算，恢复后不重放。暂时离线和未知状态不改写已确认能力或成员关系。

组原生描述、成员描述缺少时，按已知有效原生能力决定接入，缺少的反馈为未知；不能以未确认信息补造 RGB 修复条件。完整目录读取失败不解释为成员清空或设备删除。

## 灯光规划、轨迹与 Matter 报告

Matter 命令规划接收明确的能力、设置、实际状态和必要的当前轨迹信息，返回忽略、停止或执行计划。协议解码和错误映射位于 handler 边界；能力限制、目标计算、Options、WithOnOff、OnLevel 等规则由可直接测试的规划函数处理。

轨迹层负责时间、采样、目标变化、最终帧和动作进度，沿用既有坐标、转换、舍入和 HS 路径算法。它向报告层提供原始剩余时长、动作身份和受理/结束观测，不编码 Matter RemainingTime，不维护报告修订号或通知标记。

Matter 报告模块统一管理：

- 状态投影及 HS/XY 表示元数据，包括需要保留的 hue hint。
- RemainingTime 的十分之一秒编码、cluster 上限和短过渡安静上报规则。
- 已编码状态对应的 DataVersion，以及报告节流、未知状态变化和终止时的通知。
- 属性读取前的版本同步，确保 DataVersion 过滤能观察到最新编码变化。

版本比较游标与报告通知游标用途不同，保留在同一个报告所有者内部；删除的是轨迹层与 Matter 间额外的 remaining revision/report 同步协议。动作首帧在仍拥有维度时受理，才取得相应表示元数据；调用等待者退出不影响原始回执完成该处理。

协议 handler 测试继续验证 TLV、命令和属性范围、错误映射、DataVersion 与订阅接线。范围、舍入、时间及报告判断测试直接落在规则上，不创建数据库、完整 Matter 节点或协议交互模型。

## MQTT 公共机制

将现有 `xiaomi/mqtt.rs` 扩展为按职责组织的私有模块，两套驱动使用同一组具体机制：

| 机制 | 公共职责 | 驱动保留的职责 |
| --- | --- | --- |
| 帧编解码 | 包边界、长度、缓冲上限和公共编码 | 业务载荷和主题解释。 |
| MQTT 握手 | CONNECT 写出、flush、CONNACK 接收与公共协议检查 | TLS 与凭据、CONNECT 身份参数、认证错误和来源特定能力要求。 |
| 发送帧 | 部分写、offset、flush 完成与进度返回 | 请求是否仍可发送、取消范围、请求截止时间及发送阶段。 |
| 保活 | 最近完成发送、PING 等待与下一次协议期限 | 与业务请求期限合并、连接失效后的恢复策略。 |
| 入站 QoS2 | 包号、容量、重复内容检查与握手状态 | 捕获并验证订阅身份、决定是否交付业务消息。 |

公共 QoS2 接收项可以携带由驱动提供的不透明投递上下文；重复 PUBLISH 不覆盖第一次捕获的上下文。PUBREL 到达时，由原驱动验证该上下文仍有效，不能把旧消息重新归属给新订阅。握手清理和业务投递资格独立。

发送组件每次返回实际写入进度时，中枢驱动在同一次 poll 内立即更新 `RequestStage` 并调用 `first_send`，然后才能继续其他工作。发送资格和到期检查仍在每次零字节待发送轮询前执行。不能等 flush 或下一次异步唤醒才补记发送状态。

两套驱动保留各自的请求分类、订阅代次、认证与错误策略；中枢出站业务 QoS 交换仍由中枢驱动管理。公共机制只承担共同的状态转换，不增加可插拔业务协议框架。

## 统一运行入口、接口与诊断

生产只有一个由已提交配置驱动的运行入口。删除 `PreparedRuntime.publication: Option<_>` 所支持的 static/configured 双分支、`run_prepared_bridge` 和终端对应的两套配置来源。

来源准备完成后只交付实际需要的来源句柄与事实，不再返回随后丢弃的 registry。启动恢复、初次目录应用和运行中更新使用同一个配置核心。

测试在所属模块通过辅助构造准备有效配置、可控来源和 I/O，再进入同一运行生命周期。低层模块测试直接调用所属接口；集成测试通过正常应用输入、存储和协议对端，不维持生产中的测试专用运行模式。

终端保留日常 `list`、`status` 和定向 on/off 控制。配置状态、应用失败、未接入原因、控制与通知路径以及动作和实际写入结果可查询。一次命令只观察一个生效配置版本，隐藏成员仍可查看和控制；诊断直接投影真实所有者的状态，不复制另一份路由或订阅判断。

Rust 可见性按真实调用关系收窄。删除无生产用途的旧便利入口和兼容包装，保留二进制组装和真实模块边界需要的接口；不得为了迁移测试而把私有字段改为公开。

- 原生灯组入口、成员隐藏、虚拟组状态、`ls2307` RGB 与模式切换及关闭成员跳过。
- 实际具备条件的本地和云端路径、断线恢复、配置变化后的控制与订阅恢复。
- 初始化之后的正常重启、配置重建和恢复无需再次清库或重新配对，身份、名称和端点保持一致。

关系变更使用独立临时组，不修改已有业务组和自动化。断线恢复可通过仅影响 MiGate 进程的连接中断验收，不要求物理断网；该方式不覆盖网关断电或家庭网络整体失效。控制器界面刷新与 MiGate 服务恢复分别观察，沿用已知的重新订阅边界；重开「家庭」后恢复与控制器自动恢复分别记录，不将前者计为自动重订阅通过。未执行或缺少条件的项目如实说明，验收结果只记录在任务对话中。

## 实施顺序与交付条件

本轮在一个整体设计下按依赖顺序实施，各步骤均属于同一次交付：

1. 建立有效逻辑/原生模型及目标类型，替换调用者；定义并实现新存储格式。
2. 建立配置计划、提交与激活，统一启动和运行入口；生成并安装群组关系图。
3. 整理来源运行对象、连接附着与订阅状态，以统一配置流程整体应用新版描述并删除原位绑定热替换路径；合并 function 命令仲裁，保留独立的原始回执和按 DID 串行写入。
4. 集中群组执行和反馈规则，分离灯光命令规划、轨迹与 Matter 报告，迁移对应规则测试。
5. 提取 MQTT 公共机制，完成两套驱动接线、接口收窄和历史入口清理。
6. 完成核心场景集成回归、全量检查及 README、运行指南和必要的已知限制更新。

迁移期间可以逐步替换消费者，最终结果不能留下旧实现、双路径开关或兼容包装来维持测试。

| 方向 | 必须出现的结构结果 |
| --- | --- |
| 有效模型 | 删除可矛盾的类别/能力主表示和描述与绑定反复对账；有效目标自身决定维度。 |
| 配置核心 | 纯计划不携带运行资源；一次性资源独占消费；Matter 与终端消费同一提交版本。 |
| 运行入口 | 删除 static/configured 双运行分支及测试专用生产入口。 |
| 群组规则 | 一个随配置生效的关系图和所属规则实现，调用者不再各自扫描并解释成员关系。 |
| 来源所有权 | 删除 `Session.devices`、双侧登记维护和原位绑定热替换；描述在实例内不可变，新版通过统一配置流程整体应用，订阅状态通过所属对象操作。 |
| 命令所有权 | 外部不再同时协调电源 Queue、LightCoordinator、取消事务与 active 完成对象。 |
| 灯光策略 | 报告规则归 Matter，删除轨迹层报告标记及跨层同步计数，细粒度规则测试无需整套服务。 |
| MQTT 机制 | 两套驱动共用具体状态组件，删除对应重复实现；业务语义仍由驱动负责。 |
| 存储与接口 | 新格式无旧能力镜像或兼容分支；API 按真实用途收窄。 |
