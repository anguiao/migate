# 门窗、运动与人体存在接入

## 目标与范围

以 `0ddb475` 为代码基线，新增门窗开合、运动检测和人体存在三类只读状态能力。使用现有本地中枢与米家云端来源，向 Matter 发布标准传感器状态，并在 Apple Home 中验证状态显示与自动化入口。

每项能力独立识别、独立维护状态和来源，再组合到所属物理设备。照度等环境测量与整机电量沿用已有能力。人体存在本轮只接入整机状态，不接入分区；不增加灵敏度、检测间隔、自定义无人时长设置、逐次运动事件历史或自动化规则引擎。

更新依靠首次读取、来源恢复读取及真实通知，不增加定时轮询、MiGate 无人倒计时、新网关协议或主机蓝牙扫描。原生运动事件用于更新运动状态，不单独形成 Home 中的事件历史功能。

## 设计选择

三类能力共用状态模型、来源生命周期和父子端点组合。运动恢复直接使用原生无移动时长。

以中枢和云端提供的描述、状态与通知为可信依据，不额外推测设备真实状态，不为假设性的上游异常增加校验、兜底或恢复机制。边界解析与实际权限、连接、来源生命周期检查沿用已有约束；读取和通知竞争复用既有机制。

新增 `contact`、`motion`、`occupancy` 三种稳定功能键。功能种类与可读状态明确建模，不复用插座的开关命令或控制队列。内部可以共享包含未知状态的二值状态存储，各功能保留自己的语义：门窗的活动态为打开，运动的活动态为检测到移动，存在的活动态为有人。

含任意测量或本轮状态能力的物理设备，统一发布物理父端点及独立功能子端点；单项状态设备也使用这一结构。共享电量属于物理父端点。同机已有受支持控制、测量与状态能力可以组合，各自维持原有语义和权限。

## 能力识别与状态语义

### 识别原则

按标准 MIoT 服务和属性、事件类型识别，不以型号、设备名称或固定 `siid`、`piid`、`eiid` 建立接纳白名单。属性绑定和枚举数值取自实际描述；型号样例仅用于说明与验证。

每台物理设备每类最多生成一个状态功能。门窗和运动按描述顺序取第一个合格候选；存在能力只检查首个标准存在服务中的状态属性，该属性不满足能力要求时不改用后续分区。其后的同类分区服务不展开。`xiaomi.sensor_occupy.p1` 的整机服务在前，分区服务在后。

三类状态所用的属性均需声明 `read` 和 `notify`。运动功能还要求同一运动服务提供 `motion-detected` 事件与 `no-motion-duration` 属性，以形成可触发、可恢复的能力。只有运动事件而没有本轮认可的原生恢复属性时，不生成运动功能；同机其他有效能力仍可接入。

### 门窗开合

在标准 `magnet-sensor` 服务（`0x7827`）中识别以下两种表达，优先使用 `contact-state`：

| 原生表达 | 状态解释 |
| --- | --- |
| `contact-state`（`0x007C`），布尔值 | `true` 表示接触、关闭；`false` 表示分离、打开。 |
| `status`（`0x0007`），枚举 | 从 `value-list` 的 `Open`、`Closed` 语义取得打开、关闭对应的原生值。 |

枚举的数值由描述建立映射，不把 `1`、`2` 写成所有门窗设备的固定规则。只有能明确区分打开和关闭时才形成能力。

门窗状态使用属性读取及通知，不根据 `open`、`close` 事件名称推断状态。部分公开描述的事件注释存在不同用途，不能代替属性的明确开合语义。本轮不接入拆卸、门未关提醒或按键事件。

### 运动检测

在标准 `motion-sensor` 服务（`0x7825`）中绑定 `motion-detected` 事件（`0x5001`）与 `no-motion-duration` 属性（`0x00CB`）。无移动时长为以秒表示的非负整数。

| 有效输入 | 运动状态 |
| --- | --- |
| 当前活动通知来源的实时 `motion-detected` 事件 | 检测到移动。 |
| 无移动时长为 `0` | 检测到移动。 |
| 无移动时长为有效正值 | 无人移动。 |
| 读取失败或尚无有效输入 | 不能按“非零”解释；按运行状态规则保留已有状态或保持未知。 |

不枚举 `120`、`300`，也不按属性范围的步长生成时间更新。正值之间的变化仍然是同一个无人移动状态；连续运动事件或事件之后的 `0` 不制造额外的无人到有人跳变。

`0` 是该属性已明确的复位语义，即使描述中的正时长范围从 `120` 开始，也不能用测量量程检查排除 `0`。无移动时长属于状态输入，不作为新的环境测量功能发布；其范围和步长不构成 MiGate 的恢复计时器。

`custom-no-motion-time` 是另一个属性，本轮不用于运动恢复，不读取或修改它来实现无人延时。事件参数中的照度也不替代已有照度属性链路；照度继续独立读取、订阅和报告。

### 人体存在

在标准 `occupancy-sensor` 服务（`0x78C0`）中识别 `occupancy-status` 属性（`0x0166`），从枚举语义构造映射：

| 描述中的语义 | 存在状态 |
| --- | --- |
| `No One` | 无人。 |
| `Has One`、`Has Someone` | 有人。 |
| 声明的 `Quick Check`、`None` 等未给出确定有人／无人含义的状态 | 未知。 |

明确的未知枚举是一次有效观测，会将当前状态更新为未知；它与读取失败不同，后者不会单独清除已有有效状态。存在属性不能套用无移动时长的“非零即无人”规则，也不能把所有非零枚举当作有人。

### 公开描述样例

以下公开 MIoT 描述作为静态能力与协议测试样例。

| 型号样例 | 功能与绑定 | 原生表达 |
| --- | --- | --- |
| `isa.magnet.dw2hl` | 门窗属性 `2 / 2` | 布尔 `contact-state`。 |
| `linp.magnet.m1` | 门窗属性 `2 / 1004` | `1: Open`、`2: Closed`。 |
| `xiaomi.motion.pir1` | 运动事件 `2 / 1008`；无移动时长 `2 / 1024` | 事件＋秒数属性。 |
| `izq.sensor_occupy.trio` | 存在属性 `2 / 1` | `0: No One`、`1: Has One`。 |
| `linp.sensor_occupy.hb01` | 存在属性 `2 / 1` | `0: No One`、`1: Has One`、`2/3: None`。 |
| `xiaomi.sensor_occupy.03` | 存在属性 `2 / 1078` | `0: No One`、`1: Has One`、`2: Quick Check`。 |

## 模块职责与数据流

| 模块 | 本轮职责 |
| --- | --- |
| `xiaomi/capability` | 解析所需事件描述，新增独立事件绑定及三类状态绑定；构造枚举语义映射；与已有测量、控制能力组装。 |
| `xiaomi/cloud/notifications`、`xiaomi/central` | 在已有连接上增加事件订阅、取消订阅与消息解码，复用 MQTT 交付和连接生命周期。 |
| `xiaomi/adapter` | 按功能管理属性和事件订阅就绪、来源选择、首次与恢复读取、观测顺序和诊断；将有效原生输入转换成状态观测。 |
| `device` | 保存门窗、运动、存在的当前状态及观测元数据，提供只读快照和变化通知。 |
| `configuration`、`storage` | 将状态能力、绑定和映射纳入当前配置、端点规划和原子提交；持久化身份与发布结构。 |
| `matter` | 提供门窗与占用集群的状态投影、未知状态处理、数据版本和订阅报告。 |
| 终端界面 | 显示原生状态输入、解释后的状态、来源与时间、各订阅状态及相关诊断。 |

数据流保持为：原生描述 → 能力模型 → 配置规划与提交 → 来源读取／订阅 → 状态观测 → 设备状态 → Matter 投影与报告。

现有“不是测量就是控制”的判断需要明确为控制、数值测量、状态传感三类，避免将只读状态送入写命令、灯组控制或开关拓扑检查。纯控制设备维持现有布局；灯组只隐藏成员控制功能，成员测量、状态及共享电量仍归原物理设备。

## 事件与来源管理

### 事件订阅

事件绑定使用 `siid / eiid`，属性绑定继续使用 `siid / piid`，二者不互相借用字段或混淆编号。本地 session 内的属性与事件共用订阅登记、交付代次失效和按范围退订流程，各自保留绑定类型与消息解码。描述解析保留本轮所需事件及其参数定义，不建立通用事件历史存储。

云端使用既有 MQTT 连接的 `device/{did}/up/event_occured/{siid}/{eiid}` 主题；本地中枢使用 `appMsg/notify/iot/{did}/event/{siid}.{eiid}` 路径。沿用上游协议中的 `event_occured` 拼写，不为该能力增加另一种连接协议。

消息在对应来源边界关联设备、绑定、连接与订阅代次。MQTT 重复交付沿用现有协议处理；状态更新自身保持幂等。不增加以墙钟时间或自定时间窗口过滤运动事件的机制。

事件与属性快照必须区分：实时运动事件可以更新运动状态；保留的事件消息不作为新运动输入。属性的保留消息与主动读取作为状态快照处理，不重放成一次新事件。

### 来源选择与就绪

沿用本地优先、云端补充的既有来源选择，读取路径与通知来源分别选择，不要求二者一致。每个功能独立判断可读路径、通知就绪与诊断；一个功能失败不撤销同机其他功能已经成立的链路。

门窗和存在分别维护其状态属性订阅。运动同时维护事件订阅和无移动时长属性订阅，两者共同决定完整同步是否就绪。运动事件与无人时长的推送通知使用同一个活动通知来源；主动读取沿用独立选定的可读路径，可以更新另一来源通知形成的状态，不增加跨来源缓存仲裁。

只读路径可用时仍可取得状态快照，但不把读取成功当作通知同步已经就绪。订阅失败按实际绑定诊断并沿用有限恢复机制；对应功能显示同步受限。来源完整就绪后建立其活动通知归属，只接受当前活动通知来源的通知和当前有效读取路径的结果，已退出的连接、订阅、读取请求或设备生命周期中的迟到输入不得生效。

### 启动、恢复与静默

| 情况 | 当前状态与动作 |
| --- | --- |
| 程序启动 | 三类状态均为未知；为每项可读状态主动安排首次读取，同时准备对应通知订阅。 |
| 首次读取成功 | 立即采用明确的有效状态；原生未知枚举仍保持未知。 |
| 首次读取失败 | 保持未知并记录诊断，等待后续有效读取或通知。错误码不承担状态含义。 |
| 已有有效状态后单次读取失败 | 保留状态并记录诊断，不推断无人或关闭。 |
| 当前来源真实断开、失去必要授权、同步连续性中断或切换 | 保留最近一次有效观测及其时间，单独更新来源与同步诊断；恢复有效来源后重新读取并接受通知。连接变化本身不产生状态变化。 |
| 收到原生未知枚举 | 将该功能状态更新为未知，保留对应原生输入用于诊断。 |
| 正常静默 | 保持状态，不增加统一过期时长，不推断设备离线。 |

首次读取不依赖整台设备其他功能的订阅完成。选定通知来源就绪后，若该来源尚未提供有效状态通知，则使用就绪后发起的读取建立基线，避免初始化读取与订阅建立之间漏掉状态变化；尚未发出的首次读取可以承担该次读取，所需读取仍走当前有效读取路径。当前活动通知来源已有有效状态通知时，直接以该通知为基线，不再为本次通知来源就绪额外安排恢复读取；运动事件和有效的原生未知枚举也属于状态通知。这是生命周期触发的读取，不是定时轮询。

读取路径恢复或切换时沿用既有恢复读取，不重建仍有效的通知订阅；通知来源恢复或切换时按上述规则建立订阅与状态基线。状态、事件及观测时间不持久化；正常重启后的恢复依赖上游有效读取或通知，而不是上次运行的旧状态。

三类状态与已有数值测量一样，在来源中断或切换期间保留最后一次有效观测；保留值不代表通知同步正常，也不保证设备本体在线。启动尚无有效观测或收到原生未知枚举时，状态仍为未知。物理设备可用性继续由实际功能路径汇总，不因单项状态未知而把整台设备直接判离线。蓝牙与代理设备仍需区分获取通道可用和本体在线状态。

### 观测顺序与诊断

复用来源代次和读取请求标记，保证后到的旧读取结果不能覆盖请求期间收到的新通知。运动事件与无移动时长属于同一功能的状态判定，因此事件也必须推进该功能的观测顺序，使事件之前启动的无移动时长读取失效；不能只在属性自己的序号上处理竞争。

通过既有来源代次和请求生命周期检查的有效读取结果与通知按接收顺序解释，不以缺失或精度不一致的来源时间排序，也不因读取与通知来自不同路径而额外筛选。来源更新时间存在时保留，缺失时保持未知；接收时间不能冒充设备采样时间。

每项状态保存最近一次参与判定的原生属性值或事件标识、解释后的状态、可取得的来源时间和接收时间。状态、原生输入、时间及实际观测来源在接受该次观测时一并提交。只保留当前观测所需信息，不累积事件历史。来源中断、原生未知、读取失败与订阅未就绪分别诊断；保留观测的来源与时间不因重连或切换被改写。

终端应能区分事件订阅和属性订阅；例如运动可明确显示哪项订阅尚未就绪。`120 → 300` 可以更新原生观测和时间信息，但不增加 Matter 中的运动状态变化。

## Matter 发布

### 端点、集群与语义

继续使用当前锁定的 `rs-matter`：`319c791044d9aac352ac5afbbe31c3aa623842be`，不因本轮引入依赖升级。公开接口以该依赖的 Matter 1.6 集群定义为基线。

| 功能子端点 | 设备类型 | 状态集群 | 状态投影 |
| --- | --- | --- | --- |
| 门窗 | Contact Sensor `0x0015`，revision `2` | Boolean State `0x0045`，revision `3` | 关闭为 `StateValue = true`，打开为 `false`。 |
| 运动 | Occupancy Sensor `0x0107`，revision `4` | Occupancy Sensing `0x0406`，revision `7` | 检测到移动为 `Occupied = 1`，无人移动为 `0`。 |
| 存在 | Occupancy Sensor `0x0107`，revision `4` | Occupancy Sensing `0x0406`，revision `7` | 有人为 `Occupied = 1`，无人为 `0`。 |

MiGate 保留运动与存在的独立功能种类和名称，不把两者合并成同一个运行状态。Home 的具体分类文案、图标和自动化入口需要实测，协议类型相同不保证客户端分别显示为两种传感器类别。

每个子端点提供 Descriptor、现有 Identify 处理器及实际设备类型所需接口。物理父端点继续提供 Bridged Node、设备信息与可选 Power Source。父子关系、PartsList、TagList、设备类型、特性、属性和命令列表须与实际发布内容一致。

新增功能采用固定顺序 `contact`、`motion`、`occupancy`，位于已有控制及环境测量功能之后；已有测量顺序保持 `temperature`、`humidity`、`co2`、`illuminance`。功能键承担身份，普通状态和时间变化不改变端点。

### 协议功能边界

本轮通过 MIoT 的抽象状态输入桥接占用能力，Occupancy Sensing 统一选择 `Other` 模态（`FeatureMap = 0x0001`）作为桥接策略，不根据服务名称猜测设备使用 PIR、雷达或其他物理检测技术。两个必需的遗留类型属性 `OccupancySensorType` 和 `OccupancySensorTypeBitmap` 按标准遗留映射提供 `PIR = 0` 与 `PIR bit = 1`；这些遗留字段不作为 MiGate 推断设备物理检测方式的依据。

不启用可选 `OccupancyEvent`、Boolean State `ChangeEvent` 或预测特性；状态变化通过属性订阅报告。Boolean State 的 FeatureMap 为 `0`。不提供 `HoldTime`、检测延时、灵敏度等设备侧配置属性，不在 Matter 处理器中建立恢复计时器。

共享电量的 EndpointList 覆盖本物理设备实际发布的父端点与功能子端点；缺少电量或电量链路失败不阻止状态功能工作。

### 未知状态与变化报告

Boolean State 的 `StateValue` 和 Occupancy Sensing 的 `Occupancy` 均为不可空属性。当前状态未知时，状态属性读取返回 `Failure`；不得编码为协议空值、关闭或无人。静态元数据及同机其他有效功能仍可读取。

状态从未知变为已知、已知变为未知，或已知二值发生变化时，更新相关集群数据版本并通知属性变化。重复相同状态、重复运动事件、正无移动时长之间的变化，以及仅时间更新，不产生伪状态跳变。

本轮不发送单独的 StateChange 或 OccupancyChanged 事件，因此属性快照不会被桥接成一条新的 Matter 运动事件。Home 是否根据初始化后的状态变化执行已有自动化由客户端决定，MiGate 不承诺替客户端抑制规则执行。

## 配置与持久化

沿用当前 schema 8 的单份配置和原子规划、提交、激活流程，在其能力编码中增加三类功能、实际属性／事件绑定和枚举语义映射。名称、物理身份、功能身份、端点及配对按既有机制保存与恢复。

开发期因 MiGate 本身新增功能而需要更新已有配置时，按本次开发变更做一次性处理，不增加历史能力模型迁移、升级版本标记或每次启动强制重新解析描述的机制。正常持久化与重启恢复以当前能力模型生成的配置为范围。

设备 OTA 后新增能力属于正常运行中的描述更新。沿用既有目录同步发现描述版本（实例 URN）变化，重新获取并解析描述，识别新增的受支持功能，再通过既有配置流程发布；不要求升级 MiGate 或手动重建配置。信任上游描述版本，不增加对同版本描述内容的定时复查。

描述变化先构造完整有效的新能力模型，再规划配置。准备或保存失败时保留此前已提交的完整配置，不留下部分端点或仅一半运动绑定。状态输入、时间、连接就绪和诊断属于运行态，不进入配置或发布形状比较。

规划器统一过滤尚未重新确认的撤权事实、保留已保存名称并规范群组关系，从最终候选配置只派生一次逻辑图。Matter 提供纯形状投影函数，规划器直接比较当前与候选图的实际可见功能及共享电量，不从原始来源事实另建形状映射；版本计算和后续激活使用同一份候选图。

实际可见功能或发布形状变化按既有规则更新配置版本；绑定细节变化由来源生命周期接管。布局不变时，稳定功能键继续复用已分配身份与端点，不因一次状态变化重建配置。

单控制设备因设备描述更新而新增状态能力时，沿用既有父子布局转换：原设备端点成为物理父端点，原控制功能分配新的子端点，新增状态功能各自分配子端点。物理身份、已保存名称和配对保持；控制功能的端点在这次布局转换中允许改变，Home 中引用该功能的场景或自动化可能需要重新设置。已经采用父子布局的设备新增状态能力时，保留已有功能端点，只为新增功能分配端点。

`docs/running.md` 补充三类状态的查看与排障操作；`docs/known-limitations.md` 补充整机存在范围、初始化读取失败时的未知状态、来源中断期间保留最后状态、原生恢复节奏、单端点转为父子结构的影响和客户端显示边界。

## 验证与验收

### 自动验证

| 主题 | 关键行为 |
| --- | --- |
| 能力识别 | 两种门窗表达、运动事件与原生恢复属性的配对、四类存在描述；实际绑定来自描述；整机存在取首个候选，分区不展开；只读权限与已有照度、电量组合。 |
| 状态映射 | 门窗开关极性；运动事件、时长 `0` 和有效正值；`0` 不被正时长范围排除；重复事件及正值间变化幂等；存在的 `Quick Check`、`None` 明确变为未知。 |
| 来源协议 | 本地与云端事件主题、消息解码、订阅与退订；属性和事件编号互不混淆；保留事件不重放；属性快照可恢复状态；MQTT 重复交付沿用现有处理。 |
| 初始化与恢复 | 启动主动读取；通知来源就绪后使用有效状态通知或就绪后发起的读取建立基线；已收到有效状态通知时不因该次通知来源就绪额外补读；读取路径恢复不重建有效订阅；首次失败保持未知，单次失败保留有效值；真实来源中断和切换保留最后观测及其时间，连接变化不产生状态报告，恢复读取或通知可更新状态。 |
| 竞争与隔离 | 读取与通知独立选路，运动的事件与属性通知使用同一活动通知来源；新运动事件使早先发出的时长读取失效，包括读取与通知路径不同的情况；新属性通知阻止旧读取覆盖；旧来源、旧订阅和退休设备的迟到输入无效；一个功能订阅失败不阻断同机其他能力。 |
| Matter | 门窗与占用的类型、集群、极性、特性与实际属性列表；未知返回 Failure；已知和未知转换可报告；重复语义状态不报告伪变化；只读状态拒绝写入。 |
| 配置与组合 | 状态单项和与测量、控制、电量的组合；父子端点及电量归属；当前模型编码往返、正常重启恢复与原子提交；设备描述版本变化后识别并发布新增的受支持状态能力；单控制端点转为父子结构时允许控制端点改变，已有父子结构新增功能时保留原功能端点；状态、时间不触发结构重建。 |
| 回归 | 既有测量状态策略、照度和电量更新、插座和灯具控制、灯组只隐藏控制功能的规则。 |

验证命令为 `cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`、`cargo test`。

### 真机验收

使用 macOS Apple Silicon、现有账号和家庭、当前模型配置；记录实际 iOS／macOS 与家庭中枢版本。下表给出样本类别和通过条件，设备名称仅用于选择方便操作的样本，不进入能力识别规则。

| 项目 | 通过条件 |
| --- | --- |
| 门窗 | `isa.magnet.dw2hl` 与 `linp.magnet.m1` 各一台，观察真实打开、关闭；核对原生属性、MiGate 状态与 Home 显示方向一致。 |
| 运动 | 优先使用公卫门口的 `xiaomi.motion.pir1`，观察运动触发、原生无人恢复及后续正时长上报；Home 随状态更新，正时长继续增长不制造新的状态跳变。 |
| 存在 | `izq.sensor_occupy.trio`、`linp.sensor_occupy.hb01`、`xiaomi.sensor_occupy.03`、`xiaomi.sensor_occupy.p1` 各一台，观察真实有人与无人；P1 只发布整机状态，不出现分区端点。 |
| Home 与自动化 | 核对三类功能的显示、名称及可选状态触发入口；使用约定的测试目标验证状态变化可触发自动化。 |
| 更新时延 | 从 MiGate 收到有效状态变化到已打开的 Home 页面更新不超过 `10` 秒；原生检测、无人延时和上游传输等待单独记录，不算入该时延。 |
| 重启与恢复 | 正常重启并重建实际获取连接，确认启动未知及首次读取、断开期间保留最后观测且诊断反映来源问题、恢复后的状态和通知；身份、名称、端点及配对保持。实际不能触发的错误分支由自动测试覆盖，不记为真机通过。 |
| 功能组合 | 在有照度及电量的样本上分别核对独立更新、共享电量归属；状态来源问题不会清空其他功能或产生伪状态。 |

每次等待上游新上报最多 `20` 分钟；没有真实新上报的观察不算通过，不通过重复查询同一缓存补足验收。只验收样本实际支持的获取路径。

协议读取与 Home UI 分别核对。Home 对未知状态可能采用不同展示，至少应确认 MiGate 没有发布虚假的关闭或无人；有效状态及真实变化必须在 Home 可用。仅有协议属性可读不能代替状态显示和自动化入口验收。
