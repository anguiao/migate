# 窗帘控制与状态同步

## 目标与范围

以 `ca2fbff` 为代码基线，接入实际使用的 `xiaomi.curtain.acn010` 窗帘，提供全开、全关、指定位置和停止的标准 Matter 控制，并将米家侧的位置及运行状态变化自动同步到保持打开的 Apple Home 页面。

卧室布帘为主验收设备，卧室纱帘做同型号回归，代表固件为 `2.2.7_0009`。两台分别发布为独立窗帘，操作一台不影响另一台。继续使用现有设备发现与能力解析流程，型号用于标识本轮设计依据。

米家 App 是外部控制与状态对照入口。遥控器、手拉等操作均视为米家侧状态变化，不识别其触发来源，也不分别安排验收用例。

本轮不接入窗帘组、百叶倾角、速度设置、默认开合位置、行程设置、电机反转、唤醒模式、遥控器管理或厂商自定义功能，不为尚未遇到的其他型号差异增加处理。

## 设备输入与通信范围

代表设备的 MIoT URN 为：

`urn:miot-spec-v2:device:curtain:0000A00C:xiaomi-acn010:1:0000D031`

依据[代表设备的公开 MIoT 描述](https://miot-spec.org/miot-spec-v2/instance?type=urn%3Amiot-spec-v2%3Adevice%3Acurtain%3A0000A00C%3Axiaomi-acn010%3A1%3A0000D031)，使用标准 `curtain` 服务（`0x7816`）的以下属性：

| 属性 | 代表绑定 `siid / piid` | 描述中的访问与语义 |
| --- | --- | --- |
| `motor-control`（`0x0038`） | `2 / 1` | 可写；`0: Open`、`1: Close`、`2: Pause`、`3: toggle`。本轮只使用 `Pause`。 |
| `status`（`0x0007`） | `2 / 2` | 可读、可通知；`0: Opening`、`1: Closing`、`2: Stop`。 |
| `current-position`（`0x0039`） | `2 / 3` | 可读、可通知；整数百分比，范围 `0..100`，步长 `1`。 |
| `target-position`（`0x003A`） | `2 / 4` | 可读、可写、可通知；整数百分比，范围 `0..100`，步长 `1`。 |

绑定与枚举值从描述构造，表中的编号作为代表样本。四项输入共同形成一个稳定功能键 `main` 的窗帘功能；缺少所需输入时使用现有未支持原因诊断。

通信继续使用当前绑定家庭的本地中枢接口和米家云端接口，沿用本地优先、访问权限、通知订阅和选路恢复机制。窗帘控制不引入新的通信方式。

## 位置与运行状态

内部使用设备的开度百分比：`0` 为全关，`100` 为全开。当前位置、设备目标位置、运行状态各自保存；命令记录中的请求目标与设备上报的目标分开，成功回执不直接修改当前位置或运行状态。

默认开启位置与默认关闭位置不参与换算，也不作为全开、全关的比例基准。MiGate 不读取、修改或订阅这些设置来实现窗帘控制。

| 输入或状态 | 行为 |
| --- | --- |
| 当前或目标位置报告 | 分别更新对应值，保留实际报告精度。 |
| `Opening`、`Closing`、`Stop` | 分别表示正在打开、正在关闭、已停止；停止可以发生在任意位置。 |
| 首次尚无有效输入 | 对应字段保持未知，不填充全开、全关或停止。 |
| 单次读取失败 | 保留该字段最近的有效观测并显示诊断。 |
| 实际来源中断 | 保留最近观测，更新可用性和同步诊断；不推断窗帘已停。 |
| 正常静默 | 不以静默推断离线、到达或停止。 |

运行进度只跟随设备实际报告，不使用全程运行时间推算位置，不插值、不建立软件运动计时器。状态与位置可能分次到达，分别更新，不要求上游将它们作为一个原子快照发送。

## 命令与顺序

| 用户或协议操作 | 原生写入 |
| --- | --- |
| 全开 | `target-position = 100`。 |
| 全关 | `target-position = 0`。 |
| 设置开度 `p` | 将 `p` 按设备步长量化，写入 `target-position`。 |
| 停止 | `motor-control = Pause`，代表值为 `2`。 |

每个操作只提交一次原生写入，由设备自行完成运动。全开、全关不调用可能受设备预设影响的 `Open`、`Close`，也不使用 `toggle`。

运动中修改目标时，直接写入新的 `target-position`，不先发送 `Pause`，也不等待原运动结束。尚未发送的连续目标只保留最新一个；已经发送的目标由设备接收新目标后替换。

只有明确的停止操作才发送 `Pause`，并取消它之前尚未发送的目标。如果随后又收到新目标，按收到的顺序分别发送停止与新目标，不等待物理停止，也不合并掉停止操作。

每台窗帘复用现有发送与回执生命周期，分别维持顺序；旧回执只结束原请求，不能覆盖新命令或重新排入旧目标。停止同样等待此前已发送请求的回执结束，不越过在途请求发送；回执迟滞或超时时不承诺即时停止，沿用现有本地请求 `10` 秒、云端写入 `15` 秒的超时处理。

命令受理、物理动作和状态回传是三个独立事实。Matter 命令成功表示原生请求已受理；真实动作和最终位置由设备反馈及实际观察确认。命令失败或超时返回明确结果，不把失败改成成功，也不因未看到位置变化而重发。

## 同步与恢复

当前位置、目标位置、运行状态使用同一窗帘功能的活动通知来源，读取与通知仍可按已有机制独立选路。该功能的三个属性分别记录读取、订阅问题及观测元数据。

启动和来源恢复时读取三个状态属性；通知就绪与首次读取的竞争复用现有基线机制。控制后的实际状态及米家 App 操作依靠设备通知同步，不增加每条命令后的整组补读或运动期间轮询。

后到的旧读取不能覆盖更新的通知，旧会话、旧订阅和已退休设备的输入不能更新当前实例。已读取一个属性不代表另外两个属性已经建立有效基线；读取成功也不代表通知同步已经就绪。

正常发送前使用现有机制选择当时可用的路径。来源中断或设备生命周期失效时，结束未发送的旧工作；恢复只重建读取与订阅，不重新排入旧目标或旧停止命令。凡已经可能发送的写入，都不得在另一条路径上自动重放。

重启恢复身份、名称、端点和配对，重新获取状态，不持久化运动命令或待执行目标。设备在 MiGate 重启期间自行继续原有运动是设备行为，MiGate 不为此补发继续或停止指令。

## Matter 表达

每台代表窗帘沿用现有单控制设备布局，在一个端点上组合 Bridged Node 与 Window Covering（`0x0202`，revision `6`），提供 Descriptor、Bridged Device Basic Information、Identify、Groups 和 Window Covering cluster。运行状态变化不改变端点或发布形状。

Window Covering cluster 使用 `0x0102`、revision `8`，仅启用 `Lift` 与 `PositionAwareLift`。`Type` 为 `Drapery`；具体左开、右开或对开结构没有作为本轮输入，`EndProductType` 使用 `Unknown`。不发布 Tilt、绝对行程或未实现命令。

使用当前锁定的 `rs-matter` 生成接口，显式选择实际属性、命令和 FeatureMap。生成 IDL 中仍存在的 provisional 绝对位置元素不能因直接使用完整集群描述而被意外发布。

| Matter 项目 | 映射 |
| --- | --- |
| `CurrentPositionLiftPercent100ths` | 由实际开度 `p` 转为 `(100 - p) × 100`。 |
| `CurrentPositionLiftPercentage` | 由同一实际开度得到 `100 - p`，与百分之一刻度保持一致。 |
| `TargetPositionLiftPercent100ths` | 由设备目标位置按同一规则转换；`StopMotion` 的处理见下文。 |
| `OperationalStatus` | 全局与 Lift 状态均取原生运行状态：停止、正在打开、正在关闭。 |
| `UpOrOpen`、`DownOrClose` | 分别写设备目标 `100`、`0`。 |
| `GoToLiftPercentage(m)` | 接受标准范围 `0..10000`，转换为 `p = (10000 - m) / 100` 后按整数步长四舍五入。 |
| `StopMotion` | 发送 `Pause`；根据真实停止反馈更新协议状态。 |

当前或目标位置未知时，对应属性返回协议 `null`。运行状态不可空，尚无有效状态时相应属性读取返回失败，不用 `Stopped` 代替未知。

处理 `StopMotion` 时，按 Matter 要求将协议目标收敛到设备反馈的实际停止位置；该位置未知时为 `null`。这是停止命令的处理要求，不因任意一次原生 `Stop` 报告而持续用当前位置覆盖设备目标。收到后续目标命令，或设备报告新的目标、恢复运动后，重新使用设备目标，旧停止处理不能再覆盖它。

原生当前位置、目标位置和运行状态始终分别保存。目标与当前位置不同本身不代表仍在运动，运动状态以原生 `status` 为准。停止处理不把命令成功回执当作物理停止，不向设备补写当前位置，也不伪造当前位置或运行状态。

`ConfigStatus` 设置 `Operational` 与 `LiftPositionAware`，不声明底层编码器或反向运动；真实连接可用性继续由 Bridged Device Basic Information 表达。`Mode` 保持正常值 `0`；写 `0` 为无操作，非零写入返回 `ConstraintError`。本轮不通过这个标准属性开放反转、校准、维护或指示灯设置。

属性投影变化驱动对应数据版本与订阅报告。重复同值观测可以更新诊断时间，但不制造位置或运行状态的伪变化。Home 的实际显示与协议读取分别验证。

## 模块改动

| 模块 | 职责 |
| --- | --- |
| `xiaomi/capability` | 在现有控制解析中增加窗帘分支，构造位置绑定、运行状态映射与停止写入；沿用描述边界与现有组合流程。 |
| `device` | 增加窗帘功能、独立状态快照及目标／停止命令。将“所有控制都具备 power”的现有假设限制到插座和灯具，窗帘不伪造开关状态。 |
| `xiaomi/adapter` | 复用读写传输、选路、通知及观测顺序，增加窗帘原生值转换与命令发送；保持原回执的生命周期。 |
| `configuration`、`storage` | 增加窗帘配置编码、固定发布形状和端点规划；与现有完整配置一起原子保存，旧设备配置继续正常读取。 |
| `matter` | 增加窗帘处理器、位置换算、命令分派、`StopMotion` 状态处理、版本和报告；复用既有桥接基础集群。 |
| 终端 | `list`／`status DID` 显示当前位置、原生目标、运行状态、请求及回执、来源时间、接收时间和读取／订阅诊断。 |

窗帘专有状态和命令放在职责明确的模块中，不扩展灯光轨迹或颜色算法，也不为本轮重写灯具队列。共用发送边界和生命周期时保持原有插座、灯具语义。终端不新增一套窗帘控制命令；现有 `on`／`off` 不隐式解释为窗帘操作。

数据流为：MIoT 描述 → 窗帘能力与已提交配置 → 读取／通知 → 窗帘状态 → Matter 投影与报告。反向控制为：Matter 命令 → 窗帘命令顺序 → 当前选路 → 单次属性写入 → 独立回执与实际观测。

### 真机验收

使用现有 macOS Apple Silicon 运行环境、已绑定家庭和 Apple Home，保留现有配对；记录实际系统、Home 家庭中枢及窗帘固件版本。米家 App 与物理帘布作为动作和状态对照。

| 项目 | 操作与通过条件 |
| --- | --- |
| 布帘基本控制 | 全开、全关、`25%`、`50%`、`75%` 各 `3` 轮；实际停止后的设备开度达到量化后的目标，米家开度、原生输入和 Home 显示一致。设备步长只用于目标量化，不作为额外允许误差。 |
| 布帘运动中停止 | 共 `3` 轮，其中打开、关闭方向至少各 `1` 轮；在途中停止，真实运动停止，当前位置停在实际位置，Home 不继续显示旧终点的运动；之后新目标能正常执行。 |
| 布帘修改目标 | 共 `3` 轮，其中同方向、反方向新目标至少各 `1` 轮；直接发送新目标，不附加 `Pause` 或等待原运动结束，最终执行最新目标，之后不补放旧目标。 |
| 纱帘回归 | 全开、全关、`25%`、`50%`、`75%` 各 `1` 轮，途中停止和修改目标各 `1` 轮；同时确认两台设备的控制与状态互不影响。 |
| 米家外部操作 | 在布帘上用米家 App 设置位置、停止和再次设定目标，完成 `3` 轮；纱帘 `1` 轮。Home 始终保持页面打开，不通过重开页面或手动刷新取得更新。 |
| 正常停止响应 | 正常网络、通道已就绪时，从控制端发出停止命令到物理帘布停止不超过 `3` 秒；布帘与纱帘的途中停止均核对该时限。回执迟滞、请求超时等异常单独记录，不能用异常结果代替正常停止验收通过，也不为满足时限绕过已有发送顺序。 |
| 正常同步时限 | 正常网络、来源已就绪时，实际开始运动、改变方向、停止或到达目标后 `3` 秒内 Home 状态与设备一致。中间位置按设备实际报告节奏更新，MiGate 收到报告后 `3` 秒内反映到 Home；不要求设备未提供的逐秒位置。 |
| 单次运动等待 | 先以米家 App 确认相同速度设置下的正常全程耗时，使用两方向较长值加 `10` 秒作为本轮单次运动的观察上限；超过上限仍无结果则停止等待并记录失败，不无限等待。这个上限不作为 MiGate 的运动计时或控制逻辑。 |
| 重启、断连、选路变化 | 布帘各 `1` 轮，确认恢复状态和通知、身份及配对保持，且没有重放旧目标或停止。恢复观察沿用最长 `20` 分钟：断线从通信条件恢复起计，重启从 Matter 服务重新提供起计；正常状态同步的 `3` 秒不套用到故障恢复。 |
| 已有设备核心回归 | 选择已支持的插座、单灯、原生灯组各完成一次基本控制与反馈；环境测量及门窗／运动／存在状态至少各核对一次真实变化同步。 |

协议受理、真实动作和状态回传分别确认。通知验收需要实际收到新的属性报告，不用重复读到缓存补足。来源路径以实际选路诊断为准，不以米家 App 能操作推断 MiGate 的接口已经可用。无法稳定触发的异常由自动验证覆盖，不算作真机通过。

若 Home 没有提供独立停止入口，用 Matter 调试客户端触发 `StopMotion`，同时核对物理停止和 Home 状态；该结果只证明协议停止与状态显示，不声称 Home 存在相应操作入口。
