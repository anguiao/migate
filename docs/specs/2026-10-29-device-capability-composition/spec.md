# 设备功能组合与内置适配补丁

## 目标与范围

以 `fa3de7bae4afcff266242be862ed4b9b9af4a6e8` 为设计基线，将现有设备适配整理为：物理设备承载多个功能，设备品类说明主要用途，各功能复用通用识别与控制，内置补丁处理已确认的设备差异。

兼容通用功能规则的新型号可以直接接入，不需要逐型号登记。型号差异只进入对应补丁。已经添加的设备在 MiGate 规则更新或 MIoT 描述更新后自动重新识别能力。

本轮覆盖已有插座、灯光、窗帘、风扇、环境测量、状态传感器、整机电量，以及原生灯组。将已有功能的多个实例与不同控制功能组合纳入统一模型，补齐识别、身份、控制、反馈、发布和恢复链路。灯组 RGB 增强基于成员已适配的功能派生，成员型号不作为灯组准入条件。功能组合使用明确标为合成输入的测试验证。

采用项目内置 Rust 补丁，随版本发布。用户自定义补丁文件、脚本执行、动态插件、新功能类型及新的来源协议不在本轮范围内。风扇通用化覆盖现有百分比调速输入、语义明确的数值范围和离散挡位，以及相应的 Matter 映射；新增风模式控制不在本轮范围内。

不考虑旧存储格式、旧功能键和旧端点布局的历史兼容。新模型统一采用物理父端点与功能子端点；正常重启和后续更新仍须保持新模型下已建立的身份。

## 设备品类、核心功能与附加功能

设备品类来自整机描述，用于解释核心用途和必要的服务上下文。功能集合来自实际服务、属性、事件及适用补丁。品类不再决定一个设备只能进入某一个控制解析器。

每个已识别功能具有独立身份、功能类型、有效能力和可选的核心标记。功能内部仍采用有明确约束的模型，例如调光灯必须具有开关和亮度控制；不以任意属性集合直接生成协议设备。

核心标记用于说明功能与整机主要用途的关系，可以标记一项或多项，也可以没有标记；其余有效功能称为附加功能。标记仅作为描述性元数据，不参与功能准入、可用性判断、控制目标选择或 Matter 发布，也不改变功能本身的控制、读取和通知契约。

| 整机品类 | 核心标记的依据 | 附加功能示例 |
| --- | --- | --- |
| 灯、夜灯、原生灯组 | 对应的灯光功能。原生灯组仍由目录中的确认关系识别。 | 照度、人体存在、温湿度。 |
| 风扇 | 风扇控制功能。 | 灯光、环境测量。 |
| 窗帘 | 窗帘控制功能。 | 环境测量、状态。 |
| 插座 | 真实插座通道的控制功能，多路通道可以并列为核心。 | 环境测量、状态。 |
| 温湿度传感器 | 有效的温度与湿度功能，二者可以并列。 | CO₂、照度。 |
| 门窗、运动、人体存在传感器 | 分别对应门窗、运动、整机人体存在功能。 | 照度、环境测量。 |

表中的标记规则按实际功能实例应用，不要求整机必须提供表中列举的全部能力。电量继续是整机共享能力，不占用一个独立功能身份。

整机品类没有对应标记规则，或没有识别出对应功能时，不设置核心标记，其他明确识别的有效功能照常接入。是否定义或具有核心功能不产生单独的诊断项。

控制命令必须明确定位功能，不定义设备级默认控制目标。终端开关命令使用 `on DID FUNCTION`、`off DID FUNCTION`，单功能设备也必须指定稳定功能标识，可通过 `list` 查询。省略功能标识时提示命令用法且不发送命令；指定功能不支持该操作时返回不支持，不转向其他功能。Matter 控制继续通过端点定位具体功能。

## 通用功能识别与准入

识别单位是有明确语义的功能。识别器接收服务上下文和必要的整机上下文，返回候选功能、真实绑定、所需行为及未接入原因。对整台设备发现所有候选后，再处理功能归属、依赖和组合。

| 功能 | 本轮通用契约 |
| --- | --- |
| 插座 | 真实插座负载的布尔开关，可读、可写、可通知。标准 `switch` 服务须有插座语义依据；不把其他品类内所有开关都解释为插座。 |
| 灯光 | 标准 `light` 服务中的开关，以及有效的亮度、色温、RGB，组成现有四种灯型。可以在其他整机品类内识别，也可以存在多个独立灯光实例。 |
| 窗帘 | 有明确停止命令、运动状态、当前位置和目标位置；沿用现有位置量程、枚举及访问权限要求。 |
| 风扇 | 标准 `fan` 服务的布尔开关与语义明确的风速输入，均可读、可写、可通知。标准 `fan-level` 可以提供有效数值范围或有序离散挡位，不要求原生输入为 `1..100`、步长 `1`；有效水平摇头为可选能力，不要求所有风扇具有直吹模式。 |
| 测量 | 摄氏度环境温度、百分比相对湿度、ppm CO₂、lux 照度，分别满足现有格式、量程、读取和通知要求。温度继续区分环境测量与部件本体温度。 |
| 状态 | 门窗开合、运动、整机人体存在，保留当前布尔／枚举语义，以及运动事件和无移动时长的配合关系。 |
| 整机电量 | 有效百分比电量且可读、可通知，保持整机共享；其成立不依赖是否具有传感器子功能，也不单独使设备成为可发布设备。 |

控制、环境测量、门窗和运动允许多个语义独立的同类实例，分别准入和建立身份。整机人体存在仍只有一个来源，不展开分区；沿用已确认的首个标准存在服务选择规则，该服务的状态属性不满足要求时不改用后续分区。`xiaomi.sensor_occupy.p1` 继续只接入整机存在服务。

通用风速输入必须同时满足标准服务、属性类型、数据形态及访问要求，不能仅凭显示名称或数值范围识别。数值范围保留最小值、最大值和步长；离散挡位保留真实编码与明确的风速次序，不把编码大小或列表位置直接当作风速比例。自动模式、自然风预设及随模式改变含义的枚举，不直接混入普通风速挡位；由已知规则或补丁明确控制与反馈语义。

满足通用契约的风速范围或有序普通挡位可直接接入。存在模式属性时，根据它与风速输入的实际语义关系判定是否需要补丁。风速输入本身混合自动模式、预设与普通挡位，且控制或反馈语义不明确时，不自行剔除特殊值后接入，而由明确规则或补丁解释该输入。存在其他有效风速输入时仍可选用；只有找不到有效输入时才不接入风扇功能，同机其他独立功能不受影响。

相同服务的多个属性已明确表示同一风速维度时，通用选择优先采用可表达运行挡位更多的有效输入，不重复创建风扇功能；数量相同且没有明确选择依据，或无法确定功能归属时，报告该功能的歧义。适用补丁可以明确选择输入。`dmaker` 的厂商风速属性由补丁提供，不纳入任意厂商同名属性的通用匹配。

功能准入采用以下规则：

1. 独立功能分别判定，某一功能不支持不排除其他独立有效功能。
2. 功能内可选能力按已定义的依赖组成有效能力组合。例如灯光 RGB 增强无法成立时，只有不依赖该增强的基础灯型可以保留；缺少正确控制所必需的行为时，不发布受影响功能。
3. 共享开关、共享模式或互斥关系必须有明确语义。由已知规则或补丁确定归属和控制方式；无法解释的冲突只排除受影响功能，并给出原因。
4. 一个真实控制属性不能被多个独立功能重复认领。已确认的共享或组合行为由统一执行计划协调；灯组通过功能引用复用成员，不再次认领其原始属性。
5. 没有任何有效功能时保留描述与诊断，不发布空物理设备。

根结构或来源标识无效时拒绝整份新描述。局部候选的访问权限、格式、量程和编码问题归属于该候选，不阻断无关的有效候选。

功能缺失、描述不受支持、当前连接不可用分别表示。暂时离线或通知失败不改变已经确认的静态功能集合。

### 风扇风速与 Matter 映射

来源层保存真实风速编码，设备层表达有序运行挡位及其数量 `N`。数值范围按有效步长展开，离散列表按已确认次序建立双向映射。例如原生范围 `10..30`、步长 `10` 对应三个运行挡位；离散编码中的 `0` 也可以表示第一运行挡位，不等于逻辑关机。

本轮沿用 Matter MultiSpeed，以 `SpeedMax = N` 表达可达运行挡位，遵守该属性 `1..100` 的协议量程；原生数值不必落在这个范围内。不能无损表达的输入报告具体映射限制，不静默压缩为虚假的控制精度。`1..100`、步长 `1` 的既有输入对应 `N = 100`，保持原有调速精度。

百分比与挡位按 Matter 规范双向转换：百分比 `p` 对应 `ceil(N × p / 100)`，运行挡位 `s` 对应 `floor(100 × s / N)`。逻辑零表示关机，运行挡位为 `1..N`。命令只写真实可达值；风速反馈由设备观测换算，不将尚未确认的百分比请求当作实际反馈，也不把百分比界面描述为设备具有连续调速能力。

`FanModeSequence` 随挡位数确定：一挡使用 Off/High，两挡使用 Off/Low/High，三挡及以上使用 Off/Low/Medium/High。三挡及以上的 Low 和 Medium 上界分别为 `floor(N / 3)`、`floor(2N / 3)`，High 覆盖其余运行挡位；模式写入选择对应区间的最高挡位，百分比区间由同一映射导出。`N = 100` 时保留现有 `33`、`66`、`100` 的模式目标。

普通范围和挡位换算属于通用规则。模式前置条件、风速属性含义修正和特殊反馈策略仍属于补丁；已有 `dmaker` 自然风下显示记忆直吹设定的语义保持不变。

## 内置补丁

补丁以实际差异组织，明确补丁标识、匹配条件、影响的功能、绑定选择及行为。匹配可针对具体型号，也可针对具有已确认共同语义的厂商家族；家族规则仍需检查所依赖的服务、属性和数据形态。

补丁允许介入两个位置：

| 位置 | 输入与输出 | 边界 |
| --- | --- | --- |
| 功能识别 | 根据原始描述补充语义、选择绑定、关联跨服务能力，生成识别所需的明确修正。 | 保留原始描述；修正后的候选仍需满足功能契约。不能凭空补造硬件能力或原生属性。 |
| 控制与反馈 | 为已识别功能选择具体命令编码、执行步骤、数值转换和反馈来源。 | 复用既有读写、订阅、选路、动作结算与生命周期机制。策略不能绕过真实访问权限。 |

补丁按明确阶段作用于同一份候选，不依赖注册顺序隐式覆盖。作用于不同功能或不同处理点的规则可以组合；同一处理点需要专门替换时，由内置选择规则明确决定。未定义的冲突报告为受影响功能的准入失败。

适用条件不满足的补丁不执行。已匹配设备身份、但所需能力或绑定无法成立时，诊断补丁未生效的原因；是否保留通用功能由该功能是否独立成立决定。

| 现有特殊规则 | 整理后的职责 |
| --- | --- |
| `devcea.light.ls2307` | 在单灯功能中关联真实的跨服务 RGB 与颜色模式绑定，提供统一 RGB 控制与反馈契约，保留已确认的颜色切换行为；组内复用同一功能及策略。 |
| `cuco.plug.cp7pd` | 识别三个真实通道、通道名称及总控触发刷新关系；总控不为满足“主功能”概念而成为额外的虚构控制。 |
| 已支持的 `dmaker` 风扇语义 | 选择厂商百分比风速和直吹模式绑定，保留非零调速前开机／切直吹、自然风下显示记忆直吹设定等既有行为。 |

通用风扇独立开关只控制电源，逻辑零速通过关机表达，不把协议零直接写入原生风速属性；非零调速按既有电源判断确保开机，再将目标挡位编码到已选风速绑定。原生编码为零的有效运行挡位仍可正常写入。水平摇头只操作对应属性，实际状态继续取设备反馈。

一般风扇不附加 `dmaker` 的模式步骤。若已知某个设备调速必须切换模式，由其适用策略声明该前置步骤。补丁修正与通用识别最终形成同一种有效功能表示，不让上层按型号分支。

## 模型与职责

来源输入、解析结果和运行状态分开保存：

| 单元 | 职责与交互 |
| --- | --- |
| 来源描述 | 保存型号、实例 URN 和完整原始 MIoT 描述；提供服务和属性上下文，作为重新识别的输入。 |
| 通用识别与补丁解析 | 生成有效功能、核心标记、来源身份、真实绑定、执行与反馈策略，以及诊断。解析过程不发送设备命令。 |
| Xiaomi 灯组能力派生 | 消费原生组能力、确认关系及已适配的成员功能，生成逻辑能力与对应执行计划；不检查成员型号，也不重新解析成员厂商属性。 |
| `device` | 表达物理设备、有效功能、状态和功能级命令生命周期；使用语义明确的功能类型，不依赖具体厂商或型号。 |
| `xiaomi/adapter` | 按当前已提交的来源计划执行命令、读取和订阅；组命令按能力走原生接口或成员功能执行策略，维护来源状态与已确认的组合行为。 |
| `configuration`、`app` | 组合来源事实和群组关系，分配身份与端点，比较配置，提交并激活对应运行实例。 |
| `matter` | 将各功能映射为现有标准设备类型与能力，按统一父子布局发布。 |
| `storage` | 保存完整来源描述、已提交有效配置、身份和关系；恢复时交给当前规则重新识别。 |
| `terminal` | 展示品类、功能列表及其核心标记、有效能力、补丁及未接入原因；控制命令要求显式指定功能标识。 |

移除来源有效模型中“灯、风扇、窗帘必须是唯一 `main` 控制”及“插座只有某一固定三通道拓扑”的通用约束。具体型号仍然需要的绑定约束归入对应补丁。通用模型只表达功能本身及实际组合必须成立的约束。

来源私有模式和控制前置步骤由来源策略拥有。设备层不以厂商模式值判断功能是否成立；诊断所需的原生输入仍由来源记录。功能级动作与状态继续独立，同一物理设备上的传输与写入门控继续共享；对一个功能执行停止、关闭或取消，不能无依据地接管另一功能。

## 功能身份与统一端点

功能身份由语义类型和真实来源锚点组成，与整机品类、核心标记及当前功能数量无关：

- 控制功能以其主体服务为锚点，例如 `light:2`、`fan:3`、`outlet:9`、`curtain:2`。
- 属性型测量和状态以主体属性为锚点，例如 `temperature:3:7`。运动功能以提供状态恢复语义的属性为锚点，事件作为该功能的输入。
- 跨服务能力使用其所属功能的主体锚点。`ls2307` 的 RGB 补充不生成第二个灯光身份，亮度或颜色能力增加也不改变该灯光身份。

同一物理设备可以有多个语义独立的同类功能实例。整机人体存在和共享电量仍须明确选定唯一来源；不能因为支持组合就把多个候选任意合并，也不将人体存在分区当作独立实例发布。

每个可发布物理设备固定持有一个父端点，每个可见功能持有独立子端点，单控制设备也遵守这一结构。父端点承载物理身份、名称、可用性和可选共享电量，子端点承载对应功能的协议能力。核心标记不产生另一套端点布局。

后续新增功能只分配新增功能的端点；同一功能增加已支持能力时沿用其身份与端点。重启、描述重算和核心标记变化不重新编号。已分配的身份和端点继续由配置持久化管理，临时离线不释放它们。

本轮采用新存储结构，不保留旧 `main` 等功能键的别名或旧单控制合并端点的恢复分支。旧格式应明确拒绝加载并说明需要新数据目录，不自动清空、覆写或迁移现有运行数据。

## 原生灯组的能力组合与成员定位

单设备的通用识别与补丁先生成有效功能，再使用同一候选配置中的组描述、成员关系及这些功能派生灯组能力，随有效配置一起提交。灯组消费成员已经适配完成的 RGB 控制与反馈契约，型号差异只在成员补丁中处理。

### 成员定位与发布

米家目录仍是灯组与成员关系的来源。关系进入有效配置时，将成员解析为具体灯光功能引用，而非默认取设备第一个功能或名为 `main` 的功能。

成员只有一个有效灯光功能时可以唯一定位；多个候选需要明确的来源关系或补丁依据。无法定位时不给任意功能分配成员身份，记录关系诊断。依赖该定位的成员隐藏、反馈汇总和 RGB 增强不执行；可独立成立的原生组能力保留，缺少可靠来源的反馈保持未知。

成员隐藏仅隐藏已经匹配的灯光功能。复合设备只要仍有其他可见功能就继续发布物理父端点及这些功能，包括其他控制功能，不再只为传感器保留成员设备。

组内控制、RGB 增强、共享成员动作接管和状态汇总都使用同一份已提交功能引用。对成员设备中无关的风扇或其他功能操作，不触发该灯光的组接管。

### 基于成员功能的 RGB 增强

原生组能力优先，已有能力继续使用组 DID 的真实接口。原生组已提供 RGB 时直接使用该能力；缺少 RGB 时，只有全部已确认成员均能定位到满足统一 RGB 契约的有效灯光功能，且补齐后符合扩展彩灯模型，才派生 RGB 增强。通用识别或不同补丁产生的成员功能可以组合，不要求同型号。

派生过程保留原生开关、亮度和色温的控制路径，只为缺失的 RGB 建立成员功能分发计划；不改写原始组 MIoT 描述，不在组 DID 上补造 RGB 属性。成员描述缺失、功能无法定位或不满足契约时保留可独立成立的原生组能力。暂时离线或状态未知不撤销已确认的静态增强能力。

RGB 分发提交逻辑颜色目标，复用各成员功能已有的执行策略、真实反馈、传输队列和来源生命周期。成员自身的编码、跨服务绑定和模式切换由其适配策略负责；灯组不重新选择厂商属性，不追加独立的型号修复，也不为成员另建渐变轨迹或控制实例。

成员分发沿用现有组策略：每次动作固定使用已生效的成员集合，仅向发送时确认开启的成员调色，不为调色开灯；至少一个成员受理即确认组请求受理，其余成员继续执行，没有可执行成员或全部失败则返回失败。被跳过的目标不缓存、不在成员恢复或开灯后补发。原生组命令继续采用原生接口的受理结果。

虚拟组沿用成员实际反馈汇总；物理组的原生字段取组反馈，派生 RGB 与颜色模式取同一代表成员快照。组状态消费成员统一功能快照，不重新解释原生厂商属性；命令受理不替代实际反馈，未知字段仍保持未知。

## 描述持久化与自动更新

保存完整来源描述，同时保存已提交的有效配置。前者用于重新识别，后者用于配置比较、恢复身份和说明当前已生效的行为。解析时的修正不覆盖原始描述，后续规则始终可以从原始事实重新计算。

已成功取得的有效来源描述即使没有可发布功能，也保留供当前规则重新评估；它不因此创建可控制运行实例。普通属性读数、命令历史和待执行动作不进入描述缓存。

### MiGate 规则更新

每次启动使用当前程序内置的通用规则和补丁重新解析本地缓存，并重新派生已确认群组的有效配置。正常有缓存的启动不为此访问描述服务，不依赖单独维护的规则版本号。

重算结果进入现有配置准备、提交和激活流程。结果等价时不增加配置版本；真实绑定或来源行为变化时更新对应运行实例；发布形状变化时按实际差异更新 Matter 配置。型号、URN、核心标记、诊断等纯元数据变化不触发订阅重建或 Matter 重启。

启动时先完成本地重算及其配置应用，再建立本次对外服务视图。失败时采用下述更新失败规则，不能把未提交的重算结果混入恢复视图。

描述重算不直接修改正在服务的功能，也不产生设备控制。运行对象使用同一份已提交配置中的绑定和策略。

### MIoT 描述更新

本流程以 MIoT 新版描述兼容既有描述为前提：已支持的功能、属性及其标识保持稳定，描述更新按扩展处理。不为“旧版存在、新版删除”、功能乱序或重新编号增加删除检测、旧绑定回退、跨版本重映射等防御逻辑及测试，也不额外验证新旧描述是否满足这一兼容前提。

保留现有运行期目录同步机制：发现型号或实例 URN 变化后获取对应完整描述，重新识别，再通过同一配置流程应用和保存。新描述与其有效配置保持对应，不混用新描述的一部分和旧绑定的一部分。

未变化的目录、普通属性通知和连接恢复不重新获取描述。同一个 URN 下的静默修改仍不主动轮询；设备固件号变化本身不等同于已发现新的 MIoT 描述。

### 更新失败与部分支持

网络获取失败、新取得的描述无效或配置保存失败时，保留上次已提交配置并显示失败原因，后续沿用已有恢复和重新规划机制。已提交存储本身损坏或格式不受支持时，明确拒绝加载，不从残缺记录拼装运行配置。

启动时每份缓存描述只使用当前规则解析一次。某个来源的纯解析失败时，保留该来源上次已提交的完整描述与有效模型，并持续显示失败原因；其他来源的有效变更仍可进入完整候选配置，灯组按这份候选重新派生，统一提交后生效。相同输入不进入定时解析重试；取得新描述或下次启动时再执行识别。来源识别失败不阻止已确认的设备移除与访问撤销。

新增候选功能或可选能力尚不受支持时，按功能准入规则形成有效的部分支持结果，其他独立有效功能继续使用。新增能力不受支持不等于描述获取或配置保存失败，不因此阻止整份有效描述更新。

来源资格和米家目录确认的设备移除仍由现有生命周期管理。缓存描述与启动重算不授予已经失效的访问资格，也不恢复已移除设备的运行权限。

## 诊断

终端为每台设备显示整机品类和已接入功能。每个功能显示稳定标识、功能类型、当前能力、绑定来源及生效补丁；核心标记仅用于功能列表中的用途说明，不显示核心是否已定义或缺失的诊断状态。沿用现有运行状态、路径、读取、通知和动作诊断。

虚拟灯组的灯光功能沿用成员反馈汇总的通知来源与就绪判断，设备级和功能级诊断保持一致；不以虚拟组没有自身订阅为由报告同步受限。

灯组说明各项能力来自原生接口还是成员功能派生；RGB 增强未成立时，以成员功能缺口或关系歧义说明原因，不以成员型号不匹配作为拒绝理由。

识别诊断覆盖以下情况：

- 已识别的候选功能因权限、格式、量程或能力组合不受支持而未接入。
- 某项可选增强或已匹配补丁无法生效。
- 真实属性归属、功能依赖或组成员功能定位有歧义。
- 来源描述更新、重新识别或配置提交失败。

不把所有未使用的厂商属性逐项列为错误。识别诊断与实际运行故障分开，用户能够区分“功能没有接入”和“功能已接入但当前无法连接”。

## 验证要求

| 主题 | 必须证明的行为 |
| --- | --- |
| 通用识别 | 使用既有公开描述及通用风速描述样例，证明符合契约的功能不依赖逐型号登记；原有功能语义保持成立。 |
| 风速输入与选择 | 覆盖既有百分比输入、不同范围与步长、有序离散挡位，以及同一风速维度的多输入选择；原生零值和非连续编码正确映射，模式预设不被误当作普通挡位；未解释的混合枚举不自行删项接入，有其他有效输入时仍可接入风扇。 |
| 风速协议映射 | 覆盖百分比与挡位换算、边界值、关机和设备反馈，一挡、两挡及多挡的模式与速度一致；`N = 100` 保持既有精度与模式目标，无法无损映射时给出明确原因。 |
| 核心标记 | 标记准确表达功能与品类的用途关系，允许多项或没有标记；是否具有标记不产生单独诊断，标记变化不影响功能准入、身份、订阅及 Matter 发布。 |
| 显式控制目标 | 单功能与复合设备的终端控制均须指定功能标识；省略标识或指定未知功能时不发送命令；指定功能不支持操作时返回不支持，不转向其他功能。 |
| 多控制组合 | 用少量合成描述覆盖灯光与风扇共存，以及同类控制的多个实例，验证功能身份、绑定归属、命令与反馈路由。 |
| 多实例边界 | 环境测量、门窗和运动的独立同类实例分别识别与发布；整机人体存在保持唯一来源，P1 只发布整机状态，不展开后续分区。 |
| 功能隔离 | 一项候选不受支持时保留其他有效功能；明确依赖失败只影响依赖方；一个功能的动作不会无依据地取消其他功能。 |
| 内置补丁 | 既有 `ls2307` 单灯、`cp7pd`、`dmaker` 行为保持；补丁匹配、未生效原因及通用基础独立成立的情况可解释。 |
| 统一发布 | 单功能和复合设备都使用父子端点；新增功能后原有功能身份和端点稳定；电量保持父端点共享。 |
| 灯组与复合成员 | 唯一定位成员灯光，隐藏与接管仅作用于该功能，同机其他控制与传感器仍可发布和使用。 |
| 灯组能力派生 | 用通用 RGB 成员与不同补丁成员的合成组合证明增强不依赖型号白名单；原生 RGB 优先，成员不满足契约时保留原生能力；单灯规则更新能重新派生组能力。 |
| 灯组 RGB 执行与反馈 | 分发实际复用成员各自的执行策略，原生能力仍走组接口；既有仅向亮灯成员调色、受理、动作接管和反馈汇总语义保持，不重复创建成员轨迹或向组 DID 写入虚构 RGB 属性。 |
| 规则重算 | 同一原始描述和同一 URN 在新识别规则下可以获得新增能力；启动重算使用缓存，等价结果不引发配置变更；纯解析失败保留该来源旧结果与诊断，不阻塞其他来源更新，也不定时重试相同输入。 |
| 描述更新 | 运行期新 URN 自动取得兼容扩展的新描述并整体生效，已有功能身份与端点稳定；新增能力不受支持时保留有效部分；获取或保存失败保留完整旧配置，新旧绑定、策略和群组关系不混用。 |
| 恢复与诊断 | 新格式下重启恢复身份和端点，读取真实状态，诊断保留功能归属和部分支持原因。 |

合成组合测试用于证明框架契约，不作为具体复合型号已完成设备适配的证据。现有真实型号描述和既有行为回归继续约束补丁，不以通用化为由改变已经确认的控制语义。

## 文档与历史决策

实现同步调整 README 的设备适配说明、已知限制中的复合功能、端点边界、风速映射范围及灯组 RGB 增强条件，以及运行指南中的显式功能选择、诊断和新数据目录操作说明。终端命令帮助与运行指南统一使用必填的功能标识。

本方案替代[结构整理方案](../2026-10-19-architecture-restructuring/spec.md)中仅保存解析后来源描述、单控制功能布局及旧功能键约束，替代[风扇方案](../2026-10-29-fan-control/spec.md)中仅支持百分比输入、固定百挡投影及将 `dmaker` 来源语义作为所有风扇准入前提的做法。原方案中已经确认的设备行为继续由对应补丁承载。

本方案替代[原生灯组方案](../2026-10-10-native-light-groups-and-capability-repair/spec.md)中将 RGB 增强限定为全员 `ls2307` 的条件，改为消费成员已适配的功能。已确认的单灯行为、原生组控制路径、组级受理、动作协调和实际反馈语义保留，成员定位与作用范围改为具体灯光功能。[独立测量方案](../2026-10-24-independent-measurements/spec.md)和[状态传感器方案](../2026-10-26-state-sensors/spec.md)的独立准入原则扩展到控制功能。
