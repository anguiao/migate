# 空调伴侣控制与状态同步

## 目标与范围

以 `99fd1df` 为代码基线，接入 `lumi.acpartner.mcn04` 的空调控制功能，使用书房空调伴侣、固件 `2.3.0.0022` 及其已配置的冷暖空调作为代表。空调品牌和型号不作为接入条件；既有米家基本控制正常作为设计前提。

以伴侣报告的状态为准，实现 Home 控制与伴侣状态之间的闭环，并将米家侧的状态变化同步到保持打开的 Home 页面。命令回执与状态反馈继续分开；不增加空调本体检测、功率推断或外部温度传感器联动。

完整纳入当前能够通过标准 Matter 表达的空调控制：开关、制冷、制热、自动、送风、除湿、目标温度、自动及低中高风速，以及具备有效绑定的上下摆风。模式之间的参数限制按伴侣报告的控制范围执行。

采用通用空调功能与 mcn04 内置补丁。标准 MIoT 属性负责控制，补丁解释伴侣的状态报告和模式约束。相比拼接厂商整包状态写入，这条路径复用现有属性传输，单项命令无需拼凑其他设置；本轮不写 `ac-state`。

通用识别按能力契约接入，不使用型号白名单。本轮契约限定为同时具备制冷、制热、自动、送风和除湿五种模式、唯一整度目标温度，以及自动／低／中／高四种风速设置的空调；上下摆风可选。符合该契约且标准控制与反馈绑定有效、功能归属明确的其他型号可以自动接入。单冷空调、不同风速挡数或其他能力形态本轮不接入，也不通过裁掉未解释的能力拼成已支持功能；mcn04 当前配码对模式和参数的限制仍由运行期控制范围约束，不要求每次配码都开放所有静态能力。

本轮不增加 mcn02 旧 miIO 适配、设备 IP 直连、遥控码配置、速冷和安睡策略、定时、指示灯、电气测量或告警控制。是否能观测原装遥控器操作取决于伴侣是否报告变化，不建立额外的检测链路。

## 设备输入

代表设备使用以下实例描述：

`urn:miot-spec-v2:device:air-condition-outlet:0000A045:lumi-mcn04:1`

| 输入 | 代表绑定 `siid / piid` | 用途 |
| --- | --- | --- |
| `air-conditioner.on` | `3 / 1` | 布尔开关，可读、写、通知。 |
| `air-conditioner.mode` | `3 / 2` | 可读、写、通知；`0` 制冷、`1` 制热、`2` 自动、`3` 送风、`4` 除湿。 |
| `air-conditioner.target-temperature` | `3 / 4` | 可读、写、通知；摄氏度，`16..30`、步长 `1`。按原生可达整数温度编码。 |
| `fan-control.fan-level` | `4 / 2` | 可读、写、通知；`0` 自动风、`1` 低风、`2` 中风、`3` 高风。 |
| `fan-control.vertical-swing` | `4 / 4` | 可读、写、通知的上下摆风布尔值。 |
| `ac-function.ac-ctrl-range` | `8 / 6` | 读取、订阅当前配码的模式、温度与风速限制；不修改配码配置。 |
| `ac-function.ac-state` | `8 / 7` | 读取、订阅伴侣状态报告，作为 mcn04 的运行状态来源。 |

绑定从真实服务与属性构造，表中编号是代表描述的输入，不作为所有空调的通用常量。标准空调服务与它所属的风机控制共同构成一个空调功能，风机控制不重复发布为独立风扇。

代表配置的 `ac-ctrl-range` 提供以下约束，作为模式关系的设计输入：

| 模式 | 可设温度 | 可设风速 |
| --- | --- | --- |
| 制冷、制热、送风 | `16..30℃`，步长 `1℃` | 自动、低、中、高。 |
| 自动 | 温度列表为空，不开放调温。 | 自动、低、中、高。 |
| 除湿 | `16..30℃`，步长 `1℃` | 低风。 |

使用 `models` 中的 `mode`、`temps`、`speeds` 解释上述约束，并与 MIoT 声明的有效编码和量程相交。模式字段提供的取值是实际编码，不按列表位置重新编号。空温度列表表示该模式不接受调温。

`directs` 等尚无明确语义依据的私有字段保留在诊断中，不直接等同于 `vertical-swing` 的布尔取值，也不用于推导额外风向能力。上下摆风以标准布尔属性契约接入，来源明确拒绝操作时返回失败。

该描述没有环境温度读数，也没有压缩机工作状态或自动风的实际挡位读数。芯片温度、电功率、目标温度及自动风编码均不替代这些信息。

## 功能模型与内置补丁

沿用[设备功能组合设计](../2026-10-29-device-capability-composition/spec.md)：物理设备保留父端点，空调功能持有独立子端点，稳定功能标识以主体空调服务为锚点，例如 `air-conditioner:3`。风速、摆风与跨服务的伴侣状态都属于该功能，不产生第二套控制身份。

通用空调模型表达电源、运行模式、唯一目标温度、风速设置、可选上下摆风及有效的参数约束。空调的风速使用具有明确语义的枚举，自动风不视为零速或关机。

mcn04 补丁拥有 `ac-state` 的解码及 `ac-ctrl-range` 的解释。设备层只接收有效的空调状态和约束，不按型号分支，也不解析厂商字符串。来源状态、请求目标和命令结果分别保存。

mcn04 的正常状态读取与通知统一使用 `ac-state`，避免标准属性和整包报告同时竞争同一逻辑字段。标准属性保留为控制绑定；不因为它们也声明了通知能力而另建一套并行状态汇总。其他采用标准属性反馈的空调不要求具有 `ac-state` 或 `ac-ctrl-range`，按已确认的标准枚举与量程构造控制约束，不套用 mcn04 的配码限制；来源明确拒绝操作时照实返回失败。

伴侣状态中的 `P` 表示电源（`0` 开、`1` 关），`M` 表示上述五种模式，`T` 表示伴侣报告的温度设定，`S` 表示风速设置，`D` 表示摆风（`0` 开、`1` 关）。有效字段在一次状态提交中更新，沿用来源和时间元数据；不合规字段保留最近有效观测并产生诊断，不能以缺失字段补造开关或温度。

mcn04 的控制范围是运行期来源输入，启动与恢复时读取、正常运行时订阅；不写死书房的温度或除湿限制。它限制当前命令，不因切换模式而重新分配端点或改变固定的 Matter 能力集合。范围尚未取得或当前来源尚未重新确认时，依赖它的设置返回状态未就绪；独立开关和不依赖范围的上下摆风仍按各自命令处理。输入只在边界解析校验，单次读取或解析失败保留最近有效范围并显示诊断，不额外引入异常范围导致的停控状态或恢复流程；来源生命周期失效仍沿用既有隔离规则。

## 组合操作复用

共享属性传输直接使用现有 `submit_properties`、设备写入门控、实际路径选择、发送前检查、回执结算和命令诊断。风扇已有的逐步请求生命周期、待发目标合并和关机打断逻辑中，空调也需要的部分做小范围提取，供两种功能共同使用；不复制一套执行循环，也不扩展为任意工作流引擎。

空调侧只负责生成有明确依赖的步骤、编码原生属性，以及判断本次目标是否仍然有效。通用执行部分不认识空调模式或 mcn04 属性编号。原有风扇行为由现有回归继续约束。

| 操作 | 原生执行规则 |
| --- | --- |
| 独立开机、关机 | 只写 `on`，保留伴侣记忆的模式、温度和风速；`Toggle` 要求电源观测已知。 |
| 选择运行模式 | 必要时写 `on = true`，受理后写目标模式。未显式指定的温度、风速和摆风由伴侣自身联动并反馈。 |
| 单独调温 | 验证伴侣当前记忆模式允许调温，只写目标温度；不附带开机或切换模式。 |
| 非零风速或自动风 | 沿用现有风速控制的开机前置规则，必要时先开机，再写风速；不切换空调运行模式。 |
| 风速关闭 | Matter 风速零或 `FanMode = Off` 统一执行空调关机，不把原生 `fan-level = 0` 当作关闭。 |
| 上下摆风 | 只写摆风属性，不附带开机、调温或切换模式。 |
| 一次明确的组合目标 | 先验证整组参数，再按“必要的开机 → 模式 → 温度 → 风速 → 摆风”生成实际需要的步骤。模式约束使用本次目标模式；未指定模式时使用伴侣当前记忆模式。 |

温度必须落在当前模式的可达取值中；本轮不以虚假的小数精度表达整度控制。超出量程或不满足原生步长的请求返回约束错误。因当前模式而不可设置的温度、风速返回当前状态不允许，不自行切换到其他模式。

同一功能按已提交命令顺序处理。多个 Matter 属性写入保持各自操作身份，不把一组属性写入当成原子事务。确实携带多个目标的逻辑操作才统一展开上述步骤。

模式步骤已经受理、对应反馈尚未到达时，紧随其后的设置使用已受理模式作为执行上下文，避免仍按旧模式错误拒绝调温或调风；这个上下文只用于命令规划，不修改 Home 状态。新的有效模式反馈接管该上下文；模式步骤失败、来源失效或实例退出时清除。执行时仍检查当前控制范围和操作所有权。

前一步受理后再发下一步，全部必需步骤受理后返回本次操作成功。任一步骤失败或超时，结束操作并保留已经发生的结果；不回滚、不从头重做，也不靠固定延时等待空调本体动作。

相邻且尚未发送的同类参数调整只保留最新目标，不跨开关或模式操作合并。关机取消它之前待发的设置，并阻止旧组合继续发送剩余步骤；已经发送的步骤按现有机制结算后再发关机。关机之后的新操作按新意图执行，旧回执不能恢复被取消的目标。

已发送过关机但尚未收到新的开机反馈时，不使用旧的开机缓存省略后续开机步骤。可能已经发送的写入不在另一条路径自动重放；明确尚未发送的尝试才按现有机制重新选路。米家侧通知只更新观测，不额外引入外部操作识别或抢占机制。

## Matter 表达

空调子端点采用 Room Air Conditioner（`0x0072`，revision `3`），提供 Descriptor、Identify、On/Off、Thermostat 和 Fan Control。物理父端点继续承载身份、名称与可用性。On/Off 使用该设备类型要求的 Dead Front 行为；操作入口和功能名称仍归属于同一个空调。

Thermostat 使用 `0x0201`、revision `11`；代表设备提供 Heating、Cooling、AutoMode 和 LocalTemperatureNotExposed。不提供日程、预设、占用感知、无人温度设定、温度补偿或需求推断。使用当前锁定 `rs-matter` 的生成接口接入现有异步命令和实际观测，避免默认处理器恢复设置时驱动设备。

| Thermostat 项目 | 映射 |
| --- | --- |
| `SystemMode` | 电源关闭为 `Off`；开机时将伴侣模式映射为 `Cool`、`Heat`、`Auto`、`FanOnly` 或 `Dry`。电源或所需模式未知时读取失败。 |
| 写入 `SystemMode` | `Off` 关机，其余已支持值进入模式设置流程。没有对应能力的枚举拒绝。 |
| `LocalTemperature` | `null`，不使用目标温度或芯片温度填充。 |
| `OccupiedCoolingSetpoint`、`OccupiedHeatingSetpoint` | 同时投影伴侣唯一的温度设定，以 `0.01℃` 编码；不创建两个独立的本地目标或自动冷热区间。 |
| 写入两个设定属性 | 都对应伴侣唯一的目标温度，遵守当前模式限制且不切换模式；自动模式的温度列表为空时拒绝调温。 |
| 量程与 `MinSetpointDeadBand` | 发布冷热绝对上下限，代表设备为 `1600..3000`；不发布可配置限值属性。单目标采用 `MinSetpointDeadBand = 0`，对该属性的兼容性写入按规范忽略并保留固定值。 |
| `ControlSequenceOfOperation` | 代表设备为 `CoolingAndHeating`，管理写入按规范忽略并保留该值。 |
| `SetpointRaiseLower` | 基于已有温度设定计算目标，使用相同量程和步长规则；`Both` 对同一个目标只执行一次。未知基线时拒绝，超出限值按命令规范限制到边界。 |
| 运行状态 | 不发布缺少真实输入的可选 `ThermostatRunningMode`、`ThermostatRunningState` 或冷热需求属性。 |

这两个冷热设定属性是对同一个原生设定的投影，不表示 mcn04 提供独立冷热阈值。伴侣在自动模式下报告的保留温度也不作为自动模式可调目标；MiGate 只切换原生自动模式，不根据环境温度自行控制冷暖。Home 对这种原生自动模式的入口与显示需与实际协议写入对照。

Fan Control 使用 `0x0202`、revision `6`，提供 MultiSpeed 和 Auto，`SpeedMax = 3`，`FanModeSequence = OffLowMedHighAuto`。上下摆风的有效布尔绑定成立时提供 Rocking，仅使用 `RockUpDown`；不提供其他摆动方向、自然风或 Step。

| Fan Control 项目 | 映射 |
| --- | --- |
| `FanMode` | 已确认关机为 `Off`；开机时按伴侣风速报告映射为 `Auto`、`Low`、`Medium`、`High`。 |
| `SpeedSetting`、`PercentSetting` | 关机为 `0`；开机且自动风为 `null`；普通风速为 `1/2/3` 与 `33/66/100`。 |
| 写入挡位或百分比 | 零值关机；非零百分比按 `ceil(3 × p / 100)` 选择真实挡位，随后应用当前空调模式的限制。写入 `null` 保持原值、不发命令并返回成功；它不用于选择自动风。 |
| 写入 `FanMode` | `Auto` 选择原生自动风；低、中、高选择对应挡位。`Off` 关机；已弃用的 `On` 按 `High`，`Smart` 按已提供的 `Auto` 处理。 |
| `SpeedCurrent`、`PercentCurrent` | 已确认关机为零；普通风使用伴侣报告的挡位投影。自动风没有实际挡位输入时保持未知，非空属性读取返回失败，不填零或编造挡位。 |
| `RockSetting` | 读写伴侣上下摆风设置；其他方向位拒绝。 |

普通风的当前值表示伴侣报告的风速设置，不是风机转速测量。自动风下可以明确报告自动模式和空的设定值，但不能保证客户端同时显示一个数值风速。Home 缺少某个标准入口或对未知属性的处理受限时，分别记录客户端表现与协议能力，不用额外开关伪装空调模式。

所有非空属性在所需观测未知时读取失败，不填默认温度或风速。风速设定的 `null` 专门表示已确认的自动风，不兼作未建立状态基线的占位值。

## 同步、恢复与模块职责

控制、读取和通知继续独立选路。`pushAvailable` 按当前中枢对设备的声明处理，不固化为 mcn04 型号特征；本地通知不可用不直接排除本地读写。启动、来源恢复和切换按既有机制重新建立状态与控制范围基线，正常运行依靠通知，不新增周期轮询或每条命令后的整组补读。

重启恢复身份、端点、名称及配对，再读取伴侣状态。待发操作、请求目标和普通状态读数不作为恢复控制的依据。旧来源、旧订阅、退休实例及迟到读取的隔离沿用现有规则；可见投影变化更新对应 Matter 数据版本并通知。

| 模块 | 本轮增量 |
| --- | --- |
| `xiaomi/capability` | 新增空调功能识别及 mcn04 内置补丁，关联标准空调、风机控制与真实状态绑定。 |
| `device` | 增加空调有效模型、观测与操作；复用必要的逐步请求生命周期，保留功能级隔离。 |
| `xiaomi/adapter` | 解析伴侣状态和控制范围，编码空调步骤，使用现有共享传输、订阅和选路。 |
| `matter` | 发布一个空调功能子端点，处理各协议入口、共享目标投影与属性报告。 |
| `configuration`、`storage`、`app` | 接入新的有效模型和发布形状，使用现有描述重算、配置事务及身份分配；已有受支持配置仍可读取。 |
| `terminal` | 将空调纳入显式功能 `on`／`off`，`status DID` 显示模式、温度、风速、摆风、控制范围、来源与最近命令步骤。 |

沿用现有诊断区分功能未支持、读取失败、通知未就绪和命令失败；状态未知不解释为关机。控制范围的不可设项要能说明当前模式限制，自动风未知当前挡位要能与读取失败区分。

README 增加空调功能与代表型号；运行指南说明空调功能标识、状态诊断及恢复操作；已知限制说明唯一目标温度、自动模式和自动风的显示边界，以及 Home 缺少入口时的实际能力区别。

## 验证要求

自动化围绕新增契约覆盖：

- mcn04 原始描述、跨服务归属、真实功能锚点、可选摆风及控制范围解析；符合本轮契约的标准反馈空调不依赖型号白名单，不满足契约的其他能力形态不接入；自动模式不调温、除湿的低风限制、风速零与自动风的区别。
- 标准属性写入、整包反馈解码、初始未知、部分无效字段、模式联动及一次报告更新多个字段；协议回执不改写观测。
- 组合命令预校验、顺序、逐步失败、待发合并、关机打断、旧开机缓存和晚到回执；共享部分提取后既有风扇行为保持。
- 本地与云端各路径的读写、通知、发送前切换、恢复和不重放；已退休来源与旧读取不能更新当前状态。
- Matter 设备形态、五种运行模式、共享温度投影、参数边界、风速与摆风、自动风未知值、数据版本和持续订阅。
- 配置往返、缓存描述重新识别、端点与配对恢复，以及已有插座、灯光、灯组、环境测量、状态传感器、窗帘和风扇核心回归。

沿用仓库已有检查：`cargo fmt --check`、`cargo test --locked`、`cargo clippy --locked --all-targets -- -D warnings` 和当前 macOS 环境的 `cargo build --locked`。本轮不新增 Linux 构建、交叉编译或 CI 设施，也不将 Linux 构建列为完成条件。

真机验证使用书房代表设备和当前 macOS 环境，以伴侣状态及 Home 自动同步作为判据：

| 场景 | 尺度与判据 |
| --- | --- |
| 基本控制 | 独立开关、五种模式、制冷及制热下的 `16/26/30℃`、自动及低中高风速、上下摆风各 `3` 轮。只有当前模式允许的组合要求成功；不允许的组合须明确拒绝。 |
| 组合与连续操作 | 关闭→制冷 `26℃` 自动风、制冷→制热 `24℃` 低风、制热→除湿 `26℃` 低风、除湿→送风高风、送风→自动中风，各 `3` 轮；覆盖快速改值后关机，以及关机后新的显式操作。 |
| 米家侧变化 | 电源、模式、目标温度、风速和摆风各 `3` 轮；Home 页面持续打开，观察新的伴侣报告及对应更新。 |
| 重启、断连恢复、路径切换 | 各 `1` 轮，确认状态与订阅恢复、身份保持及旧控制不重放；分别记录实际控制、读取和通知路径。 |

正常网络且来源通知已就绪时，影响 Home 投影的伴侣状态变化在 `3` 秒内反映到 Home。恢复观察上限为 `20` 分钟：断连和路径恢复从通信条件恢复起计，重启从 Matter 服务重新提供起计。

Home 的最低验收标准是开关、制冷／制热切换、整数调温及这些操作对应的状态自动刷新；任一必达项失败均不能通过验收，不能仅记录为客户端限制。自动、送风、除湿、风速和摆风若没有 Home 入口，可以使用标准 Matter 客户端核对协议行为，并记录 Home 的实际入口与显示限制；存在 Home 入口时仍需确认其可操作性。

若某条真实路径在现场不可用，分别说明现场覆盖与自动化覆盖，不把切换后的缓存值当作新通知。无需逐项观察空调本体动作，也不以压缩机启动时间作为 MiGate 成功标准。
