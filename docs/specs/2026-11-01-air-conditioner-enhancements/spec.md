# 空调伴侣接入增强

## 目标与范围

以 `51fa5cc` 为代码基线，在[空调控制与状态同步](../2026-10-30-air-conditioner-control/spec.md)基础上增加两项能力：通过终端为每个空调功能手动绑定环境温度来源，以及在同一个 Home 空调入口内提供自动风控制。

环境温度仅用于展示，空调仍执行自身的原生控制逻辑。风速继续属于同一个空调功能，共享原有观测、命令队列和逐台配码约束。温控的原生自动模式与自动风速是两个独立设置。

本轮以 `lumi.acpartner.mcn04` 为代表，增量建立在现有通用空调功能上，应用于已经满足空调契约的设备，不扩大空调识别范围。温度来源使用已经接入的环境温度功能，不按米家房间自动关联，不接入 Home 中由其他网桥提供的传感器。

保留一个空调入口作为界面目标，采用同一端点声明 Thermostat 与 Fan 的方案；不新增独立风扇端点或模式开关。独立温度传感器保留已有展示。童锁、电量异常、已有风速与摆风刷新限制，以及设备自身的模式联动不在本轮修复范围。

## 方案依据与取舍

`hass-xiaomi-miot` 将风速能力提供给空调实体；Home Assistant 的 HomeKit Bridge 根据这些能力，在同一配件内建立关联到 Thermostat 的 Fanv2 服务。存在自动风和普通风速等有效组合时，桥接层提供 `TargetFanState`，再把用户操作交回空调实体。该结构可以作为同一空调共用状态与控制的参考，但 HAP 关联服务不能直接等同于 Matter 端点。[空调实体](https://github.com/al-one/hass-xiaomi-miot/blob/master/custom_components/xiaomi_miot/climate.py) · [HomeKit 创建条件](https://github.com/home-assistant/core/blob/2026.10.4/homeassistant/components/homekit/type_thermostats.py#L262) · [关联服务与命令映射](https://github.com/home-assistant/core/blob/2026.10.4/homeassistant/components/homekit/climate_base.py#L291)

讨论过的组织方式与取舍如下：

| 方案 | 取舍 |
| --- | --- |
| 新增风扇子端点，保留原空调风速入口 | 复用控制容易，但可能增加入口或重复控件，不采用。 |
| 将风速全部移到新增风扇子端点 | 改变既有空调页面的操作方式，不采用。 |
| 同一空调端点声明 Thermostat 与 Fan | 保留一个逻辑功能和现有端点，作为本轮选定方案；Home 的实际呈现仍须验证。 |

Matter 支持在一个端点声明多个设备类型，声明需同时满足对应类型的要求。该能力提供结构依据，不保证 Apple Home 会合并显示或开放自动风入口。类型列表把 Thermostat 放在首位，也不构成对 Home 界面布局的保证。[多设备类型端点说明](https://docs.silabs.com/zap-tool/latest/zap-users-guide/multiple-device-types-per-endpoint)

## 手动传感器绑定

### 终端入口

```text
bind-sensor TARGET_DID TARGET_FUNCTION SENSOR_DID SENSOR_FUNCTION
unbind-sensor TARGET_DID TARGET_FUNCTION
status TARGET_DID
```

`TARGET_FUNCTION` 和 `SENSOR_FUNCTION` 均使用 `list` 展示的稳定功能标识。例如目标可以是 `air-conditioner:3`，来源可以是 `temperature:3:7`。命令名称表达传感器绑定，具体类型从来源功能识别；本轮仅支持空调功能绑定环境温度功能，不引入任意功能之间的关联框架。

| 操作 | 行为 |
| --- | --- |
| 首次绑定 | 校验目标为空调、来源为有效环境温度功能，保存关系后生效。 |
| 对同一空调再次绑定 | 替换其当前温度来源；绑定相同来源时返回已绑定，不产生额外变更。 |
| 解除绑定 | 清除关系，环境温度变为未知；已经未绑定时返回未绑定，不产生额外变更。 |
| 查询状态 | 显示来源设备与功能、当前环境温度、时间和未知原因；与空调目标温度分别标识。 |

一个空调功能至多绑定一个温度来源，同一温度功能可以供多个空调使用。关系以目标和来源的 `FunctionKey` 保存，包含设备来源、DID 与功能标识，不依赖设备名称、房间或端点编号。

新建或更换绑定要求两端都属于当前家庭、具有当前访问资格且功能已经识别。来源暂时离线不妨碍保存绑定，能否显示读数按下节判断。不存在的标识、错误功能类型或无访问资格在命令入口返回明确错误，不改变旧关系。

终端通过应用层已有的配置所有权提交变更：先校验和准备关系，再保存，成功后替换运行关联。保存失败时旧关系与旧投影继续有效，终端报告失败。绑定操作不向空调或传感器发送控制命令。

关系保存到现有已提交配置中，并在正常目录更新和重启后保留。绑定属于当前账号与家庭的配置；账号或家庭变化时清空绑定，不保留多账号、多家庭的绑定历史。来源访问资格仍由现有接入流程确认，保存的绑定本身不授予访问权限。普通温度读数不随绑定持久化。

### 温度状态

绑定复用来源温度功能已有的读取、通知和数值观测，不创建第二套 MIoT 订阅或定时轮询。环境温度变化只更新空调的温度投影，不产生开关、模式、目标温度或风速命令。

| 情况 | 空调环境温度 |
| --- | --- |
| 未绑定 | 未知。 |
| 已绑定，尚未取得有效读数 | 未知。 |
| 来源功能有效且有当前可用读数 | 使用该来源的读数及其时间元数据。 |
| 来源功能的获取路径已确认不可用、设备被移除或访问被撤销 | 未知；最近读数可留在诊断中。 |
| 正常静默 | 保留有效读数，不按静默时长推断离线。 |
| 单次读取或订阅失败，但仍有有效获取路径和已有有效读数 | 保留读数，展示相应同步诊断。 |
| 更换来源 | 解除旧关联，采用新来源的当前有效读数；新来源没有有效读数时为未知。 |
| 来源失效后恢复 | 保留原绑定，待原来源重新取得有效读数后恢复展示。 |
| 重启 | 恢复绑定关系，等待来源正常读取或通知建立读数。 |

可用性针对所绑定的温度功能判断；同机其他控制或测量功能可用，不代表该温度功能仍有有效获取路径。蓝牙或代理设备本体缺少可靠在线信号时，继续按已有来源语义判断，不新增物理在线推断。

来源被移除或暂时失去访问资格后，绑定关系保留为无有效来源的配置；原对象重新获得访问资格并接入后恢复关联，不替换成其他传感器。解除绑定按保存的目标标识清除既存关系，不要求来源在线或仍在目录中。

更换来源使用正常的关联解除与建立过程，沿用现有来源生命周期隔离，不新增绑定代次、迟到更新缓冲或专项防御机制，也不为低频更换操作新增迟到更新专项测试。

`status` 区分空调的目标温度与绑定的环境温度，至少显示绑定对象、有效值或未知原因、来源时间和接收时间。保留的最近读数明确标记为诊断值，不能代替当前未知的环境温度。

## Matter 表达与 Home 目标

### 环境温度

在现有空调 Thermostat cluster 中提供绑定温度的 `LocalTemperature`，单位为 `0.01℃`，复用已有摄氏度测量转换。该值与空调唯一目标温度分别保存和报告，两个冷热设定属性继续投影原有目标温度。

空调统一声明可提供环境温度，移除现有 `LocalTemperatureNotExposed` 特性；是否已经绑定或当前能否读取作为运行状态处理。`LocalTemperature` 保持可空：未绑定或没有当前有效温度时返回 `null`，真实读数为 `0℃` 时正常返回零。无法被 Thermostat 表示的读数保持空值并报告映射诊断，不修改来源原始值。[Thermostat 定义](https://github.com/project-chip/connectedhomeip/blob/v1.6.0.0/data_model/1.6/clusters/Thermostat.xml)

温度绑定、更换、解除及来源可用性变化不改变端点、设备类型或特性集合，不因这些操作重建 Matter 服务。环境温度的协议投影发生变化时更新对应数据版本并通知订阅，包括数值变化及数值与空值的切换；相同投影值的时间元数据变化不单独触发温度属性报告。

Home 在有读数时应按客户端显示精度呈现正确环境温度。无当前有效读数时，MiGate 保持未知并在协议中返回 `null`；Home 可能显示 `0℃` 或保留旧温度，将此作为客户端显示限制接受，不以其数值判断来源是否有效，也不为改变界面而填入温度。

### 同入口风速

现有空调子端点的 `DeviceTypeList` 按以下顺序声明：

1. Thermostat：`0x0301`，revision `6`。
2. Fan：`0x002B`，revision `4`。

端点继续提供现有 Descriptor、Groups、Identify、On/Off、Thermostat 和 Fan Control，满足两种类型的相关要求。保留同一个空调功能标识、原生绑定和运行实例，不创建独立风扇功能或第二套命令队列。[Thermostat 设备类型](https://github.com/project-chip/connectedhomeip/blob/v1.6.0.0/data_model/1.6/device_types/Thermostat.xml) · [Fan 设备类型](https://github.com/project-chip/connectedhomeip/blob/v1.6.0.0/data_model/1.6/device_types/Fan.xml)

Fan Control 沿用现有 MultiSpeed、Auto 以及有效绑定成立时的上下摆风能力。自动风映射到原生自动风，普通风速映射到低、中、高；自动风的实际挡位仍保持未知，不为了客户端显示而补造数值。

控制语义沿用既有空调契约：风速零或 FanMode Off 关闭空调，设置非零或自动风必要时先开机但不切换空调运行模式，摆风只调整摆风。参数仍按各台设备当前配码范围校验；不照搬 HomeKit Bridge 的风扇开关或退出自动风时的默认挡位策略。

Home 必须保持同一个空调入口，并在该入口内提供实际可操作的自动风控制，同时保留既有温控操作。若组合类型仍缺少自动风入口、变成额外入口或破坏温控行为，则该方案未达到目标，需要重新讨论；不自动改成独立风扇或额外开关方案。

### 身份与配置

类型列表与环境温度特性进入固定发布形状，确保配置比较反映实际对外声明。首次应用新形状时保留物理设备和空调功能的身份、端点、名称与配对，通过配置版本变化使客户端重新读取声明。

已有开发数据如需补充绑定集合或更新发布版本，采用停机后一次性调整；不为此增加自动迁移逻辑、升级标记或迁移专项测试。后续日常绑定操作走正常配置事务，普通温度更新不修改持久配置版本。

## 数据流与职责

数据流为：终端选择功能 → 应用层保存关系 → 关联既有温度功能 → 生成空调环境温度投影 → Thermostat 读取与变化报告。风速仍走现有空调命令与反馈路径。

| 模块 | 增量职责 |
| --- | --- |
| `configuration`、`storage` | 保存目标到传感器功能的关系，保持配置更新时的关系一致性；使用 Matter 提供的固定发布形状判断结构变化。 |
| `app` | 接收绑定命令并使用既有配置事务；管理运行关联的建立、替换、解除及来源恢复，向空调投影提供所选温度。 |
| `device` | 提供环境温度投影的值、未知状态与变化通知，保持与目标温度、空调命令分离。 |
| `xiaomi/adapter` | 复用测量读取与订阅，提供所选温度功能的有效来源状态；通过有类型的接口供关联使用，不让上层解析诊断文本。 |
| `matter` | 在同一空调端点发布两个设备类型，将类型列表和温度特性纳入固定发布形状；投影环境温度并报告变化，复用现有空调风速处理。 |
| `terminal` | 增加 `bind-sensor`、`unbind-sensor` 和帮助信息，扩展空调状态中的传感器绑定诊断。 |

模块间以有效功能标识、温度观测和来源状态通信。绑定层不解析 MIoT 原始描述或厂商状态字符串，Matter 层不查找设备目录或自行保存关系。所需来源状态复用现有接入模型，不为绑定另建来源生命周期系统。

README 补充两项增强的能力边界，运行指南补充绑定、更换、解除及未知温度排障操作，已知限制与最终实际可用的 Home 能力保持一致。

## 验证要求

自动化围绕新增行为验证：

- 终端正常绑定、更换、解除与查询；目标和来源类型、标识及访问资格的边界校验；一个来源供多个空调使用。
- 配置保存、重启恢复和保存失败保留原关系；正常目录更新不丢失用户绑定，身份和端点保持。
- 有效温度、首次未知、未绑定、来源不可用、访问撤销及恢复；同机其他功能可用时仍按温度功能自身的来源状态判断；正常静默和单次失败保留有效读数。
- 更换来源后使用新来源，解除后为空值，验证正常关联切换。
- 环境温度的数值与空值投影、真实零值、数据版本及持续订阅；环境温度变化不产生空调控制操作。
- 同端点双类型声明和固定形状比较，保留现有风速能力；运行绑定变化不改变发布形状或重启 Matter 服务。
- 继续运行已有空调控制、配码约束及其他设备的核心回归。

Home 使用书房、卧室两台 mcn04 和至少一个已接入的真实环境温度功能进行核对。按场景覆盖，不要求固定重复轮数；发现异常、结果不明确或修复后需要复核时再重复。

| 场景 | 判据 |
| --- | --- |
| 环境温度绑定、解除与重新绑定 | 在同一空调入口检查有效值；解除后 MiGate 显示未知且协议返回空值，Home 的未知显示按已知限制处理；独立传感器保持原有展示。 |
| 温度正常更新 | 观察一次产生可见数值变化的有效读数，核对传感器、空调投影与 Home 一致。 |
| 自动风与普通风切换 | 每台在当前配码允许的模式下完成切换，确认 Home 入口、实际原生请求及伴侣反馈。 |
| 原有空调控制 | 两台分别核对开关、制冷、制热、原生 Auto、调温及支持的风速和摆风；按各自配码约束判断，既有设备原生联动仍以伴侣反馈为准。 |
| 重启 | 绑定、身份、端点与配对保持；重新取得有效读数后显示环境温度。 |

正常网络且来源已就绪时，环境温度读数与绑定变更应在保持打开的 Home 页面中及时反映，无明显延迟；不要求严格计时，也不将传感器的物理采样周期计入界面响应。温度来源失效与恢复以自动化测试覆盖，不要求真机场景验证。

同一个空调入口内的自动风控制，以及环境温度有效值的正确呈现，均为本轮目标。仅验证协议读写不能替代这些 Home 表现；自动风缺少入口或出现额外风扇入口，不能记为目标已完成。未知温度须保持 MiGate 状态与协议表达准确，Home 的空值显示不作为完成条件。
