# IP 局域网直连与旧 miIO 适配

## 目标与范围

以 `a78f6a1` 为代码基线，在现有 Xiaomi 来源中增加设备 IP 局域网直连，与中枢、云端共同参与统一选路。标准 MIoT 属性接口与旧 miIO 命令接口共用通信基础，分别处理业务编码和反馈转换。

首批范围为书房 `dmaker.fan.p5c` 和客房、客厅两台 `lumi.acpartner.mcn02`。p5c 沿用现有风扇功能；mcn02 沿用已经接入的通用空调功能，增加旧命令的直连映射。后续型号根据实际需求扩展，不在本轮探测或导入其他型号的命令集合。

保留现有账号认证、家庭归属、设备准入、通用功能与补丁、Matter 发布及传感器绑定。直连是同一设备新增的通信路径，不创建第二个 Xiaomi 来源、设备、功能或端点。身份、名称、配对和用户绑定保持。

实现仍在现有 Rust 单包内。运行与验证以当前 macOS 环境为范围，不增加 Linux 部署、交叉编译或 CI 要求。对已接入的可读状态增加周期读取，沿用实际可用的读取路径；不增加设备直连订阅、任意 miIO 命令终端、遥控码配置、电气测量、新设备类型或用户自定义映射脚本。

当前环境为 macOS 27.2（26B123）、Apple Silicon，MiGate 与代表设备处于同一局域网，使用现有米家账号和已绑定家庭。IP 地址属于可更新的连接信息，不作为稳定设备身份。

## 方案与复用边界

采用一套局域网通信实现，其上分别承接 MIoT 属性请求和旧 miIO 转换。

| 方案 | 取舍 |
| --- | --- |
| 共用通信层，分别处理 MIoT 属性与旧 miIO 映射 | 选用。握手、凭据、请求关联和恢复复用，业务接口差异保留在来源适配层。 |
| 两套独立客户端，仅共用报文编码和存储 | 不采用。连接状态、超时与恢复仍会重复，增加统一选路的接入成本。 |

旧 miIO 采用“共用转换器＋内置协议映射表”。映射描述已有属性与旧命令、参数和反馈字段之间的关系；执行器使用这些规则完成转换，再交给共用通信层。现有功能补丁继续处理自然风、特殊状态格式、执行前置条件等功能语义。

旧 miIO 映射仍需依据已知型号或已确认的协议家族维护。命令语义相同的型号可以共用规则，有差异时补充映射或专用解析；不能从 MIoT 描述自动推导未知旧命令，也不能仅因厂商、品类或命令名称相似就判定兼容。本轮只内置 mcn02 所需映射，使用 Rust 结构表达，不建立模板语言、脚本运行时或映射继承框架。

型号适配依据已验证来源的型号和已识别的有效绑定确定；同一份适配策略供识别说明、直连资格、身份探测、读写和选路使用。策略从已提交的来源描述推导，恢复时可重算，不单独增加持久字段；说明性补丁信息不授予访问资格。策略语义变化时按现有来源生命周期替换运行实例，保留设备身份及端点。

标准 MIoT 直连消费现有有效属性绑定，不为 p5c 重写风扇业务。旧 miIO 转换后的读写结果也进入同一套属性处理、功能状态与 Matter 投影，不让 `device` 或 `matter` 按协议或型号分支。

## 设备资格、凭据与发现

### 初次建立直连

现有账号与家庭接入流程负责确认设备归属和访问资格。正常云端目录同步补充设备的局域网地址、token 与型号信息；缺少有效凭据或不满足对应接口要求时，该设备不成为直连候选，已有中枢和云端能力独立保留。

局域网发现只提供地址线索，不授予接入资格。只为当前家庭中已经接入、且属于本轮协议范围的 IP 设备建立直连；BLE 和代理子设备不通过该机制获得 IP 直连路径。

首次使用地址时，先完成握手，再使用设备 token 进行受校验的加密通信，确认 DID 与型号，并以对应接口的只读业务请求确认可用性。hello 回应、IP 相同或云端在线标记均不能单独证明直连可用。

### 持久化与离线重启

在现有数据目录的数据库中保存独立直连记录，与 Matter 发布配置分开。记录关联现有账号、家庭、DID 和型号，保存设备 token 及最近确认的地址；账号服务区沿用现有账号配置。通知就绪、连接在线和普通运行状态不作为可直接恢复的事实持久化。

启动时恢复已提交配置、原始描述和现有访问撤销记录，使用缓存的家庭资格及直连凭据建立候选。优先尝试最近确认的地址，重新认证并读取状态后投入使用。已完成首次接入的设备不必等待云端登录刷新或中枢上线，能够在外网不可用时恢复直连。

进程冷启动时先运行 Xiaomi 来源，复用已有读取与通知采集当前发布功能、必要来源和共享电量的初始状态。每个可读属性收到有效观测或首轮读取明确失败后视为已有结果；尚无路径或未完成的项目继续等待。全部项目有结果后启动 Matter；从开始等待起最多 20 秒，超时仍启动并保留未知状态和原有恢复机制。等待期间来源、终端、退出和配置变更继续运行，配置变更采用最新已提交的对象且不延长截止时间；没有待采集项目时立即启动。此等待只在进程冷启动发生，后续 Matter 实例重建不重复等待。保留首次读取失败、设备无法提供值及后续状态变化的实际语义，不为提前启动填造状态或重新发送读取。

设备 token 与云端 OAuth token、中枢证书分别管理。云端登录过期或中枢证书过期本身不使设备 token 失效。已知的访问撤销、设备移除、退出账号或家庭范围变化仍执行现有资格规则，旧范围内的直连不能继续生效；不增加多家庭历史或切换框架。

新增存储保持现有单版本 schema 的管理方式。现有开发库如需调整，在停机备份后一次性补充结构，保留认证、配置、身份与配对数据，不通过创建空数据目录完成升级，也不引入通用历史迁移框架。token 沿用现有认证数据的存储保护，不出现在日志、状态输出或文档示例中。

### 地址与凭据更新

已知地址不可用时，触发有限时的局域网发现；发现可以收集回应，但只为已经具备资格的目标设备更新候选地址。新地址必须通过 DID、型号和 token 对应的认证通信确认，确认后保存。健康闲置时不持续扫描网络。

正常目录同步可以提供新的地址或 token。新凭据先作为候选进行验证，保存成功后替换相应直连上下文；无效候选不覆盖仍有效的记录。凭据输入无效或来源明确拒绝凭据时，该直连不可用，等待正常目录同步或相关连接信息变化后重新验证，不循环尝试同一已知无效凭据。普通响应超时按通信失败恢复，单个报文校验失败按无效报文处理，均不能单独判定 token 失效。其他路径按自身资格继续运行。

地址变化、设备重启和凭据更新不改变设备或功能身份，也不解除温度绑定。

## 共用局域网通信

新增通信模块负责 UDP 54321 上的 miIO 报文、握手、设备时间戳、token 加密与校验、请求关联和有界等待。MIoT 属性请求与旧命令共用这部分实现。

- 报文按 miIO 格式处理长度、DID、时间戳、校验与加密载荷；token 在输入边界构造为有效的 16 字节凭据。加密、解密和报文校验采用已有算法实现，不自行设计协议。
- 握手提供连接及时间信息，身份与业务能力仍以随后的认证响应确认。后续通信按设备时间和本地经过时间生成报文，必要时重新握手，不增加健康空闲期间的保活读。
- 每个在途请求保留对应设备、实际对端、请求 ID、发送阶段和截止时间。收到的报文经边界解析与校验后，只能结算匹配的请求；已结束请求的迟到应答不重新生效。
- 一次直连业务尝试的时间上限为 10 秒，包括本次必要的握手与业务响应等待。发现和恢复探测同样必须有界，不在一次控制内叠加隐式重试。
- 区分尚未发出与已经发出或可能发出。前者可以按当前选路重新安排；后者只等待原请求结算，不在本路径或其他路径自动重发。
- 业务拒绝保留设备错误，不转成成功或静默忽略；合法的参数拒绝本身不表示通信路径失效。

通信模块只处理方法、参数、响应及传输结果，不负责空调模式、风扇挡位、家庭资格或 Matter 状态。

## 两类业务接口

### p5c：标准 MIoT 属性直连

p5c 的实例为 `urn:miot-spec-v2:device:fan:0000A005:dmaker-p5c:1`，继续使用功能 `fan:2` 和既有 `dmaker.fan.straight-wind` 补丁。

| 现有绑定 | SIID / PIID | 直连处理 |
| --- | --- | --- |
| 电源 | `2 / 1` | 标准属性读写。 |
| 风模式 | `2 / 3` | 沿用直吹与自然风语义。 |
| 风速 | `8 / 1` | 沿用 1–100 的整数风速输入。 |
| 水平摇头 | `2 / 4` | 标准属性读写。 |

直连使用 `get_properties` 与 `set_properties`，逐项处理属性结果。非零调速必要时开机并切直吹、自然风下显示记忆直吹设定、独立开关与摇头的现有规则保持；不因换传输方式增加新风模式或功能。

### mcn02：旧 miIO 映射

mcn02 的实例为 `urn:miot-spec-v2:device:air-conditioner:0000A004:lumi-mcn02:1`，继续使用已经成立的 `air-conditioner:2` 功能及其标准属性绑定；标准空调品类的空调功能标记为核心功能。

直连通过 `get_prop` 一次读取电源、模式、目标温度、风速和上下摆风；控制使用下表中的旧命令。该映射只用于旧 miIO 直连，中枢或云端继续使用既有 MIoT 接口。

| 逻辑字段 | 既有 SIID / PIID | 旧控制命令 | 旧反馈字段与转换 |
| --- | --- | --- | --- |
| 电源 | `2 / 1` | `set_power` | `power` 的开／关字符串与布尔值互转。 |
| 模式 | `2 / 2` | `set_mode` | `mode` 在原生字符串与既有五种模式编码之间转换。 |
| 目标温度 | `2 / 3` | `set_tar_temp` | `tar_temp` 转为现有整度温度；旧命令传入整数。 |
| 风速 | `3 / 1` | `set_fan_level` | `fan_level` 转为自动／低／中／高。 |
| 上下摆风 | `3 / 2` | `set_ver_swing` | `ver_swing` 的开／关字符串与布尔值互转。 |

模式映射为 `auto → 0`、`cool → 1`、`dry → 2`、`heat → 3`、`wind → 4`；风速映射为 `auto_fan → 0`、`small_fan → 1`、`medium_fan → 2`、`large_fan → 3`。目标温度沿用本机描述中的 16–30℃、步长 1℃，不从其他型号复制范围。

映射按已确认的请求字段顺序解释反馈，在输入边界处理形状、类型和枚举错误。无效或未知反馈不默认解释为关机、自动模式或自动风。旧命令的成功应答只表示受理；对应设备错误照实返回，实际状态仍来自有效读取或通知。

复用通用空调计划与逐步结算：独立开关保留既有设置，单独调温不隐式开机，非零或自动风必要时先开机，不顺便切换温控模式。后续步骤失败时保留已经发生的步骤结果，不回滚或重放控制。

mcn02 不使用 mcn04 的整包 `ac-state`、`ac-ctrl-range` 或配码范围。其静态能力和约束来自自身描述及映射；来源拒绝操作时返回实际错误。本轮不扩展空调准入契约，不增加电功率功能。

### 功能与 Matter 基线

空调仍是一个逻辑功能，在同一子端点声明 Thermostat 与 Fan。环境温度绑定继续只用于显示；温控自动模式与自动风速是两个独立设置。

自动风沿用最新增强约定：开机且风速为 Auto 时，Matter 当前风速显示占位为 `SpeedCurrent = 1`、`PercentCurrent = 33`，设置值为空；原生实际挡位仍未知。关机、普通风与首次未知状态继续按现有规则表达。

## 统一选路

控制、读取和通知分别选择来源，不要求三者来自同一路径。

| 用途 | 正常优先级 | 候选条件 |
| --- | --- | --- |
| 控制 | 中枢 → 直连 → 云端 | 对应设备、功能与本次操作具有访问资格，路径可用且接口支持该操作。 |
| 读取 | 中枢 → 直连 → 云端 | 对应反馈可读，路径及属性绑定有效。 |
| 通知 | 可用中枢通知 → 可用云端通知 | 按现有设备声明、订阅结果及来源生命周期选择。 |

BLE 跳过直连候选，继续走现有中枢或云端。中枢的通知不可用不影响其读写候选；云端通知健康也不因 HTTP 暂停而被一起停用。

选中云端时，属性读取使用 `datasource=2` 请求设备当前值，不回退到可能滞后的 `datasource=1` 缓存。读取失败保留最近有效状态，首次尚无有效值时保持未知，继续接收有效通知并按既有调度恢复；控制回执及通知选路不变。单次属性读取的临时失败不暂停其他设备的云端控制，明确的账号撤权、设备离线与访问限制仍按既有规则处理。

中枢发生既有业务降级时，后续控制与读取先选可用直连，再选云端。二者均不可用时，用户控制沿用现有规则，可在中枢仍具备候选资格时尝试；自动读取不绕过中枢既有的慢恢复调度。中枢原有重连、业务探测与恢复条件保持，恢复后重新获得优先级。

直连故障按设备处理，一台设备的超时或凭据问题不使其他设备的直连失效。云端在线标记或中枢连接状态不替代直连自身的认证与业务可用性判断。

选路变化只影响尚未发送的操作和后续请求。已经发出或结果不确定的控制不跨路径补发；仍有效的在途控制按原请求结算，不能因更高优先级路径恢复就丢弃其合法回执。

## 通知与控制后刷新

直连读写成功不代表具有本地通知。本轮三个代表对象不预设直连订阅能力，通知使用现有中枢或云端；LAN 通知的能力信号与读写结果分别诊断，不据此实现未经代表设备确认的订阅方案。

保留启动、连接恢复与来源切换时的既有状态读取，另外对当前有读取路径的已接入状态安排周期读取，即使通知已就绪也适用。窗帘的状态、当前位置与目标位置每 10 秒读取；风扇的电源、模式与速度每 16 秒读取；其他可读状态，包括风扇其他属性、空调、测量、状态与电量，每 60 秒读取。周期是正常调度间隔，不是网络故障或拥塞时的完成时限。事件本身不可读取，不因静默推断通知失效。

每项周期读取按当前功能选择中枢 → 直连 → 云端，路径变化后依实际资格调度；虚拟组通过成员获得状态，不另建组周期任务。首次周期按设备错峰；同一属性已有排队或在途读取时跳过该次需求，不积压周期任务。mcn02 走旧 miIO 直连时五项反馈仍合并为一次 `get_prop`，周期为 60 秒，不保留另一套 30 秒任务。读取失败记录诊断，同一次周期不快速重试；路径及权限恢复后继续正常调度。

中枢每设备一轮最多读取一项，轮次错开并限制并发；直连保留每设备串行及全局并发上限。云端前台与周期读取分别合并同一设备同一功能的就绪属性，共用按属性结算和取消；每设备最多两个不同功能批次在途，全局最多八批，同一设备相邻起发间隔至少 200 毫秒。周期请求全局起发间隔至少 200 毫秒并保留后台独立退避，允许不同设备的周期请求在限制内并发；单项临时读取失败不暂停全部云端 HTTP 控制。明确的账号认证撤销、已识别的设备离线或权限错误，以及共享连接的生命周期仍按实际结果处理。普通基线及控制后反馈读取优先于未发出的周期读取，不取消已发送的周期请求。周期读取不能覆盖它开始之后收到的有效新通知；retained 缓存只可填充尚无新鲜值的属性，不能代替基线、使在途新鲜读取失效或覆盖已有新鲜状态。

对具备可读反馈的可控功能，在一次控制请求的全部命令步骤处理完毕后，如果至少一步明确受理，且该步经直连受理或当前没有可用通知来源，安排该功能的反馈刷新。完整成功和部分步骤受理后失败均适用；没有任何明确受理步骤时不触发。步骤处理完毕是全部步骤已收到回执，或某一步失败、超时后不再发送后续步骤；不代表窗帘等设备已完成物理动作。

反馈刷新复用既有队列和读取选路，不要求与控制使用同一路径。尚未发出的读取需求可以合并；读取已经在途时可在其结束后再安排一次读取，不为精确复用写入后的在途或已完成读取单独维护状态。旧读取不能覆盖较新的状态或替代写入后的刷新。读取失败沿用既有有界重试，最多额外尝试三次；无可用读取路径时等待路径恢复。读取诊断按功能及属性展示，不单独追踪每条命令的刷新结果。控制回执不等待刷新，刷新失败不改变命令结果，也不重放控制。已退休或失去访问资格的来源不再读取。

灯光和灯组继续使用已有写后相关属性、颜色模式、成员和渐变中间帧的回读及重试，不为本规则另加回读。其他路径判断通知可用性沿用功能实际活动来源和订阅状态；直连受理后即使订阅就绪也刷新，因为订阅成功不证明设备实际产生通知。

命令受理与状态表达沿用各功能既有语义；空调请求受理、伴侣报告与空调本体动作分别表达。控制后刷新和周期读取都只取得状态快照，不宣称实时推送；设备或上游返回旧快照时，读取也不保证纠正漏报。

窗帘等长动作的读取可能取得中途位置和运行状态，随后依通知及周期读取更新；不把受理或中途读取解释为动作完成，不推算运动时长或位置。缺少有效读取或通知时保留最近状态。

## 故障恢复与生命周期

现有中枢与云端均已有退避恢复。本轮直连的通信故障复用已有 `Backoff`，每台失效设备至多运行一个恢复任务，失败间隔依次为 1、2、4、8、16、30 秒并封顶；成功后重置。地址、凭据或网络条件变化可以唤醒重新验证，共享一次发现结果，避免同一轮为多个设备重复扫描。

恢复探测只在路径失效或需要重新建立时运行；健康闲置时不周期探测直连资格。新地址、重启后的会话或更新凭据必须完成身份确认及一次成功的只读业务请求，才能重新成为可用直连；hello 本身不作为恢复成功。

恢复用只读请求，不拿失败的控制当作探测。控制超时返回原请求的不确定结果，后续恢复不会自动执行它。路径恢复后按既有机制重新建立状态基线，并让后续请求按正常优先级选择。

直连复用既有请求结算、来源生命周期和观察顺序。已结束请求的迟到应答不再生效；仍有效的在途控制按原请求结算。新增部分只承担直连协议必要的请求关联和超时处理，不另建业务层代次、迟到消息缓存或隔离框架。

地址或 token 更新不等同于业务请求一律作废；沿用原请求持有的上下文与现有有效性规则完成结算。旧读取、已退休工作和失去资格的来源继续受现有生命周期约束，不能更新当前功能状态。

## 模块职责与诊断

| 单元 | 增量职责 |
| --- | --- |
| 新增 `xiaomi/lan` | UDP 通信、握手、报文编解码、请求关联和超时；向适配层提供明确的发送阶段与结果。 |
| `xiaomi/cloud` | 在现有目录接口边界提取直连地址与 token，提供有效的候选凭据。 |
| `storage`、`configuration`、`app` | 保存独立直连记录，关联现有家庭与设备资格，恢复缓存和执行已有撤销规则，保持发布身份。 |
| `xiaomi/capability` | 生成有效通用功能、功能补丁及型号适配策略，不承担 UDP 通信；协议映射消费已成立的绑定。 |
| `xiaomi/legacy_miio`、`xiaomi/adapter/legacy_miio` | 共用旧命令转换器；消费已识别的映射，将既有属性操作转换为旧请求，将响应转换回既有属性结果。 |
| `xiaomi/adapter` | 纳入直连候选、按设备管理就绪与恢复，复用命令结算、读取、通知选择及控制后刷新。 |
| `device`、`matter` | 沿用有效功能、操作计划与状态投影，保持端点与配对。 |
| `terminal` | 在现有状态入口中分别展示中枢、直连、云端和相关同步诊断。 |

诊断不能继续用含混的“local”同时表示中枢与设备直连。设备及功能状态应能说明：

- 控制、读取和通知当前各走哪条路径，其他候选为什么不可用。
- 直连使用 MIoT 属性接口还是哪条旧 miIO 映射，当前目标地址及身份确认情况。
- 凭据缺失或不可用、握手／业务超时、设备明确拒绝、映射失败及下一次恢复安排。
- 最近控制请求的实际发送路径、各步骤受理情况和结果是否不确定，以及功能的读取问题。

README 补充直连与旧 miIO 的能力范围；运行指南补充首次取得凭据、离线重启、路径检查、地址变化和凭据失效的操作与排障；已知限制说明支持的协议范围、通知差异、旧 miIO 周期读取及其同步边界，以及无通知时长动作的控制后刷新可能保留中途状态。

### 实际设备与 Home

每个适用场景在对应设备上执行一次；发现异常、结果不明确或修复后再重复，不固定要求多轮。地址变化、token 失效和迟到报文等边界主要由自动化覆盖，不要求为验收重置设备或重配家庭。

| 场景 | 对象与判据 |
| --- | --- |
| 风扇控制 | p5c 核对开关、调速、摇头及既有风模式行为，实际使用直连；同时核对中枢与直连切换。 |
| 空调控制 | 两台 mcn02 分别核对开关、五种模式、整度调温、自动／低／中／高风及摆风，覆盖直连与云端；设备拒绝须明确呈现，不能伪报受理。 |
| 通知 | 三台分别从米家侧改变可见状态，核对新报告、实际通知来源及 Home 更新，不把缓存读取当作新通知。 |
| 无通知反馈 | 隔离通知来源后经直连操作，核对本次控制请求的命令步骤处理完毕后的读取与 Home 更新；周期读取与控制后刷新分别观察。 |
| 重启 | 联网重启及已有凭据下的离线重启，重新取得状态；身份、端点、配对和既有温度绑定保持。 |
| 断连与恢复 | 直连断开、使用其他合格路径及直连恢复；中枢恢复后重新优先；没有原控制重放。 |

每台空调分别确认请求受理、伴侣报告，以及至少一次可观察的空调本体响应。并非每条模式或温度命令都要求立即看到压缩机动作，压缩机保护延迟和达到目标温度的时间不计入通信时限。p5c 同样区分回执、报告与实际运行。

正常条件下的观察时限如下：

| 场景 | 时限与起算点 |
| --- | --- |
| Home 状态投影 | MiGate 收到有效状态后 3 秒内更新保持打开的 Home 页面。 |
| 米家侧通知观察 | 从米家操作完成起观察 15 秒，区分真实通知与周期读取；无报告时记录实际情况，不以静默判失效。 |
| 无通知时直连控制后的反馈 | 从本次控制请求的命令步骤处理完毕起，15 秒内完成刷新并更新 Home；异常时仍按实际读取结果结算。 |
| 直连启动与恢复 | 从进程启动或通信条件恢复起，60 秒内重新可用并取得有效状态；离线启动使用事先保存的资格与凭据。 |
| 原有中枢／云端恢复 | 断连从通信条件恢复起、重启从 Matter 服务重新提供起观察，沿用既有恢复机制，上限 20 分钟。 |

上述时限是验收观察尺度，不引入额外通知超时推断。没有新通知的情况作为同步限制审阅，不能写成通知验证通过。

Home 中保留现有风扇和两个空调入口，空调保持同入口的温控与自动风能力，已有温度绑定仍只展示环境温度。实际直连控制、有效反馈、离线重启和身份保持均为本轮完成要求，不能用模拟路径或缓存状态代替。

## 与既有设计的关系及依据

本方案扩展[设备功能组合](../2026-10-29-device-capability-composition/spec.md)的来源执行方式；通用功能与功能补丁的既有职责保持。相对于[空调控制](../2026-10-30-air-conditioner-control/spec.md)，本轮新增原范围之外的 IP 直连与 mcn02 旧命令，并增加控制后反馈刷新；其余空调语义及[最新增强](../2026-11-01-air-conditioner-enhancements/spec.md)约定继续沿用。
