# 统一小米登录与米家设备云端访问

## 目标与范围

以 `b2a5084` 为代码基线，将 MiGate 的账号接入整理为一个账号、一次扫码登录、两套独立维护的服务凭据。设备云端 HTTP 统一使用米家会话；HA OAuth 用于云端 MQTT、中枢客户端证书及相关授权维护。

本文所称 HA OAuth，指小米账号对官方 `Xiaomi Home (Home Assistant Integration)` 应用的授权，由小米账号服务颁发，供该集成的云端接口使用。

用户通过同一个 `auth login` 入口完成首次登录或重新登录。每次执行都重新扫码取得账号恢复凭据与米家会话，并使用本次账号会话重新完成 HA OAuth 授权码交换，不复用已有服务凭据，也不以 refresh token 刷新代替重新授权。登录提示提前说明两套凭据的用途；用户执行登录并完成扫码，作为整套接入流程的确认，正常流程不要求第二次扫码、输入账号密码或再次人工确认 HA OAuth。已有凭据的免交互检查与维护由 `auth check` 和后台维护负责。

本轮包括账号与凭据模型、扫码及会话恢复、现有设备 HTTP 接口切换、MIoT Action 和旧 miIO 云端 RPC 通信接口、运行时恢复及诊断。服务区继续为 `cn`，每个数据目录只有一个账号。

额外安全验证采用用户自行处理后重新登录的方式，适用于无桌面的命令行环境。程序内部完整处理验证码、短信或身份验证作为后续增强，不纳入本轮。

旧 miIO RPC 在本轮提供内部通信接口，不因接口存在就为所有旧设备启用云端映射。具体型号的控制与反馈转换仍属于对应适配规则。本轮不新增设备功能或发布形状，也不提供任意 RPC 的用户调试命令。

## 方案选择

| 方案 | 取舍 |
| --- | --- |
| HA OAuth 继续承担标准设备 HTTP，米家会话补充旧 miIO RPC | 可以覆盖所需接口，但标准控制与旧协议反馈可能依赖两套不同的 HTTP 凭据，设备目录也继续依赖 HA 授权。 |
| 设备 HTTP 统一使用米家会话，HA OAuth 承担 MQTT 和中枢证书 | 采用。设备目录、标准 MIoT 与旧 miIO 使用同一设备会话，设备 HTTP 可以独立于 HA OAuth 的恢复过程工作。 |

米家会话支持标准 MIoT 属性、Action、设备目录和旧 miIO RPC；`hass-xiaomi-miot` 也使用米家会话进行设备 HTTP 访问，并实现会话复用、失效检测和重新登录。MiGate 采用扫码取得的 `passToken` 恢复账号会话，不引入保存密码的登录方式。[米家接口与认证实现](https://github.com/al-one/hass-xiaomi-miot/blob/master/custom_components/xiaomi_miot/core/xiaomi_cloud.py)

HA OAuth 的明确职责是现有云端 MQTT 和中枢证书链路。HTTP 后端的选择不以推测的性能、限流额度或长期稳定性为依据，也不要求设备写入与消息订阅使用同一种凭据。[官方云端接口](https://github.com/XiaoMi/ha_xiaomi_home/blob/main/custom_components/xiaomi_home/miot/miot_cloud.py) · [官方消息连接](https://github.com/XiaoMi/ha_xiaomi_home/blob/main/custom_components/xiaomi_home/miot/miot_mips.py)

## 账号、凭据与模块职责

账号身份不再由“包含 HA OAuth 和证书的完整记录是否存在”间接表示。新模型包含以下独立部分：

| 部分 | 保存内容与职责 |
| --- | --- |
| 账号身份 | 小米 UID 与服务区，是其他凭据和既有家庭资格的共同归属。 |
| 账号恢复凭据 | `passToken`、登录协议需要的账号标识、稳定的登录客户端标识及 User-Agent；用于免交互建立服务会话，不承担设备请求。 |
| 米家设备会话 | 同一会话的 `serviceToken` 与 `ssecurity`，以及需要的账号标识；承担设备 HTTP 请求。二者一并验证、保存和替换。 |
| HA OAuth 授权 | access token、refresh token、到期与刷新时间、HA OAuth 客户端 UUID 和回调地址；承担 HA 授权范围内的访问。 |
| 中枢客户端身份 | virtual DID、私钥和证书；同账号续期复用身份，证书有效性独立判断。 |

已保存但尚未验证的凭据不直接表示连接就绪。账号恢复凭据不可用，也不等于当前设备会话、HA OAuth 或证书已经失效。

模块沿现有 Xiaomi 来源组织：

- `xiaomi::auth` 负责账号登录、凭据获取与恢复、同账号校验及分项认证报告。登录交互由终端驱动，后台维护不发起新的交互式授权。
- `xiaomi::mijia` 负责米家会话、请求签名、HTTP 传输及设备目录、属性、Action 和 RPC 响应解析。`xiaomi::cloud` 保留 HA OAuth、证书接口与云端 MQTT，原始 MIoT 描述加载单独组织。客户端不互相接管失败的业务请求。
- `xiaomi::adapter` 继续拥有家庭与设备资格、选路、读取调度、通知、命令结算和状态提交。HTTP 控制与目录同步消费米家会话，云端通知消费 HA OAuth，局部失败只更新对应能力。
- `storage` 保存账号和各组凭据，支持重新登录时整套凭据的事务替换，以及运行期各项凭据的独立原子更新。凭据不进入设备描述或 Matter 配置记录。

已登录记录必须包含完整的账号恢复凭据、米家会话和 HA OAuth 授权，缺少任一核心凭据视为存储损坏。各服务的失效、停止恢复及临时失败仍独立判断；中枢身份和证书允许尚未就绪。重新登录的候选凭据在完整验证后统一保存，取消登录或此前任一步骤失败不覆盖现有记录。

## 登录与命令行为

保留 `migate [--data-dir <PATH>] auth <login|check|logout>` 命令结构。认证命令继续使用数据目录锁；与使用同一目录的网桥互斥。

### `auth login`

1. 说明本命令会重新获取米家会话与 HA OAuth 授权，分别用于设备 HTTP、云端 MQTT 和中枢证书。读取现有账号归属与客户端身份用于一致性校验，但不因已有凭据可用而提前成功退出。
2. 在终端展示新的米家扫码登录二维码和有效期，等待用户扫码确认。不使用已保存的 `passToken` 跳过本次扫码，不要求输入或保存账号密码。
3. 从扫码结果取得账号恢复凭据，完成 STS 服务票据交换，并以无设备控制副作用的米家请求验证候选会话。现有目录已有账号时，返回 UID 必须一致；不一致则拒绝本次候选，保留当前账号。主动更换账号使用 `auth logout` 后重新登录。
4. 使用本次扫码建立的账号会话，完成 HA OAuth 协议要求的授权提交，取得新的授权码并交换 access token、refresh token 和有效期信息，再验证身份关联与访问能力。即使已有 HA OAuth 仍有效也完整执行此步骤，不使用旧令牌或刷新结果充当本次登录结果，不增加第二个人工确认步骤。
5. 账号恢复凭据、米家会话和 HA OAuth 全部验证成功后，在同一事务中替换；首次登录同时保存账号身份。此前任一步骤失败或取消均不保存部分候选，保存失败保留原记录。本次“重新获取”以完成新的登录与授权流程为准，不要求小米返回的每个凭据字段都与旧值不同。
6. 准备或续期中枢证书。同账号的 HA OAuth 客户端标识、既有 virtual DID、私钥及仍可用的证书继续复用；获取新的服务凭据不重建客户端身份。首次创建中枢身份时先保存 virtual DID 和私钥，再获取证书。证书步骤失败不回滚已经提交的两套凭据，可用 `auth check` 重试证书维护。
7. 输出分项结果。本次两套凭据重新获取并保存成功、所需证书维护成功，且米家设备访问、HA OAuth 与中枢证书全部就绪时返回成功；否则返回非零状态，并说明失败步骤及当前状态。再次执行 `auth login` 总是重新完成整套登录，不从上次候选进度继续。

新取得的 HA OAuth 授权先核对服务端授权上下文中的 UID，再沿用 HA 的家庭查询验证令牌对应的账号 UID；二者都必须与本次扫码 UID 及已有账号归属一致。无法确定身份或身份不一致时不保存该候选，不把“两个接口都能返回设备”当作同账号证明。这项 HA 查询仅用于认证，不成为另一套运行时设备目录来源。

HA OAuth 使用现有应用标识 `2882303761520251711`、`ha.<uuid>` 客户端标识及既有 `state` 计算规则；同账号保留客户端 UUID，每次授权生成新的随机回调路径。授权和令牌交换的客户端标识、回调地址必须一致。流程截获并验证最终回调，不实际访问 `homeassistant.local`；正常扫码流程不再要求用户手动粘贴这个回调网址。[HA OAuth 实现参考](https://github.com/XiaoMi/ha_xiaomi_home/blob/main/custom_components/xiaomi_home/miot/miot_cloud.py) · [扫码流程参考](https://github.com/PiotrMachowski/Xiaomi-cloud-tokens-extractor/blob/master/token_extractor.py)

扫码轮询受本次二维码的服务端有效期和请求超时约束。二维码过期或用户取消时结束当前尝试，不在后台无限生成二维码或循环尝试登录。本次未提交的候选凭据、授权码、临时 Cookie 和跳转信息随尝试结束而丢弃，不保存跨命令的登录进度。

登录流程只向相应官方账号与 STS 域名发送其所需凭据；设备 API 和 HA API 不自动跟随重定向。任何登录票据、令牌、签名密钥、私钥及含票据的跳转网址都不进入日志或常规状态输出。

### 额外安全验证

米家登录或 HA OAuth 获取过程中，服务端明确要求额外的图形验证码、短信、邮箱或身份验证时，结束本次登录并返回非零状态，说明受阻阶段，丢弃未提交的候选并保留原凭据记录。

提示用户在手机或电脑浏览器中自行登录[小米官网](https://www.mi.com/)，完成小米要求的安全验证，再重新执行 `auth login`。参考上游排障建议，优先使用与网桥处于同一网络的设备；网桥所在机器无需桌面或浏览器。新的 `auth login` 重新扫码获取两套凭据，不导入外部浏览器 Cookie，也不接续已经结束的验证会话。[上游登录失败提示](https://github.com/al-one/hass-xiaomi-miot/blob/master/custom_components/xiaomi_miot/translations/zh-Hans.json#L166)

自行登录官网属于排障办法，不保证消除下一次验证要求；再次受阻时如实报告，不自动循环登录。`auth check` 和后台维护遇到同类要求时，停止对应凭据的自动恢复并给出相同的人工处理提示，其他能力按各自实际状态继续工作。本轮不增加验证码输入界面、验证网页或浏览器会话接续机制。

### `auth check` 与 `auth logout`

`auth check` 分别检查米家设备会话、HA OAuth 和证书，执行必要的免交互恢复、令牌刷新及证书续期，不展示二维码、不创建新的 HA OAuth 授权。各项全部就绪且本次所需维护步骤成功时返回成功；某项失败时仍显示其他项的实际状态，不统一标记为整个账号已退出。

`auth logout` 删除本地账号、账号恢复凭据、米家会话、HA OAuth、客户端私钥和证书，以及已保存的设备直连凭据。保留 Matter 身份与 Home 配对；沿用现有资格清理规则，不因缓存而恢复已退出账号的访问。该命令不承诺撤销小米服务端的其他客户端会话或 HA 应用授权。

## 设备 HTTP 接口

运行时设备 HTTP 使用 `https://api.io.mi.com`。保留现有家庭范围和目录语义，不通过改换目录接口扩大准入范围。

| 用途 | 米家路径 |
| --- | --- |
| 自有家庭及首批成员 | `/app/v2/homeroom/gethome` |
| 后续家庭、房间成员分页 | `/app/v2/homeroom/get_dev_room_page` |
| 设备详情、在线信息、直连凭据及灯组关系 | `/app/v2/home/device_list_page` |
| MIoT 属性读取 | `/app/miotspec/prop/get` |
| MIoT 属性写入 | `/app/miotspec/prop/set` |
| MIoT Action | `/app/miotspec/action` |
| 旧 miIO RPC | `/app/home/rpc/<did>` |

MIoT 原始描述仍使用现有描述服务；不会随设备 HTTP 切换为另一套描述或能力来源。HA 的令牌交换、刷新及 `/app/v2/ha/oauth/get_central_crt` 保留在 HA 客户端中。

目录与属性读取沿用单次 30 秒 HTTP 超时，属性写入与 Action 沿用 15 秒；RPC 单次请求上限为 30 秒。客户端不在这些业务尝试中嵌套登录、重发或其他后端请求。

### 请求认证

设备请求携带对应会话的 `userId`、`serviceToken` Cookie、稳定 User-Agent 和协议请求头，使用表单编码的 `data`、`_nonce`、`signature`。本轮采用已选定的签名请求形式，不额外增加 RC4 或不同签名形式之间的自动切换。

`data` 是实际发送的 JSON 字符串。nonce 由 8 字节随机数与 4 字节大端 Unix 分钟数组成；将解码后的 `ssecurity` 与 nonce 拼接后计算 SHA-256，得到 signed nonce。以 signed nonce 的二进制值为 HMAC-SHA256 密钥，对签名路径、Base64 signed nonce、Base64 nonce 和 `data=<JSON>` 依次用 `&` 连接后的字符串签名，结果以 Base64 编码。签名路径去除 URL 的 `/app` 前缀；签名与发送必须使用同一份数据，最终只进行一次表单编码。[签名请求参考](https://github.com/ha0y/xiaomi_miot_raw/blob/master/custom_components/xiaomi_miot_raw/deps/xiaomi_cloud_new.py)

账号恢复凭据只用于账号服务，不加入设备请求。HTTP 客户端不持有账号密码，也不在业务请求内部自行登录或切换认证方式。

### 目录、属性与 Action

家庭成员、账号设备目录及灯组关系继续分别解释。完整分页成功后才提交新的权威目录；请求、分页或解析失败保留此前已确认的配置，不能把半份目录或空响应当作设备移除。设备目录返回更多设备也不会自动改变当前家庭资格。

保留现有设备在线信息、LAN 候选凭据和灯组成员解析；目录中的设备 token 仍须通过既有直连验证后才能成为有效直连凭据。

属性读取显式使用 `datasource: 2`，保持向设备请求当前值的语义。读取失败不改为缓存读取，不以命令目标值代替反馈。逐属性关联 DID、SIID 和 PIID，保留可用的来源时间及逐项错误；一次部分失败不丢弃同批的有效反馈。

写入及 Action 的受理结果与实际设备状态分开。Action 使用 DID、SIID、AIID 和按原生输入定义排列的参数；不因为补齐传输接口就自动发布描述中的所有 Action。参数与结果转换属于相应功能适配规则。

### 旧 miIO RPC

RPC 客户端接受确定的设备 DID、方法和参数，构造包含 `id`、`method`、`params` 的请求数据，解析外层认证、业务错误及内层 RPC 结果。它不解释风速、模式或温度，也不把任意返回值统一当作控制成功。

旧命令转换与传输解耦：功能适配规则负责旧字段与内部语义之间的转换，并声明实际可用的传输；LAN 与云端客户端负责各自通信。不能仅因某型号已有 LAN 旧命令映射，就自动为其增加云端 RPC 路径。

传输层不自动重试 RPC。明确的读取由现有读取调度决定是否再次请求；不能根据方法名称前缀推断某次调用可以安全重放。控制的受理、拒绝和不确定结果进入已有命令结算流程。

## 凭据恢复与错误处理

### 米家会话

启动和显式检查优先使用已保存会话，通过实际认证检查或设备请求确认可用性。不猜测 `serviceToken` 的固定有效期，不为延长会话新增周期性登录或保活轮询。

遇到明确的会话过期或账号认证拒绝时，暂停该会话对应的设备 HTTP 使用，合并并发恢复请求，使用已保存的 `passToken` 重新执行 `xiaomiio` 服务登录和 STS 交换。新的 UID 必须一致，新的 `serviceToken` 与 `ssecurity` 验证并保存成功后才能整体替换当前会话。

每次恢复只进行一轮账号会话重建。网络、服务临时错误按现有退避机制安排下一次维护；账号凭据被明确拒绝或要求用户验证时，停止自动登录尝试，提示运行 `auth login`。临时维护失败不清除仍可用的旧会话，新候选验证或保存失败也不覆盖旧记录。

认证恢复与业务请求分开结算。原请求返回实际结果；恢复成功后，读取可重新进入既有读取队列，控制不会因恢复成功而自动重发。并发失败不会各自触发一轮重新登录。

### HA OAuth 与证书

HA OAuth 保留现有到期判断及 refresh token 刷新机制，不依赖米家目录同步是否成功。刷新被拒绝时暂停依赖该授权的能力并显示需要重新授权；后台不以 `passToken` 静默建立新的 HA OAuth 授权。用户显式执行 `auth login` 时重新扫码获取两套凭据，HA OAuth 使用本次账号会话完成新的授权码交换，不再要求额外人工确认。

证书续期依赖可用 HA OAuth，已有证书仍按自身有效期和真实连接结果使用。HA OAuth 刷新失败不提前作废仍有效的中枢证书；米家 HTTP 故障也不阻止可正常执行的 HA OAuth 刷新或证书续期。

### 停止自动恢复

检查或后台维护使用已保存凭据时，若账号恢复凭据被明确拒绝或要求额外安全验证，或 HA OAuth 明确需要重新授权，则持久化对应凭据的停止恢复状态。该状态跨命令和进程重启保留；`auth check` 继续报告该项需要重新登录，不再尝试已停止的账号恢复或 HA OAuth 刷新。网络、服务临时错误不产生该状态，其他独立凭据仍按各自实际状态检查与使用。

只有同账号 `auth login` 成功提交替换凭据时，才在同一事务中清除对应旧停止状态；失败或取消的重新登录不解除。停止状态归属各自凭据，不使用全账号的统一禁用标记。

### 失败分类与运行影响

| 情况 | 处理 |
| --- | --- |
| 明确的米家会话认证拒绝 | 恢复米家会话；不将其解释为 HA OAuth 或证书失效。 |
| 账号服务明确要求额外安全验证 | 登录命令结束本次尝试；检查和后台维护停止对应凭据的自动恢复，提示用户自行登录小米官网完成验证后重新执行 `auth login`。 |
| HA OAuth 被拒绝或过期且无法刷新 | 暂停云端 MQTT，并限制需要 HA OAuth 的证书操作；米家设备 HTTP 独立继续。 |
| 中枢证书失效 | 对应中枢访问不可用；已合格的其他路径仍可使用。 |
| 超时、连接失败、限流或服务临时错误 | 保留凭据及最近有效状态，按对应请求和维护调度退避，不直接要求重新登录。 |
| 签名错误或响应结构错误 | 给出协议诊断；不一概归为账号退出，也不循环重新登录。 |
| 设备离线、设备权限拒绝、属性或 Action 拒绝 | 保留具体错误及其作用范围，沿用相应设备和功能的可用性规则。 |
| 设备移除、家庭变化或明确撤权 | 执行现有资格与来源生命周期处理，不能因另一套凭据有效而保留已撤销访问。 |

请求发送前及结果提交时继续检查当前账号、家庭资格、凭据和来源生命周期。账号一致性不替代家庭授权，缓存的家庭身份也不覆盖后续明确的移除或撤权结果。

## 选路、状态与读取频率

现有中枢、直连、云端优先级继续适用；其中云端设备 HTTP 只对应米家后端，不保留 HA OAuth 设备 HTTP 的选择开关或自动回退。

首次家庭绑定仍使用既有中枢发现与家庭确认规则。已确认账号和家庭可用于恢复已有配置，恢复不再以 HA OAuth 当前可用为统一前置条件。没有账号身份时提示登录；核心凭据完整但部分服务不可用或证书未就绪时，启动后按各能力的真实资格工作，不为单项凭据维护失败退出整个网桥。

通知来源独立使用中枢或 HA 云端 MQTT。HTTP 读写成功不表示通知就绪；MQTT 中断时，已有读取继续工作。控制受理不直接更新为目标状态，后续读取及通知仍提供实际反馈。

沿用现有目录同步、功能轮询、写后刷新、冷启动采集和退避调度。不会因为迁移 HTTP 后端而复制读取队列、同时请求两个云端接口或增加轮询频率；也不为未经确认的配额限制提前降低正常频率。

`auth check`、启动状态与运行时 `status` 分别显示：

- 小米账号身份与服务区。
- `Mijia session` 的检查、可用、恢复中、暂不可用或需要扫码状态。
- `HA OAuth` 的检查、可用、刷新中、暂不可用或需要授权状态。
- 中枢证书有效期与续期结果。

设备路径仍可显示 `cloud`，并标明 HTTP 后端为 `mijia`；消息订阅状态单独显示。错误提示说明受影响的能力及下一步，不再用一个笼统的“账号失效”覆盖所有服务状态。

## 持久化

账号身份、账号恢复凭据、米家会话、HA OAuth 和中枢身份分别保存，只支持当前 schema。

每次凭据更新先验证候选，再以事务保存，成功后替换运行上下文。`auth login` 将本次账号恢复凭据、米家会话和 HA OAuth 一并提交；运行期的米家会话恢复、HA OAuth 刷新及证书维护仍分别提交，不因重新登录的提交边界而相互依赖。数据库错误沿用现有存储失败处理，不将未保存的新凭据当作已提交状态。

凭据沿用私有数据目录和数据库的保护。调试输出对恢复凭据、服务票据、签名密钥、HA OAuth 令牌、私钥及临时授权参数脱敏；原始设备描述、功能配置和 spec 均不携带这些值。

## 验证要求

| 主题 | 需要证明的行为 |
| --- | --- |
| 扫码与 HA OAuth 衔接 | 登录前说明两套凭据及其用途；每次 `auth login` 均重新扫码获取米家会话并完成新的 HA OAuth 授权码交换，包括已有两套有效凭据时；正常流程无需第二次扫码、密码或 HA OAuth 人工确认；授权提交、回调关联和同账号校验正确。 |
| 额外安全验证 | 明确的验证要求结束本次登录并保留原记录，输出官方账号登录入口及人工处理后重新登录的提示；再次执行完整获取两套凭据，不接续候选或自动循环尝试；检查和后台维护仅停止受影响凭据的恢复，无需图形环境。 |
| 登录替换与持久化 | 两套候选及账号恢复凭据全部验证后一次提交；取消、过期、错误账号、HA OAuth 失败或保存失败不覆盖原记录，不发布部分候选，也不在下次登录复用候选进度；证书维护失败保留已提交的新凭据与既有客户端身份，可通过 `auth check` 重试。 |
| 米家签名与接口边界 | 固定时钟和 nonce 下符合协议签名向量，签名内容与发送内容一致；覆盖 JSON 数据、路径和表单编码，以及认证与业务错误分类。 |
| 会话恢复 | 并发认证失败只触发一轮恢复；候选会话成对替换；网络失败退避，明确拒绝转交用户；停止恢复状态跨 `auth check` 和进程重启保留，只有成功提交重新登录凭据后解除；控制不因恢复而重放。 |
| 服务独立性 | HA OAuth、米家会话或证书各自失效时，仅对应能力受限；已合格的其他连接和读取按原规则继续。 |
| 目录与状态语义 | 完整分页、家庭范围、灯组成员、直连凭据和设备移除处理保持；实时读取失败不改用缓存；逐项拒绝与有效反馈正确关联。 |
| Action 与 RPC | 编码、结果和错误完整传递，转换归属明确，不自动扩大型号支持，不隐式重试控制。 |
| 既有行为 | 已有功能选路、通知、写后刷新、命令受理语义，以及身份、端点、名称和配对恢复不受破坏。 |

复用现有可控 HTTP 对端、时钟与运行组装入口验证这些边界；认证恢复用模拟的过期、拒绝和验证响应覆盖，不依赖等待真实凭据自然到期。真实接口核对聚焦账号归属、目录完整性和代表设备的实际读写语义，不从短期可用推导固定会话寿命或不限流承诺。
