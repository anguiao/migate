# 浴霸接入与状态同步

## 目标与范围

以 `main` 的 `e4ce0d9` 为代码基线，以公卫浴霸为代表，将照明、暖风、吹风和换气组合为一个 Apple Home 设备入口。控制、外部操作后的状态更新和通信恢复均以设备反馈为依据，保持已有设备身份、照明端点和配对。

本轮增加仅制热模型、v13 操作映射、共享反馈解码和关联刷新，接入已有通信能力。米家云端与 IP 局域网直连均须覆盖本轮浴霸功能的控制和反馈；有资格的中枢标准属性路径继续参与既有选路。

运行与验证范围为当前 macOS / Apple Silicon 环境，继续使用现有 Rust 单包。浴霸的干燥／除雾／极速加热预设、摆风、定时、遥控器配置、硬件告警和电功率测量不作为新增 Home 功能。

## 功能与 Home 表达

| 功能 | Home 控制和状态 | 边界 |
| --- | --- | --- |
| 照明 | 沿用已有开关和亮度能力 | 保留 `light:2` 及现有灯光行为。 |
| 暖风 | 关闭／制热，目标温度 25–45°C、步长 1°C，内置当前温度 | 不提供制冷、自动冷热切换或送风／除湿温控模式。 |
| 吹风 | 开关、低挡 50%、高挡 100% | 关闭为 0%；百分比表达两档设定，不表示连续调速或转速测量。 |
| 换气 | 开关、低挡 50%、高挡 100% | 与吹风独立控制和反馈，关闭为 0%。 |

吹风和换气的低挡／高挡对应 Home 中的 50%／100%。暖风功率由用户在米家设置，改档可能同时开启暖风。Home 根据设备反馈更新暖风状态。

暖风与吹风互斥，换气可以与其中任一功能共同开启。功能分别建模不表示它们拥有独立电机；共用执行部件和联动由设备自身处理。MiGate 不提前推算另一个功能已经关闭，也不为维持本地目标反向覆盖米家或面板操作。

暖风开关表示设备独立暖风功能的启用状态，不表示 PTC 加热元件正在通电。MiGate 不根据目标温度与当前温度的差值推断实际加热，也不在本地运行恒温控制循环。

高级预设不映射为额外 Home 模式，Home 的暖风开关也不是整机所有热风预设的总开关。米家运行预设时，保留原生模式诊断，已经接入的独立功能仍依据各自真实属性反馈；不从预设名称、风机转动或温度变化推导独立功能开启。

### 本轮增量

从现有空调实现提取统一温控核心，用有效能力档案表达空调与仅制热设备。

| 层次 | 本轮变化 |
| --- | --- |
| 温控核心与能力档案 | 共享电源、模式、目标温度网格、当前温度观测、结算和 Thermostat 投影；保留完整空调档案，增加要求有效暖风开关与可读写目标温度的仅制热档案，只提供 Off / Heat。 |
| Xiaomi 暖风识别 | 增加标准 PTC 暖风的能力契约，按服务、属性语义、访问权限和数值约束识别，纳入已有功能组合流程。 |
| v13 内置补丁 | 声明两路风扇、低挡操作在各路径上的编码、旧接口反馈字段、共享解码及受影响功能集合；型号差异集中在这里。 |
| Xiaomi 适配计划 | 将 Action、内置旧命令和跨功能共享读组接入现有执行与读取流程，按具体操作或反馈输入声明所用接口。 |

照明和两路风扇复用现有灯光、风扇模型。空调的风速与摆风仍属于原有空调功能，浴霸两路风扇独立建模。温控整理须保留既有空调契约、身份、外部温度绑定、自动风表达及 mcn02 / mcn04 特有规则。

仅制热档案接入浴霸内置当前温度作为自身只读来源，复用现有数值观测与温度有效性语义；不增加浴霸外部传感器选择或自动切换温度来源的策略。

### 来源绑定与执行边界

来源计划显式区分 MIoT 属性、MIoT Action、内置旧命令和旧接口反馈字段，并声明同一逻辑操作在不同路径上的原生编码。动作不伪装成可读写属性，旧接口字段不分配虚构 SIID / PIID，也不添加不存在的 MIoT 通知订阅。

扩展适配层现有属性操作计划，承载 Action、内置旧命令及反馈读组的绑定、参数和结果转换，调用已有通信客户端。计划由内置规则产生，沿用设备写入门控、请求结算与来源生命周期。直连在业务报文发送前失效时，可重新选择其他可用路径。已发送或结果不确定的控制只安排只读核对。

将现有直连适配中“一份旧映射对应一个功能”的限制扩展为按操作和反馈输入声明接口，使同一浴霸的标准属性与旧接口并用，并允许同一原始读组服务多个功能。mcn02 与 p5c 的接口范围保持。

云端与直连共用 v13 的编码、解码和联动规则；转换后的逻辑状态进入通用模型，`device` 和 `matter` 不按型号或旧字段分支。

## v13 控制与反馈映射

### 控制与标准状态

| 逻辑操作 / 状态 | 原生来源 |
| --- | --- |
| 照明开关、模式、亮度 | 既有 `2.1`、`2.2`、`2.3` 绑定 |
| 原生工作模式诊断 | `3.1 mode`，读取和订阅真实枚举反馈，仅用于诊断及关联刷新，不向 Home 提供该属性的模式控制 |
| 暖风开关 | `3.3 heating`，读写布尔值 |
| 暖风目标温度 | `3.8 target-temperature`，读写 25–45 的整数 |
| 米家暖风功率变化 | 订阅可通知的原生属性 `3.5 heat-level`，收到有效通知后回读 `3.3 heating`。 |
| 吹风开关状态 | `3.2 blow` |
| 吹风低挡 | 云端调用 `4.4 blow-low` Action，无输入参数；直连调用 `set_bh_mode ["coolwind", 1]` |
| 吹风高挡 / 从关闭单独开机 | 写入 `3.2 = true` |
| 吹风关闭 | 写入 `3.2 = false` |
| 换气开关状态 | `3.4 ventilation` |
| 换气低挡 | 云端调用 `4.5 ventilation-low` Action，无输入参数；直连调用 `set_bh_mode ["venting", 1]` |
| 换气高挡 / 从关闭单独开机 | 写入 `3.4 = true` |
| 换气关闭 | 写入 `3.4 = false` |

两路风扇的低挡只发送当前选定路径的对应动作或旧命令，不先开高挡再降挡，也不将两种编码依次发送。风道和实际识别出的云端 Action 随能力配置保存，直连命令及参数由 v13 内置补丁按风道确定。已有配置可继续读取，旧命令字段不参与执行。

普通开机（`On`）只要求风道开启。已运行时保留当前挡位，关闭后单独开机使用原生高挡。低挡从关闭启动时，跟随的 `On` 复用该操作的受理、拒绝、取消或超时结果。运行中调挡失败，或关闭被明确拒绝，均保留原有开机反馈。暖风可能关闭吹风、或关机请求已发送但结果不确定时，根据新的风道开关反馈处理普通开机。再次读到关闭，或显式关闭已受理，下一次独立开机使用高挡。明确选择 100% 始终执行高挡写入。Home 的开关和挡位由真实反馈更新。

沿用已有两档风速换算：0 关闭，1–50 选择低挡，51–100 选择高挡；确认后的显示归一为 0%、50% 或 100%。

暖风开启只发送原生暖风开启请求，沿用设备当前功率设定。调整目标温度只写入目标值。Home 关闭某一功能只使用该功能的独立控制，不调用 `stop-working` 或 `stop-all`。

暖风目标温度在命令入队前按该功能的固定温度网格校验。无效设定立即返回约束错误，之前已排队的有效调温命令继续执行。

### 旧接口反馈

使用一次 `get_prop` 读取 `bh_mode`、`fan_speed_idx`、`temperature`。同一个读组可以由直连或云端 RPC 执行，请求字段及解码规则相同；一次需求选择一条合格路径，不同时从两路获取后任意覆盖。该读组由物理设备拥有，供相关功能共同消费，不为两路风扇分别重复请求同一字段。

| 字段 | 用途与解释 |
| --- | --- |
| `fan_speed_idx` | 十位表示吹风挡位，个位表示换气挡位；对应数字 1 为低挡、3 为高挡。其余数位不参与风速解码。 |
| `temperature` | 浴霸自身报告、可与机身温度显示对照的当前摄氏温度，作为暖风的当前温度来源。 |
| `bh_mode` | 原生工作模式诊断；不按未确认的字符串或预设编码推导独立功能状态。 |

标准属性 `3.1 mode` 与旧字段 `bh_mode` 分别保留原始值、来源和观测时间。遇到设备实例枚举表未声明的 `3.1` 值，诊断同时保留未知原因。`3.1` 和 `3.5` 的关联读取只由各自枚举表中的值触发。`bh_mode` 通过共享读组取得，暖风、吹风和换气开关分别取自各自的真实属性。

`fan_speed_idx` 按数值位解码，允许前导零未出现在整数表示中，例如 `3` 的吹风位为 0、换气位为 3。设备关闭时仍可能保留挡位，也可能在某些位报告 0；不能直接把整个字段当作一个风速。

两路风扇各自按下表投影：

| 开关反馈 | 对应挡位反馈 | 对外状态 |
| --- | --- | --- |
| 已确认关闭 | 任意记忆值或未取得挡位 | 当前风速为 0。 |
| 已确认开启 | 1 / 3 | 当前设定挡位为低 / 高，百分比为 50 / 100。 |
| 已确认开启 | 0 或未识别的挡位编码 | 挡位未知，保留原始输入及原因，不填低挡或上次命令目标。 |
| 开关未知 | 任意挡位 | 不从记忆挡位推断已经开机。 |

RPC 响应整体形状、字段数量和对应关系在边界校验。结构完整但单个字段无效时，只影响依赖该字段的观测；一个风扇位无效不抹掉另一个有效位，模式字符串未知也不使有效温度失效。明确报告的未知值使相应观测变为未知；通信或读取失败则保留最近有效观测并记录失败，二者分开处理。

当前温度与目标温度分别保存，内置温度按既有温度来源语义处理有效性：有效时投影，未知时返回空值；单次失败保留有效读数，所有获取路径失效后旧读数仅供诊断，恢复后等待新读数。直连与云端读取的是同一个逻辑温度来源，温度不可用不禁用暖风控制。传感器具体安装位置、精度及其与独立温湿度计的偏差不作保证，不复制其他型号的测量量程。

## 浴霸通信适配与状态同步

### 混合接口接入

将 v13 纳入现有直连适配策略，使用来源计划中的有效布尔开关属性完成既有只读业务确认。建立连接后，标准属性与旧读组分别获取基线并记录结果；挡位或温度缺失、单字段异常及单接口业务拒绝只影响相应观测或操作，连接与访问资格失效仍按共用规则处理。

### 按操作和反馈来源选路

| 浴霸请求类别 | 使用的已有通信路径 |
| --- | --- |
| 标准属性控制、标准属性实时读取 | 正常优先级为合格中枢 → 直连 → 米家云端 HTTP；保留既有中枢降级规则。 |
| 吹风、换气低挡操作 | 合格直连旧命令 → 米家云端 Action；中枢不参与该操作的候选。 |
| 旧接口反馈读组 | 合格直连 `get_prop` → 米家云端 RPC；中枢不参与该读组的候选。 |
| 标准属性通知 | 现有中枢或云端 MQTT，独立判断通知资格及就绪状态。 |

为现有选路提供具体操作和反馈输入的接口资格。标准属性可用中枢时，旧读组仍需独立选择直连或云端；同一功能的低挡与高挡也可以使用不同路径。

两路挡位和内置温度依靠旧读组回读，标准属性通知不能充当这些字段的反馈。将共享读组接入现有读取来源与有效性检查，切换路径后重新取得基线，旧路径迟到结果按既有生命周期和观测顺序丢弃。

### 周期读取与关联刷新

本机接入的照明开关／亮度及其必要模式输入、暖风开关／目标温度、吹风与换气开关、原生工作模式 `3.1`，以及旧接口反馈读组，正常周期统一约 16 秒，以满足外部变化 30 秒内更新的目标。其他设备维持原周期。已有排队或在途的相同读取合并需求，不重复建立浴霸专用轮询循环。

已发布的风道或暖风依赖共享读组时，启动等待包含该设备的首次共享读取。成功取得结果或确认读取失败均可结算，沿用现有启动时限。照明通知按其自身属性和设备声明的刷新触发器判断就绪。v13 补丁声明以下关联读取，通知仍直接更新其真实属性：

- 暖风或吹风控制涉及互斥状态，完成后刷新暖风、吹风、换气和原生工作模式的相关标准属性及共享读组。
- 换气控制后同样刷新这组状态，确认设备实际联动；不把其他功能保持不变当作预先结论。
- 收到当前来源关于暖风、吹风、换气及原生工作模式 `3.1` 的有效新通知时，触发合并后的关联读取；通知值相同也可能伴随换挡，不仅按布尔值是否变化判断。未产生通知的变化由周期读取发现。
- 收到当前来源的暖风功率变化通知时，回读暖风开关。调温刷新目标温度与当前温度来源；照明沿用既有控制后刷新。

本型号将控制后刷新扩展为：命令步骤完成且至少一步明确受理后，无论通知是否就绪均安排上述关联读取；已发送但结果不确定的控制也安排只读核对，原命令仍按不确定结算。完全未发送或明确拒绝且没有已受理步骤的命令不触发写后核对。

共享读组一次返回的两路挡位从同一个原始值解码、按同一读组观测提交。标准属性和 RPC 不是设备级原子快照，不宣称它们采样同时发生；原始来源、接收时间及未知原因保留。相关新通知或写入使过早的在途读取失效，但不清空已经确认的挡位；等待回读时保留最近有效挡位及其观测时间，并在诊断中标明待刷新，不以通知时间或命令时间刷新旧挡位的时间戳。首次有效反馈前仍为未知，明确收到无效挡位编码时才将相应挡位置为未知；过早的读组结果不能覆盖后续观测，也不能恢复已经被明确无效反馈置为未知的挡位。

以上读取需求使用现有队列、优先级和有界重试。当前温度的 30 秒更新目标从设备已经提供新读数起算。

## Matter 发布与身份

按已有身份分配规则保留物理父端点和原照明子端点，仅为新增功能分配端点。暖风使用 `heater:3`，吹风使用 `fan:3:2`，换气使用 `fan:3:4`。

仅制热档案只声明 Heating 能力及相应设定属性，支持 Off / Heat；不公布冷设定、Auto Mode、自动冷热区间或未取得真实反馈的运行加热状态。

吹风与换气各用独立子端点，复用 Fan Control，`SpeedMax = 2`，只提供关闭、低挡和高挡，不提供自动风、自然风或未接入的摆风。

父子组成关系、功能命名和协议描述须使 Home 呈现一个“公卫浴霸”入口，其中可分别操作照明、暖风、吹风和换气。内置温度在暖风中展示。

一个 Home 聚合入口是交付条件，协议可读或父子 PartsList 正确不能替代此项。若 Home 不能按该结构同时容纳两路独立风扇，应返回讨论发布方案；不以独立卡片替代、不拆成多个虚假物理设备，也不通过删除现有配对掩盖身份变化。

## 浴霸诊断与终端入口

在现有 `status DID` 的状态、路径、命令及同步诊断中补充：

- 暖风、吹风、换气各自开关、目标／当前温度、两路风速挡位，以及分别保留的 `3.1 mode`、`bh_mode` 和共享原始挡位字段。
- 标准属性与旧读组各自的来源和结果，以及同一功能的低挡与其他操作使用不同路径的情况。
- v13 补丁与原始字段解码问题；两路风速和内置温度的未知原因分别说明；两路挡位等待回读时的待刷新状态与最近有效观测时间。

终端沿用按功能标识执行的现有控制入口，为暖风提供与通用温控一致的模式和目标温度操作。

### Apple Home 与实物验证

使用已有配对和数据目录，在设备、网络和凭据正常时完成以下三组验证。低挡操作可以与 Home 操作或路径切换合并进行。用 `status DID` 核对控制和回读实际使用的路径。

| 场景 | 操作与通过条件 |
| --- | --- |
| Home 日常操作 | 在同一个浴霸入口操作照明开关和亮度、暖风启停和目标温度，将吹风和换气分别调到关闭、低挡（50%）和高挡（100%）。观察暖风与吹风互斥、换气可与二者分别共存。Home 在原生请求受理后 10 秒内显示实际反馈。保持页面打开，在米家调整暖风功率、在浴霸面板切换一次风挡，核对暖风启停和风速在设备状态改变后 30 秒内自动更新。 |
| 直连与云端的低挡操作 | 在直连和云端分别将吹风、换气各调到低挡一次，共四次。核对实际运行的风道，以及直连 `set_bh_mode` 或云端 Action 的执行记录。对照同一路径 `get_prop` 返回的挡位、内置当前温度和 Home 显示。若温度自然变化，核对 Home 在设备提供新读数后 30 秒内更新。 |
| 重启与路径切换 | 用原数据目录重启一次，再完成一轮直连失效、云端接管、直连恢复。确认原配对、名称、照明端点和浴霸入口仍可用。重启从进程启动起计，切换从接管路径具备通信条件起计，均应在 120 秒内取得新反馈并能执行新控制。核对命令记录，确认已发送的旧命令没有重放。 |

核对暖风启停时以设备报告的功能状态为准，停机后的散热延时单独观察。验证结束后恢复原设置和工作状态。现场未覆盖的路径或未出现的温度变化在验收时说明。
