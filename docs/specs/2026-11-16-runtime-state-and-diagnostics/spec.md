# 运行状态、选路与诊断的结构整理

以 `main` 的 `9f333e1` 为基线，一次整理 Xiaomi Adapter 的状态归属、设备运行实例、路由与诊断、逻辑设备快照、终端渲染和相关测试。采用按需生成诊断快照的方案。一次控制为什么走中枢、上次温度从哪里读到、终端为什么显示该值，都能追溯到负责这项事实的模块。

## 与既有模块的边界

这次结构审查发现，修改一条访问规则的主要成本，是要同时追踪写入该事实的模块、重新解释它的诊断代码，以及持有另一份结果的消费者。整理是否有效，看同一事实的写入点是否收拢、控制与诊断能否共用一次判断，以及新增一种设备时需要同步修改哪些分支。

`configuration` 用 `SourceFacts` 与当前配置生成 `Plan`。计划已经携带下一份 `CommittedConfiguration` 及对应的 `DerivedConfiguration`，`app` 在存储提交成功后一起安装运行实例和派生关系。`storage` 负责编码与事务，`matter` 从逻辑设备读取状态并负责协议投影。小米通用能力识别和型号补丁归 `xiaomi/capability`，中枢和云端驱动共用的帧与握手机制归 `xiaomi/mqtt`。本设计通过这些已有接口取得功能、配置和连接事实。[模块职责](../../../README.md#代码组织)

## Adapter 的状态归属

| 状态 | 写入职责 | 其他模块如何使用 |
| --- | --- | --- |
| 账号与认证 | 凭据管理维护账号、米家会话与 HA 授权各自的代次和恢复状态，以及中枢证书有效期。认证检查时间由完成该检查的操作写入。 | 米家 HTTP、云端 MQTT 和中枢分别按所需凭据判断资格。诊断使用同一组认证事实生成报告。 |
| 家庭、目录与准入 | 目录同步维护当前家庭、已确认的组成员关系、拆分设备记录、云端访问事实及目录错误。每个 DID 的 `DeviceSlot` 负责描述加载和准入。配置安装接收已提交的描述、设备实例和群组关系图。 | 规划读取最新完整描述和关系。运行中的读写使用已安装实例、对应的已提交绑定和随配置生效的群组关系图。 |
| 连接与访问 | 中枢维护当前会话、设备访问结果、网关状态和目录恢复后的优先级。直连维护每个 DID 的资格与已确认连接。云端通知维护 MQTT 会话，各功能的订阅由其运行实例持有。 | 中枢、直连和云端分别向选路提供连接及不可用原因。目录错误与中枢访问错误各自保存原因，在生成诊断时组合。 |
| 命令、刷新与报告 | 命令协调器记录发送、实际路径与回执。刷新器记录读请求及其结果。状态发布者接收变更通知。 | 命令或反馈有新进展就能更新报告，即使设备路径和认证都没有切换。 |

`Context` 组装这些对象并协调跨模块操作。例如，`Live` 中的凭据和代次与 `Context` 中的 HA 刷新、米家拒绝记录归入凭据管理，设备集合归入家庭目录，中枢会话归连接管理。安装新会话、替换凭据、撤销设备访问等操作由所属模块修改私有状态，再通知受影响的消费者。释放可变借用后再通知、调用其他模块或等待异步结果。

`Network` 采用一个网络接口。中枢连接、云端通知连接和 LAN 发现执行 I/O，`lan_target` 给出直连实际使用的地址与超时。生产端由 `XiaomiNetwork` 实现这四项操作，测试端的 `TestNetwork` 为同一组路径提供可控对端。这是基线提交从 `Context` 移出测试网络参数后形成的边界。

`DeviceSlot` 允许同时持有最新描述（`candidate`）、已提交描述（`committed`）和服务中的实例（`admitted`）。加载中的任务以自己的生命周期标识和目标型号／URN 结算。新目标取代旧目标后，迟到的旧结果只能结束自己的工作。配置提交失败时，最新完整描述可供重试，旧实例继续服务。成员确认、访问资格和描述错误可以独立变化。例如缓存重算失败的原因由一次成功识别清除，重复收到相同目录时仍可查询。确认撤权时，当前来源立即失去访问资格。[设备功能组合与描述更新](../2026-10-29-device-capability-composition/spec.md)

## 路由决策与切换历史

一次决策从同一时刻的凭据、家庭、连接、设备访问、功能绑定和订阅事实取得候选。每项候选携带可用连接或具体不可用原因。相同条件在本次求值中检查一次，候选列表、选择结果和错误说明复用这份结果。设备级摘要、功能级读取以及只读属性的云端资格各用对应的条件。

| 操作 | 选择规则 |
| --- | --- |
| 用户控制 | 正常优先中枢，其次直连、云端。中枢目录降级时依次选择直连、云端、仍有访问资格的中枢。只读设备没有控制路径。直连按已提交的协议和具体功能绑定判断。 |
| 自动读取 | 设备摘要和功能的选中读取路径表示按当前选路规则可发出自动读取的路径。中枢目录降级时，控制功能和只读功能均优先直连、其次云端。仅剩仍有访问资格的中枢时，保留中枢读取候选，选中读取路径为 `none`，等目录恢复后再读。BLE／代理子设备的传感器可在云端在线标志不可靠时使用已授权路径。混合设备分别判断每项功能。 |
| 主动通知 | 从已就绪且仍有效的中枢或云端订阅得出活动来源。直连读写与推送就绪分别判断。虚拟灯组的通知由已确认成员及其订阅状态汇总。 |
| 专用操作 | 浴霸低挡控制和共享反馈读组按各自的操作资格选择直连或云端。高挡、独立开关等标准属性使用标准路径。 |

控制与观察分别判定候选资格，再交给同一个小函数按优先顺序选路，收拢 `control_path_with_direct` 与 `observation_path_with_direct` 中重复的分支。候选列表报告访问资格，实际选择还取决于操作。例如中枢降级且只有中枢可用时，同一插座可以有中枢控制路径，自动读取的选择为空。发送端在实际发送边界检查所选连接、凭据和设备实例的有效性。相同的路径名称可以对应新的中枢连接、直连客户端或米家会话代次。已发送或可能已发送的写入由原请求结算一次，迟到结果按原实例归属处理。[统一选路与发送边界](../2026-11-01-ip-lan-and-legacy-miio/spec.md#统一选路)

全局切换原因属于优先级变更。每个 DID 记录上一次已处理的控制路径、读取路径和活动通知来源的种类，以及最近一次实际切换的原因。首次纳入路由时建立比较基线，包括当前无路径的情况。访问条件变化时，按影响范围比较设备及依赖它的灯组，只计算记录切换所需的信息。订阅实际接管某个功能时，即使设备摘要仍显示同类来源，也记录这次交接。重复目录、普通属性反馈和重复查询保留原原因。设备移除时释放它的切换记录，同一 DID 重新准入时建立自己的基线。

## 诊断的读取与发布

`AdapterStatus` 是一次只读投影。构造时取一次当前时间，从各所有者读取认证与证书、网关与目录、待处理设备、路径、订阅、观测、读取错误及命令回执。控制和刷新直接使用各自的运行事实。适配器内原先可变的整份 `AdapterStatus` 及从中反查证书的依赖随之移除。

每个有待处理问题的 DID 生成一条 `pending` 记录。先列当前的描述或配置规划问题，再依次列出已安装实例的功能订阅和读取问题。各项按自己的恢复结果清除，全部解决后移除这条记录。尚无已安装实例的设备也可报告其描述或配置规划问题。

凭据和证书按查询时刻判断。即使维护任务还没获得执行机会，越过有效期的路径也即时失去资格。若本次选择相对已记录的路径只因到期而改变，快照可直接给出对应的到期原因。维护任务处理该期限时记录实际变更并唤醒消费者。一次读取前后，切换记录、订阅、刷新队列和事件通知次数相同。HA 令牌到期只影响依赖它的路径，有效米家会话仍可处理 HTTP 控制。

发布器先登记现有事件监听，再读取快照。首次发布当前状态，后续在发生可见变化时才回调，退出时交付最后一次有变化的状态。发布器可持有上一次发出的值用来去重。命令完成、订阅交接、凭据到期、目录或读取失败都由对应事件唤醒发布器，查询频率不影响切换历史或报告能否送达。

## 单设备运行实例与反馈

`DeviceWork` 协调一个具有不可变原生描述的运行实例。连接、动作帧、观测和订阅已有各自的实现模块，同一次切换中一起使用与清理的状态归相应模块持有。跨职责的交接从 `DeviceWork` 进入。

| 状态 | 生命周期和用途 |
| --- | --- |
| 原生连接与订阅 | 连接、准备中的订阅、就绪绑定和活动来源属于原生实例。仅替换逻辑设备时复用可用订阅。原生实例退役时取消它的订阅准备、尚未发送的读取与灯光帧。 |
| 逻辑投递与命令 | `LogicalSink` 持有当前逻辑设备、命令消费者的生命周期和按功能维护的共享风扇电源协调状态。仅切换读取或通知来源时，已有风扇电源协调要求重新读取。替换整个逻辑设备时，旧消费者结束，新目标重新协调电源并结算初始读取。继电器将已观测的电源与模式交给新目标，mcn04 空调按来源重新建立动态控制范围。 |
| 观测与来源 | `Observations` 维护观测次序、新鲜度、识别迟到读写的代次，以及按功能、按输入的观测来源。继电器电源通知更新功能与电源属性的来源，随后到达的模式通知只更新模式属性的来源。风扇原生模式、mcn04 控制范围和浴霸共享反馈由各自的观测处理保存。 |
| 读取与刷新 | `RefreshState` 拥有排队、在途、再次读取需求、基线、首次结果和读取错误。功能读取与共享读组的路径交接也归刷新器维护，比较上次选中的连接身份，使旧读取失效并安排所需基线。共享读组第一次求值即使选不到路径，也要建立内置温度的初始可用性。 |

浴霸的一次共享读取给两路风扇和内置温度提供原始反馈，由 `SharedFeedbackState` 保存整组观测来源、时间和各字段的解码结果。某个字段无效时记录其原始值与原因，同包的有效字段照常采纳。相关命令一经发送就使较早的在途读取失效。命令受理、结果不确定或收到相关的新通知时，才标记等待新反馈并安排回读。周期读取也能入队，这个动作本身不会设置等待标记。因此旧读取的有效性、等待新反馈和读取队列各有独立含义。直连和云端均失效后，当前共享读取路径为空，内置温度来源不可用，诊断仍可显示上一次从直连读到的 `26.5 °C`。路径恢复后按新连接读取。[浴霸共享反馈契约](../2026-11-10-bath-heater-control/spec.md)

## 逻辑设备状态与终端

`FunctionKind` 在构造边界用穷尽匹配创建封闭枚举 `RuntimeValue` 的对应变体。变体直接决定 `FunctionState`，由编译器检查快照投影是否覆盖全部种类。插座、继电器和灯可共用电源与命令协调，继电器携带自己的模式，灯携带自己的照明状态。各测量量和状态传感器可复用载荷结构，运行值保留足以识别其对外快照的种类。静态量程、灯型和控制能力从 `FunctionDescription` 取得。

`Function::snapshot()` 从运行值生成逻辑状态，再组合物理可用性、版本和适用的温度来源。独立温度传感器、浴霸内置温度、空调绑定环境温度各自表达原有语义。外部调用者继续通过 `FunctionSnapshot` 获取状态。内部的电源、命令协调器和灯光状态访问共用相应运行载荷的匹配，新增功能时由编译器指出待补的构造和投影分支。

独立温度功能的获取路径以当前可执行的读取或已就绪且有效的通知为准。中枢目录降级、自动读取暂停且通知也不可用时，该温度来源失效。若温度是设备唯一的非电量功能，Matter `Reachable` 为 `false`。诊断保留最近读数，绑定该功能的空调将环境温度显示为未知。读取或通知路径恢复后，传感器恢复可达，空调在新路径取得首个有效温度读数后恢复显示。[绑定温度的状态约定](../2026-11-01-air-conditioner-enhancements/spec.md#温度状态)

桥接终端在 `list`、`status` 和 `status DID` 开始时，通过应用已有的来源句柄取得一次即时诊断，同时取得本次命令的已提交配置视图。各段渲染使用同一份输入。状态回调仍可用于输出变化日志，命令的当前路径直接来自本次取样。认证命令可独立呈现账号报告。

`render` 负责 DID 过滤、设备遍历和输出顺序。控制、测量与状态、配置与发布、路径与命令诊断由对应的格式化函数负责。格式化只读取所给的设备快照和诊断。现有设备标识、字段名称、单位、未知值、顺序和命令语法作为输出契约，覆盖隐藏成员、未发布的回路及待接入设备。

对尚无已提交配置、但已有待处理记录的 DID，`status DID` 复用 `list` 的 `DID (名称): pending (原因)` 格式，显示该设备当前的待处理原因。只有在已提交配置和待处理记录中都找不到该 DID 时，才返回 `Unknown device DID.`。

## 测试组织与验收条件

审查点名的五个测试文件按实际混合的行为整理。浴霸的 `bhf.rs` 围绕控制、共享反馈和首次就绪归组，`bhf_direct.rs` 覆盖直连与中枢／云端协作、掉线及恢复。`relay.rs` 按回路发布、模式反馈和控制组织，`credentials.rs` 按米家会话、HA 令牌和中枢证书组织，`light_commands.rs` 按帧合并、接管／取消和原始回执组织。单一主题即使较长也可独立成篇，跨越多项职责才能证明的场景保留为一个用例。

测试复用现有 `Rig`、可控时钟和协议对端。浴霸共享反馈、面板模式等特定输入随使用它们的场景组织。协议握手由协议测试验证，设备测试使用仓库中的 MIoT 描述样本观察控制、反馈与恢复结果。[设备样本](../../../tests/fixtures/miot/)

| 场景 | 可观察的结果 |
| --- | --- |
| 已选中枢的证书刚到期，维护任务尚未运行 | 查询立即显示新的选择和中枢证书到期原因。连续查询没有写入或唤醒。维护任务随后驱动状态发布，同一内容只回调一次。 |
| 米家 HTTP 故障、HA 令牌到期或中枢目录降级 | 报告指出实际原因。控制、自动读取和通知分别使用适用的来源。仅有有效通知的只读功能仍能接收状态。 |
| 中枢目录降级且温度传感器只剩中枢可访问 | `status DID` 的读取候选仍含 `hub`，设备和温度功能的选中读取路径均为 `none`。目录恢复前不发出中枢属性读取，已就绪的有效通知仍能更新温度。 |
| 上述传感器仅有温度功能，通知失效后恢复 | 通知失效期间传感器不可达，诊断保留最近读数，绑定空调的环境温度为未知。订阅恢复就绪时传感器可达，空调在收到新的有效温度通知后才显示该值。 |
| 新设备首次获取描述或规划配置失败，尚无已提交配置 | `list` 和 `status DID` 显示同一设备名称及对应失败原因。另查配置和待处理记录中均无记录的 DID 时，仍提示 `Unknown device DID.`。 |
| 新描述获取失败，仍在服务的旧实例也出现属性读取错误 | `list` 中该 DID 只有一条 `pending` 记录，先列描述错误，再列读取错误。读取成功后只剩描述错误，描述获取恢复后该记录消失。 |
| 设备描述更新、逻辑替换、移除后重新准入 | 提交失败期间服务原配置。逻辑替换可复用原生订阅。原生替换或移除后，迟到反馈不能更新新实例，已发送命令仍按原回执结算。 |
| 浴霸共享读组从直连切换到无路径再恢复 | 在发布回调尚未执行时，直接运行 `status DID` 即可同时看到当前读取路径、最近观测来源及原始温度。此用例从真实终端入口取样，免去测试辅助函数手动注入 `AdapterStatus` 的步骤。 |
| 设备快照与终端输出 | 以现有设备样本覆盖电源／继电器／灯、窗帘、风扇、温控、测量和状态传感器。Matter 和终端读取一致的逻辑状态，终端命令在同一配置版本下展示功能和诊断。 |

整体交付同时满足以上行为和仓库的开发检查。[开发检查](../../../README.md#开发检查)
