# 运行状态、选路与诊断的结构整理

MiGate 从米家目录识别设备，把已提交的功能装配成 Matter 端点。命令通过当前可用的连接发出，回执说明设备是否受理，观测说明设备处于什么状态。Matter、终端和诊断分别从负责这些事实的模块取值。

MiGate 作为应用交付，内部 Rust 接口和存储表示可以随设备模型调整。整理是否有效，取决于修改一条规则时需要修改几处，或一次状态变化需要维护几份数据。代码量可与整理起点 `9f333e1` 对照。

## 从设备描述到已提交配置

`xiaomi::capability` 在 MIoT 描述入口识别标准服务和属性。`Service` 集中判断指定名称和类型标识的属性是否唯一，`Property` 集中解释访问权限、布尔控制属性、整数和数值格式。各品类决定哪些属性必需、哪些可选，以及支持的范围、步长、单位和组合。空调可以接受浮点编码的整度目标温度，暖风要求整数编码。通用解析和型号补丁使用相同的属性规则。[设备功能组合](../2026-10-29-device-capability-composition/spec.md)

`NativeDescription` 描述设备实际使用的控制与反馈方式，也负责判断两份描述能否复用原生实例。比较覆盖有序的功能 ID 及各自完整的 `FunctionBindings`、电量绑定、刷新触发属性，以及生效的直连协议、旧协议属性映射和适配计划。适配计划包括标准模式、共享反馈读组和关联刷新。仅改变展示名称可以复用原生订阅。例如，两份设备描述中的暖风功能 ID 和目标温度属性编号相同。旧描述声明最高可设 45 °C，新描述声明最高可设 46 °C。可设范围变了，MiGate 在新描述提交成功后替换持有旧范围的原生实例，按新上限校验设温命令。

暖风和空调的目标温度绑定共用 `ThermostatTemperatureBinding`，存储使用对应的 `WireThermostatTemperature` 编解码。能力模型的错误对应实际解析结果，移除已无构造点的 `UnsupportedLightGroup`。

家庭目录以 DID 为键维护 `DeviceSlot`。`confirmed` 表示米家已在本次运行中确认该设备属于所选家庭。仅从存储恢复的成员仍待确认。普通设备的目录名称保存在 `catalog_name`。目录按组 DID 查已确认的灯组记录来识别原生灯组。记录提供名称和成员，`spec_type` 字段给出读取功能描述所用的 MIoT 实例类型标识（URN）。记录未提供此标识时，目录直接报告缺少设备类型。灯组是否发布取决于已提交配置。拆分设备记录随所选家庭的目录更新。

目录保留米家返回的访问资料（`cloud_access`）以及该 DID 是否被云端明确拒绝（`cloud_forbidden`）。普通设备的访问资料包含型号、URN、在线状态和直连资料。设备离线只更新在线状态。云端拒绝立即停用该设备的云端路径。普通设备须在后续同步中取得该 DID 的访问资料，原生灯组须成功确认本组关系，才能恢复云端路径。米家确认设备退出家庭时，立即撤销该来源的全部访问并移除目录条目。

`latest_description` 持有最近一次完整取得的 MIoT 描述及其识别结果。每个 DID 同时只加载一份描述，即使目录尚未给出型号和 URN 也可以发起首次读取。目标变更时取消旧任务。结果须来自当前任务，并与目录已给出的目标型号和 URN 匹配。读取或识别失败时，条目保留上一次完整描述，并记录出错的操作、目标和原因。目标重新与已有描述匹配，或新描述读取成功时，清除对应的读取错误。启动时重新识别存储中的描述失败，设备继续使用已提交的识别结果。该 DID 的诊断保留这次失败，直到重新识别成功。

米家设备信息更新后，`app` 将目录提供的最新信息（`SourceFacts`）和当前已生效的配置（`CommittedConfiguration`）交给 `configuration`。写库前，`configuration` 比较新旧信息，算出下一份配置及其发布与组成员关系（`DerivedConfiguration`），并确定哪些设备实例需要安装、复用、替换或退役。这些结果组成 `Plan`。

运行中，只要一台已配置设备的新型号或 URN 尚无匹配描述，或一个已配置灯组的目录记录缺少 URN，本轮规划就对当前家庭仍保有的全部设备沿用已提交描述，对仍有效的灯组沿用已提交关系。其他设备已取得的新描述也暂缓发布，等上述条件解除后一并应用。已确认退出家庭的设备仍立即撤权。

`storage` 负责事务和编码。写库成功后，`app` 安装实例、派生关系和配置，再通知消费者。目录和内存中的配置可以共用本次提交的完整描述，省去按 DID 回填已提交描述的步骤。写库失败时，最新描述留在目录中供重试，仍有访问资格的实例继续按旧绑定服务。

设备改名、继电器类型或标签变更、温度传感器绑定在 `app` 共用一个提交入口。入口先写库，使相应变更与新配置一起生效，再通知消费者。各操作负责自己的校验和生效动作。改名同步来源设备及派生描述。改变已发布回路的类型会推进回路与根配置版本，并请求重建网桥。温度绑定安装到服务中的空调，已有绑定可在来源消失后解除。继电器映射与传感器绑定共用按设备键和功能 ID 查找已安装功能的入口。

## 实例生命周期与端点装配

Adapter 通过目录条目的可选句柄 `DeviceSlot.work` 查找和退役在服务的 `DeviceWork`。首次加载描述的设备，以及已有完整描述但没有可桥接功能的设备，都可以只有目录条目。`DeviceWork` 持有实际读写使用的原生绑定、直连任务和已确认的直连客户端，并协调订阅、观测和刷新。`LogicalSink` 持有当前逻辑设备、命令消费者及按功能维护的共享风扇电源协调状态。

| 变更 | 运行时处理 |
| --- | --- |
| 仅更换逻辑设备 | 保留原生实例，复用直连客户端和就绪订阅，结束旧逻辑消费者。新目标重新协调风扇电源并结算初始读取。继电器接收已观测的电源与模式，mcn04 空调按当前来源建立动态控制范围。 |
| 更换原生实例或来源授权、撤回设备来源、停止 Adapter | 退役旧实例时停止它的直连任务并释放客户端，撤销订阅准备、未发送的读取与动作帧，通过所属 sink 关闭逻辑设备。已经发出的请求由原回执结算，迟到反馈只属于原实例。 |
| 同一 DID 再次准入 | 取得本次来源的匹配描述并随整批配置提交后，清除撤销记录，安装实例，以本次接入建立路由比较基线。等待期间，已撤权的旧描述和旧组关系不参与规划。 |

`EffectiveConfiguration` 持有已提交配置、派生关系和已安装条目 `entries`。创建网桥时，从这份配置取得根版本，按发布键、独立回路和当前家庭仍保有的来源筛选条目。按已预留的端点号装配可见功能、稳定身份、配置版本和活动的 `PhysicalDevice` 句柄。处理器一次消费装配输入，运行中经设备句柄读写当前状态。历史端点预留由存储持有。这个流程取代 Adapter 和 App 各自维护的 `DeviceRegistry`，也消除 `App::frozen()` 与网桥之间整表保存、再克隆的步骤。

## 连接、订阅与选路

Adapter 的 `Context` 组装运行对象。凭据管理维护账号、米家会话与 HA 授权各自的代次、拒绝及恢复状态，以及中枢证书有效期。完成认证检查的操作记录检查时间。中枢维护当前会话、设备访问结果、网关状态和目录恢复后的优先级。直连按当前家庭授权、设备的直连资料和在服务原生实例的协议判定资格。云端通知维护当前 MQTT 会话。各所有者完成变更并释放可变借用后，再通知消费者、跨模块调用或等待异步结果。

米家 HTTP 返回 426 时，响应正文中的 `message` 为 `SERVICETOKEN_EXPIRED` 表示当前米家会话过期，即使业务码为 0 也进入已有的会话恢复流程。其他 426 响应保留 HTTP 错误。恢复成功后重新同步家庭目录。

`Network` 提供中枢连接、云端通知连接、LAN 发现和直连目标地址与超时，由 `XiaomiNetwork` 和可控的 `TestNetwork` 实现。`xiaomi::mqtt` 共享帧、握手、发送进度、保活和入站 QoS 2 处理。中枢驱动负责实际写入前的请求检查和出站 QoS 2 发布，云端通知驱动负责自己的收发循环和订阅应答。

中枢和云端连接各自持有属性与事件的订阅结果，同一属性可以在两边分别就绪。两边的订阅入口都接收回执处理函数，共用准备订阅、确认回执属于当前连接和本次准备、记录逐项成功或失败、判定就绪、结束或撤销订阅的逻辑。每个功能记录实际接管它的来源。中枢按本地请求启动准备，云端另行管理设备在线订阅和并发额度。可选电量订阅的失败可单独诊断。

选路从当时的凭据、家庭、连接、设备访问、功能绑定和订阅状态得到候选及不可用原因。控制与观察分别判定候选资格，共用优先级选择。设备摘要、混合设备的各项功能和只读属性使用各自适用的资格。

| 操作 | 选择规则 |
| --- | --- |
| 用户控制 | 正常依次选择中枢、直连、米家云端。中枢目录降级时优先直连、其次云端，仍有访问资格的中枢可用于控制。直连按已提交的协议和功能绑定判断。只读设备的控制路径为空。 |
| 自动读取 | 按实际可发起读取的路径选择。中枢目录降级时优先直连、其次云端。仅剩中枢时，读取候选仍可列出 `hub`，设备及相应功能的选中读取路径为 `none`，待目录恢复后再读。BLE／代理子设备的传感器可使用已授权的云端路径，即使云端在线标志不可靠。 |
| 主动通知 | 根据当前有效且已就绪的中枢或云端订阅选择来源。直连读写资格与推送就绪分别判断。虚拟灯组的通知来源按已确认成员及其订阅汇总。 |
| 专用访问 | 浴霸低挡控制和共享反馈读组按各自资格选择直连或云端。高挡、独立开关等标准属性使用标准路径。 |

同一条通知检查来源有效性和期望来源时共用一次设备路由计算。新来源接管后，以更新后的订阅状态计算可用性和切换记录。批量检查设备时可共用本次的时间、连接和授权信息，每个 DID 按自己的功能求值。复用限于输入相同的一次处理，后续事件和实际发送边界读取当时的事实。[统一选路](../2026-11-01-ip-lan-and-legacy-miio/spec.md#统一选路)

全局切换原因记录优先级变化。每个正在服务的 DID 在其目录条目上保留一条选路历史，由选路模块记录上次选定的控制路径、读取路径、活动通知来源及最近一次实际切换的原因。首次求值即使没有可用路径也记录选择，此时原因可以为空。访问变化时只比较受影响的设备及依赖它的灯组。订阅实际接管某个功能时，即使设备摘要中的来源种类相同，也记录这次交接。普通属性反馈和重复目录沿用最近的原因，诊断查询只读取历史。设备来源撤回或该 DID 结束服务时清除这条记录。

## 命令发送与设备反馈

开关、灯、窗帘、风扇和温控的标准属性写入共用中枢、直连和云端的实际发送与逐项回执处理。一个布尔属性就是一项属性写入，中枢统一用 `WriteProperties` 编解码 `set_properties`。发送端记录实际路径、发送时点及对应连接的错误。多属性写入部分成功时仍能区分每一项的结果，由设备按步骤结算动作。普通开关按功能顺序执行，同一设备的独立回路可以分别推进。多步设备命令和灯光帧在各自的调用方处理批次顺序、动作有效性和反馈。

Home 继电器命令按 MiGate 发出命令时已知的家庭资格和回路模式判断一次。实际传输按所选连接的身份检查凭据和运行实例仍然有效。传输层确认请求在写出前已撤回时，可以重新选路。已发送或可能已发送的写入由原请求结算一次。普通插座成功受理后，沿用既有观测次序判断是否采纳目标值。继电器成功回执确认命令已受理，电源状态由设备通知或回读更新。这项观测决定在共用的回执处理后执行一次。[插座的观测次序](../2026-10-06-cloud-access-routing/spec.md#观察顺序与迟到结果)

风扇、暖风和空调共用 `StepCoordinator` 和队列条目管理提交、等待上一条操作、出队、取消与回执结算。每种设备定义自己的命令、替代条件和执行步骤，例如风扇调速、暖风以电源控制制热、空调按运行模式解释目标温度。切换读取或通知来源时，需要共享电源协调的风扇重新读取电源。

`Observations` 按功能和输入维护观测次序、时间与来源，用于判断迟到的读取和写回执。继电器电源通知更新电源与功能的来源，后到的模式通知只更新模式属性的来源。风扇原生模式、mcn04 动态控制范围由相应观测处理保存。`RefreshState` 维护排队、在途、再次读取需求、首次结果、基线和读取错误。读取路径交接按实际连接身份使旧读取失效，安排新基线。共享读组首次求值即使没有路径，也建立内置温度的可用性。

浴霸的一次共享读取给两路风扇和内置温度提供反馈。`SharedFeedbackState` 保存整组来源、时间和逐字段解码结果。无效字段记录原值与原因，同包有效字段可以采纳。相关命令一经发出，较早的在途读取便失效。命令受理、发送结果不确定或收到相关新通知时，标记等待新反馈并安排回读。周期读取也可入队，入队本身只表示有读取需求。直连和云端都失效时，当前共享读取路径为空，诊断仍保有上次读数及来源。[浴霸共享反馈](../2026-11-10-bath-heater-control/spec.md)

## 逻辑设备、灯光与 Matter

`FunctionKind` 在构造时通过穷尽匹配选择 `RuntimeValue`。运行值直接投影成对应的 `FunctionState`，`Function::snapshot()` 再组合可用性、版本和温度来源。静态量程、灯型和能力取自 `FunctionDescription`。插座、继电器和灯共用适用的电源与命令载荷，继电器另有模式，灯另有照明状态。测量与状态传感器可以共享载荷结构，运行值携带对外状态需要的种类。

暖风和空调共用电源与设定温度的观测。暖风持有内置温度和来源状态，制热模式由电源表达。空调持有设备上报的模式、风速和摆风，环境温度从绑定的传感器读取。独立温度功能在有可执行读取或有效就绪通知时可达。两者都失去时保留最近读数供诊断，绑定空调显示环境温度未知。若温度是设备唯一的非电量功能，Matter 的 `Reachable` 为假。新路径取得首个有效读数后，空调恢复显示。[环境温度与可达性](../2026-11-01-air-conditioner-enhancements/spec.md#温度状态)

`device::lighting`（`src/device/lighting/`）管理亮度和颜色轨迹、时钟、动作令牌、逐帧提交及原始剩余时间。色相和饱和度共用计时与恢复进度，色相依方向绕环，饱和度连续移动到边界即停止。`matter::lighting` 解释命令选项、`OnLevel` 和 `WithOnOff`，给出轨迹的单位、时长、插值坐标及相应帧的电源目标。设备层按计划生成 `LightTarget`。例如色温在一秒内从 400 走到 200 mired，半程是 300 mired，对应约 3333 K 的设备目标。剩余毫秒由 Matter 编码成 `RemainingTime` 并按簇的规则报告。[灯光规划与报告](../2026-10-19-architecture-restructuring/spec.md#灯光规划轨迹与-matter-报告)

Matter 的组合处理器为端点装配实际支持的簇。风扇与空调共用风扇控制簇的属性、命令和 `FanMode` 校验，暖风与空调共用温控簇的属性和命令校验。各簇按本端点公开的属性表处理请求，越界的 `FanMode` 写入先检查数据版本。空调的温控类型随处理器声明。设备命令错误统一转换，参数越界用 `ConstraintError`，缺少执行所需状态或当前状态不允许用 `InvalidInState`，设备明确拒绝用 `Failure`。处理器对不支持的命令和受理超时分别使用 `CommandNotFound` 和 `RxTimeout`，日志保留具体命令及失败原因。例如风扇尚未上报电源时，`Toggle` 返回 `InvalidInState`。

Matter 协议栈更新到 `rs-matter` 的 `c86233d`。系统簇和 Groups 处理器在装配时借用本次运行的 `Matter` 实例。普通设备的新订阅使用上游默认的 120 秒最大报告间隔上限，控制端要求的最小间隔仍有优先级。重启时，已保存订阅的报告间隔若与当前协商规则不同，则等待控制端重新订阅；间隔相同则尝试恢复，首次报告失败仍按上游规则删除该订阅。CASE 会话耗尽发送重试后保留接收对端新请求的能力，收到对端新消息后恢复会话。

## 诊断、终端与配对

`AdapterStatus` 按需生成。一次查询取一次当前时间，从各所有者读取认证与证书、网关和目录、路径和订阅、最近观测、读取错误及命令进度。目录错误与中枢访问错误各自保存，生成报告时才组合。凭据按查询时刻判断，即使维护任务尚未运行，到期的证书或令牌也会影响相应路径。若相对上次记录的选择只因到期而改变，此次报告可以直接给出到期原因。有效的米家会话仍可用于 HTTP 控制。

读取诊断只产生报告。维护任务处理到期或实际变化时才更新切换记录、唤醒消费者。发布器先登记监听，再读取当前状态，首次交付当前值，随后用上次已发值去重，退出时交付最后的可见变化。命令完成、订阅交接、凭据到期、目录或读取失败都能独立触发发布。

`list`、`status` 和 `status DID` 在命令开始时取得一次即时诊断和当次已提交配置视图。展示已生效的设备资料时，按当前家庭仍保有的 DID 从这份配置取描述，包括已识别但没有运行实例的设备。`render` 组织 DID 过滤、遍历和输出顺序。控制与传感状态、配置与发布、路径与命令各自格式化，只读取传入的设备状态和诊断。每种输出使用约定的设备标识、字段、单位和未知值，覆盖隐藏组成员、未发布回路和待接入设备。

每个有待处理问题的 DID 只有一条 `pending`，先列处理设备描述或计算新配置时遇到的问题，再列已安装实例的订阅和读取问题，各项随各自恢复而清除。某个 DID 尚无已提交描述时，`list` 和 `status DID` 均用 `DID (名称): pending (原因)` 显示记录。第一次加载描述就失败的设备也可以显示目录给出的名称。配置和待处理记录都查不到该 DID 时，`status DID` 返回 `Unknown device DID.`。

认证报告按同一组规则生成账号、米家会话、HA 授权、证书、登录失败和恢复指引。查询输出按终端布局排版，日志使用对应行的级别。登录失败阶段与验证提示来自收到的这份 `AuthReport`。米家登录提供登录 URL，Matter 的配对事件提供窗口时长、手动配对码和配对串。终端共用字符二维码渲染，两种入口各自提示扫码方式、有效时间和后续操作。

## 验证设计

测试围绕行为组织。浴霸控制、共享反馈和首次就绪放在拥有这些行为的用例中，直连与中枢／云端协作覆盖掉线与恢复。继电器覆盖发布、模式反馈与控制，凭据覆盖米家会话、HA 令牌与中枢证书，灯光动作覆盖帧合并、接管／取消与原始回执。设备用例使用实际 MIoT 描述样本、现有 `Rig` 和可控时钟，协议对端单独验证握手与传输。[设备描述样本](../../../tests/fixtures/miot/)

设备、能力和 Adapter 的可见性按二进制入口及实际调用者收紧。跨文件 `#[path]` 挂载归回实际被测子模块。米家单属性读取、云端无回调订阅、测试客户端构造及模型字段断言归对应测试，重复的 `next_power` 共用。新库只有一条桥接配置记录的断言并入 `tests/storage.rs`。进程测试负责向空库写入账号，存储单测的凭据替换还负责更新运行中的记录与代次，各有独立入口。

| 场景 | 验收条件 |
| --- | --- |
| 显示名称变化、暖风设温上限变化、配置写库失败 | 名称提交后可见，原生订阅可复用。上限变更写库失败时，仍有授权的实例按旧范围校验。用目录保留的描述重试成功后替换实例，新范围生效。 |
| 已配置设备变更描述目标或灯组目录缺少 URN | 旧加载任务的迟到结果不能覆盖新目标。等待期间保留仍有效的已提交灯组关系。同期完成识别的无关新插座在等待条件解除后一并发布。 |
| 启动时重识别失败 | 重复目录保留启动重识别错误，成功识别后清除。 |
| 已建立直连的设备更换实例或失去访问 | 仅更换逻辑设备时复用直连。更换原生实例时停止旧实例的直连任务并释放客户端。云端拒绝只停用云路径，确认退出家庭则立即停止全部来源访问，即使配置写库失败。 |
| 新建网桥或重新准入同一 DID | 网桥使用当次已提交的身份、功能和端点，端点持有的设备句柄能读到后续反馈。退役后迟到的回执只结算旧请求，新实例从自己的来源取得状态，重新接入的 DID 建立自己的选路基线。 |
| 原数据目录普通重启 | 保留配对、名称和端点，控制与新的设备反馈约两分钟恢复，允许控制端重新建链和页面更新的少量额外时间。Home 自动恢复状态同步，无需手动刷新或重开页面；恢复后不重放旧命令。 |
| 中枢证书刚到期、HA 令牌到期或米家 HTTP 故障 | 查询立即显示受影响的路径及实际原因。连续查询不改动切换记录或队列。维护事件独立驱动发布，相邻相同的报告只交付一次。 |
| 温度传感器在中枢目录降级时只剩中枢 | 设备和温度功能的读取候选仍含 `hub`，选中路径为 `none`。有效通知仍可更新温度。最后一个来源消失再恢复时，可达性随之变化，空调等待有效新读数。 |
| 两边订阅同一属性，一边失败或新来源接管 | 诊断分别列出两边的就绪与错误。接管后可用性和切换原因反映新来源。重复目录和普通反馈保留最近的实际切换原因。 |
| 插座或继电器写入、分步命令或多属性写入 | 单项和多项均能查到实际路径与对应回执。成功时，插座可显示目标值。写入后若已收到有效电源通知，则保留通知值。继电器在设备反馈后更新电源。独立回路可以并行，已发送的写入只结算一次。 |
| 浴霸共享读取部分字段无效，或从直连切到无路径再恢复 | 同包有效字段可用，无效字段保留原值与原因。直接执行 `status DID` 可同时看到当前读取路径、最近来源与上次温度。恢复后按新路径读取。 |
| 有待处理新设备，或在服务的设备同时发生描述和读取错误 | `list` 和 `status DID` 显示同一名称及待处理原因。两类错误按恢复顺序分别消失。查询两处都不存在的 DID 得到未知设备提示。 |
| 设备状态与 Matter 命令 | 开关、继电器、灯、窗帘、风扇、温控及传感器的状态在 Matter 与终端一致。缺少电源观测的风扇切换返回 `InvalidInState`，越界写入返回 `ConstraintError`。 |
| 调光与调色 | 轨迹按选定坐标产生中间帧和最终帧，设备在计划指定的帧联动电源。色相可绕环，饱和度到边界停止，Matter 向控制端报告剩余时间。 |
| 终端认证与配对 | 给定同一份认证报告，日志和查询给出一致的恢复指引。登录二维码编码登录 URL，配对二维码编码 Matter 配对串，手动配对码同时可用。 |
